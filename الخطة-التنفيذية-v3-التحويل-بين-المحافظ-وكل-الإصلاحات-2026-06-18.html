👛 الميزة الجديدة — التحويل بين المحافظ (تصميم كامل قويّ)

راجعه 3 وكلاء من الجذور: البنية (~70% جاهزة كأنماط مجرَّبة) · التصميم الكامل · الفريق الأحمر الأمنيّ/AML. الدفتر سليم بنيويًّا: القيد DR CUSTOMER_WALLET_{sender} · CR CUSTOMER_WALLET_{receiver} متوازن آليًّا (post_journal يرفض غير المتوازن)، والثابت Σ CUSTOMER_WALLET == Σ balance_minor محفوظ، والمطابقة لا تُظهره كاختلال. الشروط الإلزاميّة: تحديث balance_minor ذرّيًّا مع القيد · قفل الصفّين بترتيب ثابت (wallet.id — وإلّا سباق من صنف HIGH-01) · جدول WalletTransfer بـidempotency_key UNIQUE.

الطرق الثلاث + حكم الأمان

(1) برقم المحفظة 🟢 الأأمن — المسار الافتراضيّ
كيف: رقم `LY-##########` (wallet_service.py:58) غير قابل للتعداد كالهاتف ولا يكشف اسمًا بمجرّده. تحقّق وجود + ACTIVE.
الضوابط: آمن مع: تأكيد الاسم المقنَّع + atomic+قفل + idempotency + تجميد على مستوى الحساب.
(2) برقم الهاتف + كشف الاسم 🔴 الأخطر — لا يُشحن إلا بالحزمة الكاملة
كيف: تطبيع E.164 (registration_router.py:86) → بحث المستخدم → عرض display_name+المحفظة قبل التأكيد.
الضوابط: حصاد الأسماء أصيل (المحدِّد IP فقط). إلزاميّ: إخفاء جزئيّ للاسم (mask_name لا يوجد) + موافقة المستقبِل (discoverable_by_phone OFF) + حدّ يوميّ لكلّ-مُهاجِم + CAPTCHA + عدم تأكيد الوجود + ربطه بتدفّق تحويل لا دليل.
(3) بـQR كود 🟡 متوسط — آمن بـQR موقَّع منتهٍ
كيف: توكِن HMAC `{wn,uid,exp,nonce}`؛ توليد QRCodeSVG + مسح html5-qrcode (موجودان). resolve يتحقّق exp(410)+nonce لمرّة-واحدة GETDEL(409).
الضوابط: خطر quishing/replay. إلزاميّ: HMAC موقَّع + nonce + exp قصير (120ث) + استخدام-واحد + كشف الاسم المقنَّع بعد المسح + لا مبلغ ثابت + تثبيت scheme.
