① الخلاصة

استكمالًا لاتّجاه التدقيق العدائيّ (بعد مسار النقد)، دقّقتُ مسار المحفظة (المال الرقميّ الموازي). وجدتُ عيبًا أخطر من عيب النقد: دورة حياة الحجز (commit/release/adjust) كانت check-then-act على حالة الحجز بلا قفل صفّ — تحت التزامن قد تُحدِث قيدًا محاسبيًّا مزدوجًا أو تسريب مال. أصلحتُه بثلاثة أقفال آمنة (نفس نمط بقيّة المسارات)، بلا تغيير مبلغ/منطق.

النتيجة
عيب تزامن حقيقيّ (أخطر) أُصلح · حرّاس الحالة والقيود سليمة
طبيعة الإصلاح
قفول صفّ with_for_update (no-op على SQLite، تشاؤميّ على PG) — بلا تغيير مبلغ
القلب الماليّ
مصون — FIN-COR PASS · بلا migration

③ العيب — دورة حياة الحجز بلا قفل تزامن · خطير

الدوال الثلاث (commit_reservation/release_reservation/adjust_reservation) كانت تقرأ صفّ الحجز بلا with_for_update ثمّ تفحص state == "HELD" ثمّ تنتقل. حارس الحالة يحمي النداء التسلسليّ فقط؛ والمُستدعون (order_service · dispatch_service · accept_timeout · provider_service) لا يقفلون صفّ الطلب. فالفحص-ثمّ-الفعل غير ذرّيّ.

سباق أ — تثبيت مزدوج

خيطان (إعادة نداء) يريان HELD ⇒ كلاهما يثبّت ⇒ قيد محاسبيّ مزدوج (إيراد + ذمم مضاعفة)

سباق ب — تثبيت + إفراج

تسليم (commit) يزامن إلغاءً (release) ⇒ كلاهما يرى HELD ⇒ العميل يُسترَدّ + المزوّد يُدفَع = تسريب مال

هذا أخطر من عيب النقد (الذي كان انزياح عدّاد): هنا قيد مزدوج فعليّ أو تسريب مال.

④ الإصلاح + أمان الجمود

# commit / release / adjust — قفل صفّ الحجز ⇒ الفحص-والانتقال ذرّيّ
reservation = await session.scalar(
    select(WalletReservation).where(... order_id ...).with_for_update()
)
if reservation is None or reservation.state != "HELD": return reservation

# release / adjust يعدّلان balance_minor ⇒ اقفل المحفظة أيضًا (مثل reserve/spend)
wallet = (await session.execute(
    select(WalletAccount).where(... id ...).with_for_update()
)).scalar_one_or_none()
الدالّةقفل الحجزقفل المحفظةالسبب
commit_reservation✅—لا يعدّل الرصيد (القيد فقط)
release_reservation✅✅يردّ الرصيد balance += amount
adjust_reservation✅✅يعدّل الرصيد ±delta
أمان الجمود (deadlock): ترتيب القفل ثابت — الحجز ثمّ المحفظة. reserve يقفل المحفظة فقط (الحجز صفّ جديد)؛ لا دورة انتظار دائريّة بين الحجز والمحفظة على نفس الزوج ⇒ لا جمود.

⑤ المؤكَّدات الإيجابيّة

  • حارس الحالة: HELD-only صحيح (مع القفل صار ذرّيًّا) — لا تثبيت/إفراج بعد التغيّر.
  • القيود متوازنة: record_wallet_reservation_commit / _release متوازنة (WALLET_HELD يبقى = إجماليّ الطلب).
  • مسارات مقفلة أصلًا: reserve_wallet · spend_from_wallet · apply_debit تقفل المحفظة (CHECK رصيد ≥ 0 قائم).

⑥ الاختبارات — توضيح تلوّث الحزمة الجزئيّة

تشغيل -k الجزئيّ أظهر 4 فشل، لكنّها ليست من تغييري: اختبار المحفظة test_phase457_wallet_search نجح بالعزل 10/10 (الفشل في الحزمة = تلوّث DB المشترك StaticPool)؛ والثلاثة الأخرى (phase372 بحث المزوّد · phase11 مقاييس · phase457) كلّها ضمن الأساس المسموح به (allow-listed baseline) وغير متعلّقة بأقفال المحفظة. التحقّق الحاسم = البوّابة الكاملة: NEW=0.
