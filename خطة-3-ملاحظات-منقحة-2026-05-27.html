٠. التَّحذير الكبير

🚨 الخطة الأَصلية (الـ4 موجات A→B→C→D) فيها 3 عُيوب أَمنية حَرجة لو نُفِّذت كَما هي:

  1. HMAC على 4 أرقام = أَمن وَهْمي: السائق يَفتح DevTools، يَنسخ الـhash + salt، يَكتب JS صَغير يُجرّب كل 10,000 احتمال (0000-9999) في 10 مللي ثانية. الـHMAC ليس KDF — لا scrypt، لا bcrypt. الـcode يَنكشف فوراً.
  2. User row مُنشَأ قَبل email verify: أي شخص يَستطيع تَسجيل email لشخص آخر بـtypo (user@gmial.com) → الـattacker الحقيقي مالك user@gmial.com يَستلم الـOTP → يَدخل ويَتحكَّم بالـaccount.
  3. G-2 reassign لا يُجَدِّد الـcodes: سائق A يَطلب reassign، OPS يُوافق، الـorder يَنتقل لـB، لكنّ pickup_token و delivery_handoff_code يَبقَيان كَما هما → السائق A يَستطيع نَظرياً التَّسليم بِشَريك (لو احتفظ بالـcode + بنفس offer قَبل revoke).

اِكتشف الإيجنت أيضاً عَيباً موجوداً سابقاً (قبل الخطة): verify_handoff لا يَفحص حالة الـorder — حتى لو الـorder ألغاه العميل، الـverify يَنجح. هذا bug قديم يَحتاج إصلاح ضِمن G-2.

الخلاصة: الخطة الأَصلية ابتدأت بـA (آمن) → C (عُيوب أَمنية) → D (عُيوب أَكثر). الخطة الجديدة تَبدأ بـA → B (مع 3 إصلاحات أمنية) → D (مع 4 إصلاحات أمنية) ثم تَتوقَّف قَبل C لِقَرار جَذري: هل نَستبدل HMAC بـed25519 QR cryptographic؟

٢. قَرارات جَذرية مَطلوبة منك (قَبل التَّنفيذ)

قَرار #1: نَموذج verify offline للسائق

المُشكلة: HMAC على 4 أرقام يَنكسر في 10ms بـbrute-force محلي. ثلاث خيارات:

الخيارالوصفالمَخاطرالجُهد
أ — لا offline verify للسائق (الأَأمن) السائق يَكتب الـcode، يَنتظر النِّت. لو لا نِت، يَفتح driver_emergency(kind=NO_INTERNET_AT_DELIVERY) → OPS يُؤكِّد يَدوياً ✅ صفر مَخاطر أمنية. ⚠️ UX سَيء في مناطق ضَعيفة ~1 ساعة (driver emergency kind + UI)
ب — زيادة الـcode إلى 6 أرقام + Argon2id backend يُولِّد 6 أرقام. الـapp تَستخدم Argon2id بـcost عالٍ (100ms/hash). brute-force = 1M × 100ms = 27 ساعة ⚠️ Argon2id على هواتف ضَعيفة قد يُجَمِّد الـUI لـ500ms على verify المَشروع ~5 ساعات + اختبار أَداء
ج — QR cryptographic بـed25519 backend يُولِّد key-pair للـorder، private للعميل (في QR)، public للسائق. السائق يَمسح QR من شاشة العميل → التَّوقيع يُتحقَّق محلياً بـpublic key ✅ آمن cryptographically. ⚠️ يَحتاج العميل أن يَعرض QR (ليس فقط 4 أرقام) ~8 ساعات (تَصميم جَديد كامل)

تَوصيتي: الخيار أ (الأَبسط + الأَأمن). G-1 يَتقلَّص إلى "F-15 queue + UX feedback صَريح" بدون verify محلي.

قَرار #2: email verify كـgate أم اختياري؟

أإجباري للكل قبل أيّ نشاطأَأمن — حلّ R-9
بإجباري لـprovider/driver/staff فقطمتوازن
جاختياري للجميعتَجربة أَسهل لكن R-9 يَبقى

تَوصيتي: ب (إجباري لـprovider/driver/staff، اختياري لـcustomer). لو ج، نَحتاج حَلاً مُختلفاً لـR-9 (مثل عَدم سَماح password reset عَبر email حتى verify).

قَرار #3: مَنطق تَبديل السائق (Settlement)

إذا سائق A قَبل offer + استلم بَضائع + تَعَطَّلت دَرّاجته + سائق B أَكمل التَّسليم:

  • أ: B يَتقاضى كل الأَجر، A لا شيء
  • ب: A يَتقاضى distance(A→provider→A_stop)، B يَتقاضى distance(A_stop→customer)
  • ج: A يَتقاضى نِسبة ثابتة (مثلاً 30%) بِغَضّ النَّظر عن المَسافة

تَوصيتي: ج (الأَبسط). توَثَّق السياسة في policy doc.

٤. تَفاصيل كل عَيب + إصلاحه

🔴 العُيوب الحَرجة (11)

R-1 G-1

brute-force محلي لـHMAC 4 digits = أَمن وَهْمي

المشكلة: الخطة تَخزن handoff_code_hash على جهاز السائق. السائق يَفتح DevTools → IndexedDB → يَنسخ {hash, salt}. يَكتب JS: for (let i=0; i<10000; i++) compute_hmac(String(i).padStart(4,'0'), salt). SubtleCrypto.digest('SHA-256') = 1µs/hash → 10,000 hash = 10ms. الـcode يَنكشف فوراً.

الإصلاح: اِنظر القَرار #1 أعلاه. التَّوصية: لا offline verify (الخيار أ).

R-2 G-1

local counter غَير مُتزامن مع server

المشكلة: backend عَدّاد handoff_attempts max=3 (delivery_handoff_router.py:59). لو السائق جَرَّب 100 محاولة offline (local hash-compare) ثم وَجد الـcode → يُرسَل واحدة فقط للـbackend مع attempts=0. الـ3-attempt cap يَصبح بلا مَعنى.

الإصلاح: أَرسل local_attempts_count مَع الـpayload. الـbackend يَدمج: max(server_attempts, local_attempts). لو > 5 → freeze + alert.

R-3 G-1

persistence split (IndexedDB ↔ localStorage)

المشكلة: الخطة تَقول "نَحفظ في IndexedDB". لكنّ useOfflineQueue المَوجود يَستخدم localStorage["tawa-offline-queue-v1"]. الـbundle (في IndexedDB) قد يُمسح بَينما الـqueue (في localStorage) يَبقى → السائق يُرسل verify بدون bundle مَوجود.

الإصلاح: وَحِّد على IndexedDB (مكتبة idb-keyval). تَعديل useOfflineQueue.ts ليَستخدم نَفس الـstore.

R-4 G-1

pre-check failure → action يَتابع رغم state-conflict

المشكلة: useOfflineQueue.ts:117 — لو الـstateCheckUrl يَفشل في pre-check (مثلاً 404 لأنّ الـorder ألغي)، الـcatch يُكمل (continue) ويُرسل أيّ حال. الـorder المُلغى يَنجح في verify (bug).

الإصلاح: فَرِّق بين network-fail (continue) و state-conflict-error (drop). إذا 404/410 على pre-check → اِحذف الـaction + إشعار السائق "الطلب ألغي".

R-5 G-2

pickup_token لا يُجَدَّد عند reassign

المشكلة: order.pickup_token يُولَّد مَرَّة عند request_pickup_token (pickup_verify_router.py:104). لو سائق A استلمه + حَدَث reassign لـB، الـtoken باقٍ. A يَستطيع verify بِه إن كان الـorder في DRIVER_AT_PROVIDER.

الإصلاح: ops_reassign_driver يُصفِّر order.pickup_token = None ذرّياً. B يَجلب token جَديد عند فَتح الـapp.

R-6 G-2 (bug قَديم)

verify_pickup لا يَفحص driver_id الحالي

المشكلة: pickup_verify_router.py:155-165 يَفحص فقط: token signature صحيح + order_id يَتطابق + token لم يَنتهِ. لا يَفحص أنّ token_driver_id == order.driver_id الحالي. لو الـorder.driver_id تَغيَّر، الـtoken القديم يَعمل!

الإصلاح: أَضِف فحص if token_driver_id != str(order.driver_id): raise 403 "outdated token".

R-7 G-2

handoff_code لا يُجَدَّد + العميل لا يَعرف

المشكلة: delivery_handoff_code يُولَّد مَرَّة عند create (order_service.py:804). لو reassign + جَدَّدنا الـcode، العميل عنده الـcode القَديم في الـUI (cached). السائق B يَأتي، العميل يَقول رَمز قَديم → mismatch دائم.

الإصلاح: ops_reassign_driver يُجَدِّد delivery_handoff_code = generate_handoff_code() + يُرسل push notification للعميل + frontend customer يُلتَقَط الـpush ويُعيد جلب /handoff-code.

R-8 G-2

A's bundle لا يُسحب على reassign

المشكلة: سائق A عنده IndexedDB cached bundle (في حال نَفَّذنا G-1). reassign يَحدث، لكن A's device لا يَعرف. A يَستطيع verify-local-match ثم queue → backend يَرفض 403 (لا offer ACCEPTED) → action يُحذَف صامتاً.

الإصلاح: publish "bundle_revoked" event عَبر SSE/FCM للسائق A → التطبيق يَحذف IndexedDB + يَعرض رسالة "الطلب نُقل لسائق آخر".

R-9 G-5

User row مُنشَأ قَبل email_verify = privilege escalation

المشكلة: POST /auth/register يُنشئ User + Role + Profile (registration_router.py:333+). الـuser يُمكنه login بـphone+password حتى لو الـemail غير مُتحَقَّق منه. لو الـemail خَطأ (typo سَلَب email شخص آخر)، الـattacker الحقيقي يَستلم OTP ويَكتسب الـaccount.

الإصلاح: اِحجز الـregistration كـ"pending-registration" في Redis (TTL 30 دقيقة) بدلاً من إنشاء User row. الـrow يُنشأ فقط بعد email_verify ناجح. اِسترداد على timeout = الـpending يُحذف، المُسجِّل يُعيد التَّسجيل.

R-10 G-5

enumeration via 404

المشكلة: registration_router.py:723 — if not db_user: raise 404 "Email not found". أيّ شخص يَستطيع POST /email/verify-request مع أيّ email ويَعرف هل هي مُسجَّلة (404 vs 200). enumeration attack.

الإصلاح: always return 200 (مع fake delay عَشوائي 100-500ms). انتظار لو الـuser غير موجود = simulate التَّقدُّم.

R-11 G-5

لا زر "تَغيير البريد" في email_verify step

المشكلة: المُستخدم كَتب user@gmial.com، لا يَستلم OTP. لا يُمكنه تَغيير الـemail (لا UI). محاولات: حذف الـaccount (لا login بَعد)، إعادة التَّسجيل (409 "phone already registered"). عالِق إلى الأَبد.

الإصلاح: الـstep email_verify يَعرض زر "البريد خاطئ؟ تَغيير" → يَعود لـstep "form" مع الـemail مَفتوحاً للتَّعديل. لو نَفَّذنا R-9 (pending-registration in Redis)، الـUpdate سَهل.
