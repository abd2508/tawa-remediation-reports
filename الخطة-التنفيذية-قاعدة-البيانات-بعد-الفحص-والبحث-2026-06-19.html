المرحلة 1 — مكاسب سريعة (مخاطرة منخفضة، قيمة عالية)

التغيير: تحويل أعمدة JSON المُستعلَمة بالمسار إلى jsonb (ALTER COLUMN ... TYPE jsonb USING col::jsonb)، وإضافة فهارس تعبيريّة على المفاتيح المُستعلَمة فعلًا (مثل (display_name->>'ar')) لا GIN كاملة (البحث يحدّد 2-3 مفاتيح فقط؛ GIN يكلّف 30-50% على الكتابة). الأولويّة: providers.display_name (بحث حيّ)، ثمّ بقيّة الـ49 تدريجيًّا.
الملفّات: models/provider.py، models/catalog.py، ... + هجرة aaXX (JSONB + expression index). لا تغيير كود (jsonb متوافق مع json في القراءة).

التحقّق: PG-validate up/down + EXPLAIN ANALYZE يُظهر استخدام الفهرس + بحث المزوّد لا يتغيّر سلوكه.
P1-B فهرسة الـ43 FK غير المفهرسة أقوى⏱ يوم
التغيير: إضافة فهرس B-tree على كلّ عمود FK ساخن بلا فهرس — يبدأ بالساخنة على المسار الحرج: orders(address_id), order_items(catalog_item_id), order_items(variant_id), cash_collections(driver_id), complaints(opened_by_user_id), customer_debts(order_id), wallet_transfers(sender_wallet_id)+(receiver_wallet_id)، وبقيّة الـ43.
الملفّات: __table_args__ في النماذج المعنيّة + هجرة aaXX واحدة بكلّ الفهارس.
الهجرة/التنفيذ: هجرة: op.create_index('idx_orders_address','orders',['address_id']) × 43 (مع CREATE INDEX CONCURRENTLY في الإنتاج لتفادي القفل عند الكِبَر).
المخاطر: منخفضة جدًّا — فهارس إضافيّة فقط (لا تغيير سلوك). كلفة كتابة طفيفة مقابل تسريع JOIN/حذف كبير.
التحقّق: PG-validate + التأكّد من ظهور الفهارس + رجعة الاختبارات.
P1-C حذف الأعمدة الميّتة (تنظيف المخطّط) أحسن⏱ ساعات

الملفّات: models/payment.py + modules/payments/wallet_service.py (إزالة wallet.version += 1) + هجرة aaXX (drop_column).
الهجرة/التنفيذ: هجرة: op.drop_column('wallet_accounts','version'); op.drop_column('wallet_accounts','status'). تحقّق صفر-قراءة مرّة أخيرة قبل الحذف.
المخاطر: منخفضة — مؤكَّد عدم القراءة (grep + التدقيق العدائيّ السابق). يزيل فخًّا أربك التدقيق.
التحقّق: PG-validate up/down + رجعة اختبارات المحفظة (يجب أن تبقى خضراء).
P1-D تفعيل WAL/PITR + مراقبة أأمن·أقوى⏱ يوم

الملفّات: docker-compose (مجلّد /wal-archive + إعادة تشغيل postgres مرّة) + shared_preload_libraries=pg_stat_statements.
الهجرة/التنفيذ: لا هجرة مخطّط — إعداد تشغيليّ + إعادة تشغيل postgres واحدة (نافذة صيانة).

المرحلة 2 — تحصين القلب المالي + تجهيز التوسّع
P2-A قيد قاعدة لتوازن الدفتر (نقل الثابت من الكود) أأمن·أدقّ⏱ أسبوع
التغيير: trigger مؤجَّل (CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED) يفحص Σ debit_minor = Σ credit_minor لكلّ journal_id عند الـcommit ⇒ يستحيل قيد غير متوازن حتى لو أخطأ الكود. (نمط Stripe/Adyen: دفتر مزدوج غير قابل للتغيير + idempotency.)
الملفّات: هجرة aaXX (دالّة PL/pgSQL + constraint trigger على ledger_entries). post_journal يبقى (دفاع عميق مزدوج).
الهجرة/التنفيذ: هجرة: دالّة تجمع DR/CR per journal_id وتُطلق exception عند اللاتوازن؛ trigger مؤجَّل بعد كلّ INSERT.
المخاطر: متوسّطة — يجب اختبار أنّ كلّ المسارات الحاليّة تنشئ قيودًا متوازنة (هي كذلك بفضل post_journal) قبل التفعيل، وإلّا تُرفَض.
التحقّق: تدقيق: لا قيد غير متوازن تاريخيًّا (trial-balance) + اختبار عدائيّ (محاولة قيد غير متوازن ⇒ رفض القاعدة).
P2-B ربط حارس Σ المحفظة حيًّا (بعد تدقيق) أأمن·أدقّ⏱ أيّام
التغيير: تحويل check_wallet_ledger_invariant من استشاريّ إلى فحص دوريّ مُنبِّه (pg_cron كلّ ساعة ⇒ ينشئ ReconciliationException عند أيّ انحراف Σ CUSTOMER_WALLET ≠ Σ balance_minor). لاحقًا: قيد أصرم بعد ضمان التطابق التامّ.
الملفّات: reconciliation_service (الدالّة موجودة) + جدولة pg_cron + ربط بالتنبيهات.
الهجرة/التنفيذ: لا هجرة مخطّط (الدالّة موجودة) — جدولة + تدقيق بيانات أوّلًا.
المخاطر: متوسّطة — يجب تأكيد أنّ الثابت يصدق على البيانات الحاليّة قبل التنبيه (تفادي إنذارات كاذبة من أرصدة بذور بلا قيد).
التحقّق: تشغيل الفحص على الإنتاج ⇒ diff=0 قبل الجدولة.
P2-C التقسيم الزمنيّ (pg_partman + pg_cron) أقوى⏱ أسابيع
التغيير: تحويل الجداول الـ7 المتنامية إلى partitioned by range(created_at) شهريًّا عبر pg_partman، مع pg_cron لإنشاء الأقسام مسبقًا وفصل/حذف القديم (أرشفة) ⇒ استعلامات وصيانة أسرع آلاف المرّات عند الملايين.
الملفّات: هجرة aaXX لكلّ جدول (إنشاء parent partitioned + ترحيل البيانات + إعداد partman). الكود لا يتغيّر (الاستعلامات بـcreated_at تستفيد من partition pruning).
الهجرة/التنفيذ: هجرة معقّدة لكلّ جدول (تحويل جدول قائم إلى مُقسَّم) — تُنفَّذ بحذر مع ترحيل بيانات؛ تبدأ بـlogin_attempts/otp_events (أقلّ حساسيّة) ثمّ audit_log ثمّ ledger_entries (الأحسس).
المخاطر: متوسّطة-عالية — تحويل جدول مُقسَّم على بيانات قائمة يحتاج خطّة ترحيل + اختبار حِمل. ledger_entries آخرًا.
التحقّق: PG-validate على نسخة + التأكّد من partition pruning (EXPLAIN) + سلامة العدّ قبل/بعد.
P2-D تفعيل الـoutbox القائم (CDC موثوق) أمرن·أذكى·أقوى⏱ أيّام
التغيير: ربط event_outbox (الموجود بلا publisher) بـrelay worker يستنزفه ضمن الترانزاكشن وينشره (Redis pub/sub قائم أصلًا، أو وسيط رسائل) ⇒ بثّ أحداث موثوق بلا «dual-write» (نمط Stripe/Revolut/Adyen).
الملفّات: models/audit.py::EventOutbox (موجود) + كاتبو الأحداث يكتبون إليه + worker جديد في main.py (نمط حلقات الخلفيّة القائمة).
الهجرة/التنفيذ: لا هجرة (الجدول موجود) — كود relay + ربط منتجي الأحداث.
المخاطر: منخفضة-متوسّطة — البنية موجودة؛ الإضافة relay + idempotency على النشر.
التحقّق: اختبار: حدث يُكتب ترانزاكشنيًّا ⇒ يُنشَر مرّة واحدة بالضبط؛ فشل النشر ⇒ إعادة محاولة.
المرحلة 3 — التوسّع والذكاء والأمان الأعمق
P3-A ترقية PostgreSQL 16 → 17 ثمّ 18 أقوى·أحسن⏱ أيّام (مع اختبار)
التغيير: 17: vacuum أخفّ 20×، JSON_TABLE، تحسينات تقسيم. 18: async I/O (io_uring) حتى 3× مسح تسلسليّ، skip-scan لفهارس B-tree المركّبة. ترقية تدريجيّة (16→17→18) بـpg_upgrade أو dump/restore.
الملفّات: صورة postgres في الـcompose + اختبار التوافق (الامتدادات pg_trgm).
الهجرة/التنفيذ: لا هجرة مخطّط — ترقية محرّك القاعدة (نافذة صيانة + نسخة احتياطيّة + اختبار على نسخة أوّلًا).
المخاطر: متوسّطة — ترقية كبرى؛ اختبار شامل على نسخة + خطّة rollback (النسخة الاحتياطيّة).
التحقّق: تشغيل كامل الاختبارات على PG الجديد + قياس الأداء.
P3-B PgBouncer + نسخة قراءة (read replica) أقوى·أمرن⏱ أسبوع
التغيير: مجمّع اتّصالات (PgBouncer) أمام القاعدة + نسخة قراءة (logical/streaming replication) لتوزيع القراءات الثقيلة (تقارير/بحث/لوحات OPS) ⇒ تحمّل أحمال أعلى دون لمس الكود الكتابيّ.
الملفّات: بنية تحتيّة (compose/خادم) + توجيه القراءات للنسخة (طبقة جلسة).
الهجرة/التنفيذ: لا هجرة — بنية تحتيّة.
المخاطر: متوسّطة — إعداد تشغيليّ؛ يتطلّب فصل القراءة/الكتابة في طبقة الجلسة.
التحقّق: اختبار حِمل قبل/بعد.
P3-C PostGIS للمكان (دقّة جغرافيّة) أدقّ·أذكى⏱ أسبوع+
التغيير: تثبيت PostGIS + تحويل zone_suspensions.polygon_* و إحداثيّات المزوّد/السائق إلى geometry/geography مع فهرسة GiST ⇒ أقرب-سائق ومناطق-خدمة دقيقة في القاعدة بدل haversine بايثون + احتواء-مضلّع حقيقيّ.
الملفّات: هجرة aaXX (امتداد + أعمدة geometry + GiST) + geo_service يستعمل استعلامات PostGIS (مع احتفاظ بالاحتياطيّ).
الهجرة/التنفيذ: هجرة: CREATE EXTENSION postgis; ALTER TABLE ... ADD COLUMN geom geography; CREATE INDEX ... USING GIST.
المخاطر: متوسّطة — امتداد جديد + ترحيل إحداثيّات؛ يتعايش مع Redis GEO الحاليّ.
التحقّق: مقارنة نتائج أقرب-سائق PostGIS مقابل haversine (تكافؤ) + أداء.
P3-D pgvector — ذكاء داخل القاعدة أذكى⏱ أسابيع (مع النموذج)
التغيير: تثبيت pgvector (0.8: HNSW/IVFFlat، أسرع 9×) لتخزين تضمينات: كشف الاحتيال (تشابه متجهيّ لإشارات velocity_decisions/fraud_flags ⇒ شذوذ المعاملات)، توصيات، بحث دلاليّ — كلّه في Postgres دون قاعدة متجهيّة منفصلة.
الملفّات: هجرة aaXX (امتداد + أعمدة vector) + خطّ تضمين (يربط ml_scaffold القائم بنموذج).
الهجرة/التنفيذ: هجرة: CREATE EXTENSION vector; ALTER TABLE ... ADD COLUMN embedding vector(N); CREATE INDEX ... USING hnsw.
المخاطر: منخفضة (إضافيّ) — يبني على ml_scaffold القائم؛ يحتاج بيانات/نموذج تضمين.
التحقّق: تقييم دقّة الكشف على بيانات تاريخيّة.
P3-E RLS + pgcrypto (أمان أعمق) أأمن⏱ أسبوع+
التغيير: RLS: سياسات صفّ على الجداول الحسّاسة (wallet_accounts, orders, wallet_transfers) ⇒ طبقة دفاع ثانية تحت RBAC الكود (العميل يرى صفوفه فقط حتى لو أخطأ الكود). pgcrypto: تشفير حقول PII مختارة في الراحة.
الملفّات: هجرة aaXX (ENABLE ROW LEVEL SECURITY + CREATE POLICY) + ضبط app.current_user في الجلسة + pgcrypto للحقول.
الهجرة/التنفيذ: هجرة: سياسات RLS + ربط سياق المستخدم بالجلسة (set_config).
المخاطر: متوسّطة-عالية — RLS يتطلّب تمرير هويّة المستخدم للجلسة بدقّة؛ خطأ يحجب أو يكشف. يُطبَّق تدريجيًّا.
التحقّق: اختبار: مستخدم لا يرى صفوف غيره حتى باستعلام مباشر.
P3-F تقييم uuid أصليّ بدل varchar(36) أحسن·أقوى⏱ تقييم
التغيير: 134 معرّفًا varchar(36)؛ uuid أصليّ = 16 بايت (مقابل 36)، مقارنة أسرع، فهارس أصغر. تقييم الترحيل (PK+FK) — مكسب أداء/تخزين مقابل هجرة كبرى عالية المخاطرة ⇒ قرار محسوب (قد يُؤجَّل).
الملفّات: كلّ النماذج (PK+FK) — هجرة ضخمة. توصية: تقييم لا تنفيذ فوريّ.
الهجرة/التنفيذ: هجرة كبرى (تحويل نوع كلّ PK/FK) — تُدرَس بعناية أو تُترَك.
المخاطر: عالية — تمسّ كلّ الجداول؛ ليست أولويّة. للدراسة فقط.
التحقّق: n/a (تقييم)
