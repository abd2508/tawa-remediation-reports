الحَقيقة المُتحقَّق منها:

  • الـcert صادر من Let's Encrypt على الـhost المباشَر (لا Cloudflare proxy — DNS A record مباشر إلى 178.105.87.192)
  • nginx الـcontainer يُضيف X-Frame-Options، CSP، إلخ — وَتَمرّ كاملاً للـbrowser عبر host nginx
  • HSTS مُؤَجَّل عمداً (تَعليق صَريح في web/nginx.conf:16: «requires HTTPS/TLS termination (BLOCK-03)»)
خَطر preload: إذا أَضفت preload + includeSubDomains لـ63072000 (سَنتان) دُفعةً واحدة، أيّ خَطأ في تَجديد الشَّهادة أو أيّ subdomain يَحتاج HTTP (مثلاً staging.tawanow.com لو وُجد لاحقاً) سَيؤدّي إلى قَفل المُستَخدِمين خارج المَوقع. لا يُمكن إلغاء preload بسُهولة (تَتطلّب 6 أشهر مَع HSTS مُتبَقّ).

T-4: HS256 + لا secret rotation P2

الواقع

  • jwt_algorithm = "HS256" — مُناسب للـmonolithic لكنّ rotation سَريع للسرّ غَير مَدعوم
  • لو تَسرَّب SECRET_KEY عبر env-leak أو memory dump → كلّ token يَتمّ تَزويره
  • الـjti + Redis revocation مَوجود (P-369) — لكنّه يُلغي tokens صَحيحة، لا يُساعد ضدّ tokens مُزَوَّرة بالسرّ الصَحيح

المُقترَح

الانتقال إلى RS256 (asymmetric) تَحسين defense-in-depth حَقيقيّ لكنّه يَتطلّب:

  • توليد key pair (private + public)
  • تَدوير المفاتيح (key rotation infra)
  • تَحديث كلّ مَكان يَتحقّق من JWT (jwt_service.py + dependencies.py + tests)
  • backwards-compat — لا يَجب أن تَتعطّل tokens مَوجودة لـ60 دَقيقة

الـبَديل الأَسرع: SECRET_KEY rotation policy — env variable يُحدَّث دَوْرياً + JWT يَدعم «أَكثر من سرّ» مَؤقتاً للسماح بالـtransition.

3) المحاكاة الذهنيّة للآثار الجانبيّة

قَبل التَّنفيذ، يَجب توقّع كلّ تَأثير جانبيّ مُحتمَل ووَضع التَّخفيف. إليك السيناريوهات:

السيناريو 1: «المستخدِم يَكتب كَلمة المُرور خَطأً 5 مرّات»

🔥 الخَطر: إذا فَرَضنا 5/15min على /login، مُستَخدِم شَرعيّ يَنسى كَلمته يُقفَل لـ15min — تَجربة سيّئة.
✓ التَّخفيف: رَفع الحَدّ إلى 10/15min + إضافة كَلمة المُرور المَنسيّة كَبَديل واضح في رَسالة الخَطأ («إذا نَسيتَ، اضغط استرجاع»). مفتاح rate-limit يَكون phone+ip فلا يَتداخل مُستَخدِمان على نَفس IP.

السيناريو 2: «اختبارات pytest تَفشل بَعد lockout»

🔥 الخَطر: 9 ملفّات اختبار تَستخدم login مُتَكرّراً — لو فَعَّلت lockout بَعد 5 محاولات، الاختبارات سَتفشل.
✓ التَّخفيف: (أ) الاختبارات تَستخدم هَواتف عَشوائيّة لكلّ اختبار → مفاتيح مختلفة لا تَتداخل. (ب) في conftest.py نُضيف auto-flush لـRedis قَبل كل test. (ج) في dev mode، نَستخدم fakeredis (مُسبقاً مَضبوط) لذا الـrate limit لا يَتراكم بَين الاختبارات.

السيناريو 3: «HSTS preload يُقفِل المُستَخدِمين عَلى TLS broken»

🔥 الخَطر: إذا أَضفنا max-age=63072000; preload اليَوم وانتَهت شَهادة Let's Encrypt بَعد 3 أَشهر (cron renew فَشل) — الـbrowser يَرفض الاتّصال HTTP plain ولن يَقبل HTTPS بشَهادة فاسدة → blackout كامل لا يُمكن إصلاحه إلّا بَعد انتهاء max-age.
✓ التَّخفيف: رَفع max-age بالتَّدريج: 5 دَقائق → 1 يوم → 1 أسبوع → 1 شَهر → 6 أَشهر → سَنة → سَنتان + preload. كل مَرحلة بَعد مُراقبة 48-72 سَاعة. لا preload حَتى استقرار 6 أَشهر مُتتابعة.

السيناريو 4: «register صامت يَكسر تَجربة المُستَخدِم»

🔥 الخَطر: لو وَحَّدنا الرَدّ إلى 200 دائماً، المُستَخدِم الذي يَملك حساباً مَوجوداً لن يَعرف لِمَ لا يَستلم OTP، أو سَيظنّ أَنّ التَّسجيل نَجح لكنّه لن يَستطيع الدخول.
✓ التَّخفيف: النَّمط الحَديث (Twilio/AWS/Stripe): اِستجابة 200 مُوحَّدة + إرسال OTP في كِلتا الحالتَين. لو الحَساب جَديد → OTP يَفتح إكمال التَّسجيل. لو مَوجود → OTP يَفتح login. هذا يَخفي الحالة بِلا كَسر UX.
✓ البَديل المُختصَر: الإبقاء على 409 لكن مَع تَأخير عَشوائيّ 300-800ms + رَسالة عامّة «لم نَستطع إكمال التَّسجيل» بِلا تَفاصيل field. يَزيد كُلفة الـenumeration دون كَسر UX.

السيناريو 5: «الـrate-limit يَكسر اختبار E2E الكامل (السيناريو الذي رَأَيناه قَبل قَليل)»

🔥 الخَطر: السيناريوهات الكاملة (verify_full lifecycle) تَستدعي login 4-6 مرّات للحُسابات المختلفة في 30 ثانية → قد يَصل لحدّ 5/15min.
✓ التَّخفيف: كلّ سيناريو يُسجّل حسابات مختلفة بأرقام هَواتف عَشوائيّة. مفتاح rate-limit phone+ip → كلّ هاتف بُكَيت مُنفصل. لا تَداخل.

السيناريو 6: «X-Forwarded-For spoofing يَكسر التَّبكيت»

🔥 الخَطر: المُهاجم يُرسل X-Forwarded-For: 1.2.3.4 لِكلّ محاولة → كلّ محاولة في bucket مختلف → الـrate limit يَفشل.
✓ التَّخفيف: الكود الحاليّ (SEC-03، Wave 1) يَستخدم X-Real-IP أوّلاً الذي يَضعه nginx فَقط، ثُمّ يَأخذ XFF من اليَمين (آخر مَن أَضافه proxy موثوق). مَحمي بالفعل. ولكن: تَأكّد أنّ host nginx يَضع X-Real-IP صَريحاً.

السيناريو 7: «الـvelocity check للـWALLET يَتعارض مع auth-bucket»

🔥 الخَطر: الـvelocity_check في wallet_router يَستخدم Redis بمفتاح مختلف. إذا أَضفنا بُكَيت auth جَديد بمفتاح مُشابه، احتمال تَصادم.
✓ التَّخفيف: namespace مُختلف: rate:auth:{phone}+{ip} vs rate:wallet:{user_id} vs rate:general:{ip}. لا تَصادم.

+_LOCKOUT_DURATION_SECONDS = 1800   # 30 دَقيقة

+async def _check_lockout(redis, user_id: str) -> bool:
+    key = f"login_lockout:{user_id}"
+    count = await redis.get(key)
+    return count is not None and int(count) >= _LOCKOUT_THRESHOLD

+async def _bump_lockout(redis, user_id: str) -> int:
+    key = f"login_lockout:{user_id}"

+    pipe.incr(key)
+    pipe.expire(key, _LOCKOUT_DURATION_SECONDS)
+    results = await pipe.execute()
+    return int(results[0])
+

الإصلاحRollback إن فَشل

8) خُلاصة + التَّوصية

الفَحص الأمنيّ الأَصليّ ذَكر 7 بُنود — لكنّ التَّتبّع الجذريّ كَشف 5 اكتشافات إضافيّة أَخطر:

  • S-A: /password-reset/confirm يَكشف الهاتف غير المَوجود
  • S-B: /register يَكشف عَبر 3 حُقول (phone, email, username)
  • S-C: لا login lockout — credential stuffing مُمكن
  • S-D: CSP script-src 'self' صَارم — تَحقَّق أَنّه لا يَكسر inline scripts
  • S-E: TLS مُنتَهي على host nginx، الـcontainer nginx يُضيف headers تَمرّ — HSTS يَحتاج تَنسيق

الخطّة المُقترَحة:

  • P0 (~3.5س): F-1 (auth bucket) + F-2 (login lockout). يُغلق credential stuffing فَوريّاً.
  • P1 (~4س + ramp): F-3 (HSTS تَدريجيّ) + F-4 (register uniform) + F-5 (password-reset silent). يَغلق enumeration + ssl-strip.
  • P2-P3 (مُؤجَّل): F-6 (rotation) + F-7 (RS256). تَحسينات defense-in-depth.

تَأكيدات الأَمان:

  • FIN-COR SHAs بِلا تَغيير (لا feature_flags تَعديل)
  • لا migration
  • كلّ إصلاح قَابل للـrollback بِلا data-loss
  • الاختبارات المَوجودة 9 ملفّات topup + 2 ملفّ E2E يَستَمرّ نَجاحها (هَواتف عَشوائيّة، monkeypatch)
