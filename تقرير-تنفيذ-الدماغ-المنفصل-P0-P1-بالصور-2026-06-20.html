ماذا فعلنا بكلمة؟ بنينا «العقل» كبرنامج منفصل، وحفرنا «بابًا» واحدًا آمنًا بين المشروع والعقل بحيث: لو غاب العقل أو تأخّر، يكمل المشروع وكأنّه غير موجود. ثمّ وصلنا نقطتين تجريبيًّا (لوحة مخاطر OPS + ظلّ احتيال COD) — لكن أبقينا العقل مُطفأً، فالمشروع اليوم يعمل بالضبط كما كان، والعقل جاهز للتشغيل متى قرّرت.

٢ الفصل والصمود — «لو انقطع لا يتأثّر المشروع» (مُثبَت)

بلغة بسيطة: الباب بين المشروع والعقل فيه ثلاثة أقفال أمان: قفل «مُطفأ» (افتراضيّ)، قفل «الانتظار 0.15ث فقط»، وقفل «إن فشل العقل مرارًا توقّف عن سؤاله». أيّ قفل يُغلق ⇒ المشروع يكمل بقواعده فورًا.
📸 إثبات الاختبارات العدائيّة (مخرجات حقيقيّة):
$ pytest tests/test_tic_client_resilience.py .... [100%] 4 passed in 0.29s # disabled-by-default → None · gate-off → None · breaker-open → None · state-machine ✓
تقنيًّا: tic_client.score() مُشتقّ من نمط geo_providers (مهلة من config + التقاط ضيّق except (httpx.HTTPError,...)) + بوّابة مخصّصة platform:tic:enabled عبر المسبح المشترك مع كاش 5ث (تفادي اتّصال Redis لكلّ نداء) + قاطع دائرة في الذاكرة (لا round-trip). كلّ مسار يرجع None فورًا ⇒ المُستدعي res if res is not None else القاعدة.

٣ وصل المفاصل المصحّح (بعد المحاكاة)

بلغة بسيطة: المحاكاة العميقة كشفت أنّ مفصل احتيال COD يحجب طلب العميل فعلًا عند تفعيله — فلا يصحّ أن يقرّر العقل الحجب. لذا جعلناه «ظلًّا» يراقب ويسجّل فقط، والقاعدة وحدها تحجب.
المفصلالوصل المصحّحيمسّ قرارًا حيًّا؟
المخاطر المركّب (build_risk_profile)استشاريّ inline آمن — مستهلِك واحد = لوحة OPS عرضيّة (operations_router:4835)؛ يعرض فقط، لا يحجبلا (عرض)
احتيال COD (order_service)ظلّ غير حاجب: القاعدة وحدها تحجب؛ نداء العقل محروس ونتيجته لا تُقرأ هنالا (ظلّ)
التوزيعأُجِّل بوعي: dispatch_scoring مجرّد معاينة OPS لا التوزيع الحيّ ⇒ التحسين الحيّ في P3 بظلّ صارم على find_nearestمؤجَّل
القاعدة الذهبيّة المطبَّقة: أيّ مفصل يمسّ قرارًا حيًّا (COD/التوزيع) ⇒ الدماغ ظلّ لا يحجب ولا يبطئ. المفاصل العرضيّة فقط (لوحات OPS) ⇒ inline آمن. صفر مسّ للمال، FIN-COR ثابت.

٤ خدمة الذكاء المنفصلة — تعمل (smoke حيّ)

بلغة بسيطة: العقل برنامج مستقلّ بذاته (حاوية منفصلة). جرّبناه: سألناه عن درجة مخاطرة، فأجاب بنفس درجة قواعد المشروع بالضبط (توافق 100%) — وهذا يُثبت أنّ «البوّابة» ستعمل بسلاسة عند التشغيل.
📸 تشغيل حاوية العقل واستجوابها (مخرجات حقيقيّة):
# build + run tawa-intelligence, then query its endpoints $ GET /health/live → {"status":"ok","service":"tawa-intelligence"} $ POST /tic/score-risk {trust:50, device_sharing:3, gps_mismatches:2} → {"composite_risk_score":4,"risk_level":"CRITICAL","engine":"rules","model_version":"tic-rules-v1"} $ POST /tic/unknown → {} # مهمّة مجهولة → فارغ → المُستدعي يرجع لقاعدته
تقنيًّا: الخدمة FastAPI (/health/live + /tic/{task}) · orchestrator.route توجيه حتميّ (score-risk→composite_risk، score-cod-fraud→fraud) · وكلاء رول-بورت ينسخون منطق القاعدة (الدرجة 4 = نفس _compute_score للمدخل ذاته) ⇒ توافق 100% في P1 (يُثبت الوصل قبل أيّ نموذج مدرَّب) · feeds/sinks سطوح معرَّفة تُوصَل في المراحل التالية.

٦ المتبقّي مرحليًّا + خطوات التفعيل

بلغة بسيطة: أنجزنا الأساس كاملًا وآمنًا. المراحل التالية تحتاج «وقود» لا يُصنَع بضغطة زرّ: بيانات حقيقيّة لتدريب النماذج، واختبار في «وضع الظلّ»، وذاكرة خادم أكبر للنموذج اللغويّ. لذا تُبنى بالتدريج وبأمان.
المرحلةالمحتوىلماذا مرحليّة
P2نموذج LightGBM→ONNX + River (تعلّم حيّ) + NannyML (مراقبة انحراف) + وضع الظلّتحتاج بيانات موسومة حقيقيّة + بوّابة holdout
P3تخريج ETA + Redis Streams الدائم + التوزيع الحيّ بظلّ صارماختبار حِمل + التوزيع الحيّ حسّاس
P4الوكيل النصّيّ (Qwen3 للعربيّة) + جدار PII (Presidio)الخادم 7.6GB ⇒ يحتاج تحميلًا كسولًا/ترقية RAM
خطوات تفعيل الدماغ (بيدك متى شئت): ① رفع مجلّد intelligence/ + خدمة compose للسيرفر · ② إنشاء دور قاعدة هجين tawa_brain_ro (SELECT على الكلّ + INSERT على جدول التوصيات فقط) · ③ تشغيل الحاوية (--profile intelligence) · ④ ضبط tic_url + قلب البوّابة platform:tic:enabled=1. حتى تفعلها ⇒ صفر أثر.
التوصية: الأساس (P0+P1) منشور ومُثبَت آمنًا. الخطوة التالية المنطقيّة = P2 في وضع الظلّ (نموذج مدرَّب يُقارَن بالقاعدة دون التأثير على أيّ قرار) عند توفّر بيانات كافية — أو تفعيل تجريبيّ للوحة مخاطر OPS أولًا (الأقلّ خطرًا).
