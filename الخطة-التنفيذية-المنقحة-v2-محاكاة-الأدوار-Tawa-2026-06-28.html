R3 — الواجهة لا تَعكِس قيود الخادم

R4 — الفلترة/الترتيب بعد LIMIT

قصّ SQL ثم فلترة بايثون → نتائج ناقصة وترقيم مكسور. ~5 أعراض. العلاج: نقل كل قرار التصفية للاستعلام.

R5 — قراءة-مرة-واحدة في واجهات لحظية

useEffect مبدئي لا يُضمَّن في setInterval → بيانات قديمة بجوار متجدّدة. ~4 أعراض. العلاج: hook تحديث دوري موحّد.

R6 — رسالة واحدة تبتلع أكواد HTTP الدلالية

الخادم يُرجع 410/422/409/403، والواجهة catch عام. ~6 أعراض. العلاج: مُترجِم أخطاء مركزي.

R7 — «أثّر ثم سجّل/احذف» (ترتيب معكوس)

حذف رمز step-up قبل التحويل · استثناء بلا فحص · توقيع بلا idempotency. ~4 أعراض. العلاج: «نفّذ → تأكّد نجاح → سجّل/احذف» + idempotency.

R8 — حالة محلية بلا انتقال (آلة حالة UI ناقصة)

C4 الاستثناء النقدي يحبس الإثبات · حالات عالقة بلا مخرج. ~3 أعراض. العلاج: آلات حالة UI صريحة بكل المخارج.

  • i18n CI gate (فشل البناء على مفتاح ناقص). → G5 + N6.

١٨) قرارات أحتاجها منك قبل البدء

  1. الإذن العام بالتنفيذ + تجاوز المحظورات الخلفية.
  2. F9 البقشيش (مُتنازَع): أوافق على إجراء مراجعة جنائية مالية أولاً (لا تعديل قبلها)؟
  3. F1 SPLIT عدم الحضور: دين على الجزء النقدي أم امتصاص موثّق؟
  4. C4: هل يُسمح بإثبات التسليم بعد استثناء نقدي (تحت مراجعة OPS)؟
  5. مصفوفة STAFF: فتح/إغلاق المتجر — سماح أم إخفاء؟ وباقي البنود الستة.
  6. البنود المُتنازَع عليها (SSE·الفئة·الشكوى/PII): أعيد فحصها دقيقاً قبل أي إدراج — موافق؟
  7. السكوتر: اللوحة مطلوبة أم لا؟
  8. نطاق الدفعة الأولى: الموجة 0 فقط ثم وقفة مراجعة، أم المضي تباعاً؟
توصيتي: الموجة 0 (الست الحرجة) أولاً — مع عزل F9 البقشيش في مسار مراجعة جنائية منفصل — ثم عنقود SPLIT كوحدة باختبار بالقرش، ثم وقفة مراجعة قبل الموجة المالية الكاملة.
