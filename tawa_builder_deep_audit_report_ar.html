F-01 — تناقض FIN-COR حول wallet_peer_transfer

Critical

الدليل: PR #11 يقول إن sealed flags unchanged وتشمل wallet_peer_transfer=false. لكن contracts/feature_flags.yaml الحالي يحتوي wallet_peer_transfer: true. وfeature_flags.py لا يضعها داخل SEALED_FLAGS.

شرح مبسط

تقرير الدمج يقول إن باب التحويلات المالية مغلق، لكن ملف التشغيل يقول إنه مفتوح. هذا تضارب في منطقة مالية.

التأثير

  • ضعف الثقة في FIN-COR.
  • إمكانية تشغيل ميزة مالية قبل اكتمال legal/AML gates.
  • صعوبة قبول المشروع في مراجعة امتثال.

الحل

الخيار المحافظ:
contracts/feature_flags.yaml
wallet_peer_transfer: false

أو:
إنشاء docs/WALLET_PEER_TRANSFER_DECISION_RECORD.md
مع موافقة صريحة وحدود KYC/AML/OPS review.

الأعراض الجانبية

  • تعطيلها قد يكسر UI/tests التي تتوقعها.
  • إبقاؤها true يبقي خطر الحوكمة إذا لم تغلق gates.

اختبارات القبول

python _ai_tools/bin/contract_flag_hash_check.py
pytest backend/tests/*transfer* -q
pytest backend/tests/*feature* -q

F-02 — Launch Gates تمنع الإطلاق رسمياً

Critical

الدليل: contracts/launch_gates.yaml يقول: No soft launch until all blocking gates are CLOSED. لكن GATE_LEGAL وGATE_PAYMENT_SANDBOX وGATE_SECURITY_PENTEST وGATE_DR_RUNBOOK وGATE_OPERATIONS_READINESS وغيرها ما زالت open وblocking.

شرح مبسط

المشروع نفسه كتب شرطاً: لا تطلق قبل إغلاق البوابات. والبوابات ما زالت مفتوحة.

التأثير

  • أي إطلاق عام يخالف عقد المشروع.
  • خطر قانوني وتشغيلي ومالي.
  • لا توجد أدلة كافية لجاهزية السوق.

الحل

docs/launch_evidence/GATE_LEGAL.md
docs/launch_evidence/GATE_PAYMENT_SANDBOX.md
docs/launch_evidence/GATE_SECURITY_PENTEST.md
docs/launch_evidence/GATE_DR_RUNBOOK.md
docs/launch_evidence/GATE_OPERATIONS_READINESS.md

الأعراض الجانبية

إغلاق البوابات شكلياً بلا دليل أخطر من تركها مفتوحة. أضف CI يمنع status=closed بدون evidence.

F-03 — self-claim للموظف لا يزيد عدّاد الحمل active_orders

High

الدليل: في provider_service.py عند self-claim يتم تعيين assigned_staff_id وassigned_at. في distribution_service.py خوارزمية الاختيار تعتمد على active_orders < DEFAULT_CONCURRENCY_CAP، والدالة record_assignment() هي التي تزيد active_orders.

شرح مبسط

الموظف يمسك الطلب، لكن عدّاد “كم طلب عنده الآن” لا يزيد. فيظهر للنظام كأنه أقل انشغالاً من الحقيقة.

التأثير

  • توزيع غير عادل.
  • تكدس طلبات على موظف واحد.
  • SLA أسوأ وتأخير في التحضير.

الحل

if actor_role == "PROVIDER_STAFF" and order.assigned_staff_id is None:
    order.assigned_staff_id = provider_user_id
    order.assigned_at = now
    await distribution_service.record_assignment(
        self.session, order.provider_id, provider_user_id, now
    )

الأعراض الجانبية

قد يحصل double increment إذا كان الطلب محسوباً سابقاً. الحل: زد العداد فقط عند الانتقال من unassigned إلى assigned، واختبر complete/cancel/reject decrement.

F-04 — مسار /providers/me/staff/my-stats لا يستخدم guard المزود المركب

High

الدليل: المسار يستخدم require_active_role. بينما require_provider_permission هو الذي يفحص OperationalProfile.is_suspended إضافة إلى الدور والصلاحية.

شرح مبسط

هناك حارس بسيط وحارس قوي. هذا المسار يستخدم الحارس البسيط، لذلك قد لا يحترم إيقاف الموظف التشغيلي.

التأثير

  • موظف موقوف قد يقرأ إحصائيات المتجر.
  • نموذج الصلاحيات يصبح غير موحد.

الحل

أضف permission:
provider_staff:self_stats

ثم:
Depends(require_provider_permission("provider_staff:self_stats"))

الأعراض الجانبية

قد يحصل 403 للموظفين الحاليين. الحل: اجعلها baseline-held أو أضف migration grandfather.

F-05 — Frontend وE2E ليسا حاجزين في CI الرئيسي

High

الدليل: ci.yml يحتوي contracts/lint/revision/backend-tests. أما web/package.json فيحتوي build/typecheck/lint/test/E2E scripts لكنها ليست ضمن CI.

شرح مبسط

الباكند يُفحص، لكن الواجهة قد تنكسر ولا يمنعها CI من الدمج.

الحل

web:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: "22"
        cache: npm
        cache-dependency-path: web/package-lock.json
    - run: cd web && npm ci
    - run: cd web && npm run typecheck
    - run: cd web && npm run lint
    - run: cd web && npm run test
    - run: cd web && npm run build
