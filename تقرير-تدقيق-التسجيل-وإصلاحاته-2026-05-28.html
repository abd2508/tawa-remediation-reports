النقطة 3 (الحرجة) — تسجيل الموظف كان مكسوراً تماماً

المشكلة

الواجهة كانت تُعامل «معرّف المتجر» كـرقم صحيح:

<input type="number" ... />          ← حقل رقميّ
const pid = parseInt(providerId, 10);  ← يُحوّله رقماً
payload.provider_id = pid;             ← يُرسل رقماً (مثل 123)

لكن المزوّدين في النظام لهم UUID نصّيّ (مثل bf22b239-9bde-42ac-86d0-8af20bbaf781). الخلفية تَتوقّع نصّاً. فأيّ موظف يُحاول التسجيل كان يَحصل على «بيانات غير صالحة» حتمياً.

الدليل الحيّ (قبل الإصلاح)

موظف بـUUID نصّي → ✓ نجح (الخلفية)
موظف برقم 123 (ما تُرسله الواجهة) → ✗ «Input should be a valid string»

الإصلاح المنشور

  • الواجهة: type="number" → type="text"
  • أُزيل parseInt — يُرسل provider_id نصّاً كما هو
  • نوع API: provider_id?: number → string
  • التسمية: «معرّف المتجر (Provider ID)» + مثال UUID + توضيح «سلسلة طويلة من الأحرف»
  • عرض خطأ الحقل تحته بالعربية
بعد النشر: موظف بـUUID نصّي → ✓ نجح حيّاً على tawanow.com

⚠️ ملاحظة تصميمية مهمّة (تتطلّب قرارك)

الإصلاح يَجعل التسجيل يَعمل، لكن كيف يَعرف الموظف UUID متجره (35 حرفاً عشوائياً)؟ هذا غير عمليّ. الحلّ الاحترافيّ مستقبلاً: آلية «كود دعوة» — المزوّد يُولّد كوداً قصيراً (أو QR) من لوحته ويُعطيه للموظف. هذا عمل أكبر — أَنتظر قرارك إن أردته.

النقطة 4 — البريد لم يَكن يُتحقَّق من صيغته

المشكلة: notanemail (بلا @) كان يُقبل عند التسجيل. لاحقاً، تحقّق البريد عبر OTP (Wave 2) سيَفشل في الإرسال لعنوان غير صالح، ويَظنّ المستخدم أنّ بريده مسجَّل صحيحاً.

الإصلاح: أضفتُ مُحقِّق صيغة في الخلفية (regex ^[^@\s]+@[^@\s]+\.[^@\s]+$). البريد يَبقى اختيارياً، لكن إن أُدخل يَجب أن يَكون صالحاً. الواجهة تَعرض الخطأ تحت حقل البريد بالعربية.

الدليل الحيّ (بعد الإصلاح)

بريد خاطئ notanemail → ✗ مرفوض على حقل email ✓
بريد صحيح good@gmail.com → ✓ نجح ✓
بريد فارغ (اختياريّ) → ✓ نجح ✓

النقطة 5 (متبقّية) — موقع المنشأة «مطلوب» بلا فحص

التسمية تَضع نجمة * على «موقع المنشأة» لكن لا فحص JS يَمنع الإرسال بلا موقع، والخلفية لا تَفرضه. النتيجة: قد يُسجَّل مزوّد بلا موقع.

لم أُصلحها (لم تَطلبها). الخياران: (أ) أُضيف فحص JS يَفرض الموقع، أو (ب) أُزيل النجمة إن كان اختيارياً فعلاً. أَنتظر قرارك.
