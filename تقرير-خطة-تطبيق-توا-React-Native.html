0) القرار الأهم — اقرأه أولاً

تنبيه صريح: يوجد تطبيق موبايل عامل بالفعل لمنصة توا، مكتوب بتقنية Flutter (اسمه libya_delivery)، وقد بنيناه ووقّعناه وثبّتناه على جهاز السامسونج في الجلسة السابقة، وهو يعمل (86 ملف، يغطّي العميل/السائق/المزوّد/العمليات). هذا الطلب الجديد يطلب بناء تطبيق من جديد بتقنية مختلفة تماماً (React Native + Expo).

قبل أن نكتب سطراً واحداً، يجب أن تقرّر بوعي ماذا نفعل بالتطبيقين، لأن لكل خيار تكلفة:

الخيارماذا يعنيالميزةالعيب
أ) استبدال Flutter بـ React Native
موصى به إن اخترت RN		 نتوقّف عن تطوير تطبيق Flutter، ويصبح RN هو تطبيق الموبايل الرسمي الوحيد. فريق/كود واحد، لا ازدواجية، توحيد التقنية مع الويب (React). نتخلّى عن عمل Flutter المُنجز (لكنه يبقى مرجعاً للميزات).
ب) تطبيقان معاً نطوّر Flutter و RN في نفس الوقت. — تكلفة مضاعفة، صيانة مزدوجة، تشتّت. غير مُوصى به.
ج) إكمال Flutter بدل RN نوقف فكرة RN ونكمل تطوير تطبيق Flutter الموجود (الذي يعمل اليوم). أسرع وأرخص — العمل موجود ويعمل فعلاً. لا يطابق رغبتك في React Native.
توصيتي بصراحة مهنية: إن كان سبب الانتقال إلى React Native هو توحيد التقنية مع موقع الويب (React) ومشاركة المعرفة/المنطق — فهذا سبب وجيه، وأوصي بالخيار (أ): استبدال Flutter بـ RN، مع الاستفادة من تطبيق Flutter والويب كـ«مرجع ميزات» جاهز (وفّرا علينا تحديد كل الشاشات والمنطق). أمّا إن كان الهدف فقط «تطبيق يعمل بسرعة»، فالخيار (ج) أوفر. الخيار (ب) مرفوض لأنه يضاعف الكلفة بلا فائدة. هذا التقرير مكتوب على أساس أنك ستختار (أ)، لكن القرار قرارك.

1) ماذا فحصت في المنصة (الوضع الحقيقي)

المنصّة الحالية في المجلد /home/a/Desktop/APP/platform وهي «أحادية المستودع» (monorepo) تضم ثلاثة أجزاء رئيسية:

أهم ما اكتشفته (حقائق مؤكّدة)

المجالالواقع
الخادمFastAPI حيّ على https://tawanow.com/api (يعمل: health 200). وحداته غنية: orders, dispatch, wallets, finance, providers, catalog, complaints, loyalty, promotions, bonus, kyc, legal, notifications, geo, support, settlement, payments, identity…
تسجيل الدخولبكلمة مرور (login_identifier = هاتف أو بريد) أو OTP (device_id + purpose)، مع refresh token و TOTP اختياري. ✅ اختبرته فعلياً وأنشأت حساب عميل ونجح الدخول + قراءة الطلبات + تصفّح 12 مزوّداً.
العملةالوحدة «درهم» (mills)، 1 د.ل = 1000، تُعرض «د.ل» بثلاث خانات.
اللغةعربي RTL أساسي + بنية إنجليزي/فرنسي موجودة في الويب.
الدفعنقداً عند الاستلام (COD) أولاً؛ الدفع الإلكتروني مُقفل حالياً (production_payment_enabled=false).
الشهادة/الشبكةالخادم خلف Cloudflare بشهادة Let's Encrypt (جذر ISRG Root X1). درس اليوم: الأجهزة القديمة جداً قد لا تثق بهذه السلسلة — سنعالجها في تطبيق RN بحزم الجذور.
الخبر الجيد: لن نخمّن الميزات. موقع الويب يحتوي شاشات العميل كاملة (الصفحة الرئيسية، التصنيفات، تفاصيل المزوّد، السلة، الدفع، تتبّع الطلب، السجل، العناوين، المحفظة، الولاء، الدعم…) وطبقة API منظّمة (auth, orders, providers, catalog, addresses, wallets, loyalty, support…). سنستخدمها كعقد جاهز لبناء RN بدقّة.

2) أين سيوضع تطبيق الموبايل الجديد

لأن المشروع monorepo، الأنظف وضع تطبيق RN في مجلد مستقل أعلى المستودع باسم apps/mobile (أو platform/mobile_rn)، منفصلاً عن web/ و mobile_app/ (Flutter)، مع إمكانية مشاركة الأنواع/الثوابت لاحقاً عبر مجلد packages/shared.

APP/
└── platform/
    ├── backend/         (الخادم — موجود)
    ├── web/             (الويب React — موجود، مرجع)
    ├── mobile_app/      (Flutter — موجود، مرجع)
    └── apps/
        └── mobile/      ← تطبيق React Native الجديد (هنا)

السبب: عزل واضح، لا تعارض في الأدوات (Vite للويب، Expo للموبايل)، وسهولة مشاركة الأنواع لاحقاً دون خلط.

5) المعمارية بالرسم — كيف تتدفّق البيانات

القاعدة الذهبية: الشاشة لا تتكلّم مع الـ API مباشرة. الشاشة → hook → service → apiClient → الخادم. وهذا يسمح بتبديل «المحاكاة» بالإنتاج بسطر إعداد واحد.

حالة الواجهة (Zustand)

سلة، جلسة الدخول، اللغة، المدينة المختارة — أشياء «محلية» تخصّ التطبيق.

حالة الخادم (TanStack Query)

المطاعم، الأصناف، الطلبات — تُجلب من الخادم وتُخزّن مؤقتاً تلقائياً.

8) الأمان · الأداء · العمل دون إنترنت · الاختبارات

🔒 الأمان

  • الرموز في SecureStore فقط (لا AsyncStorage).
  • apiClient موحّد: مهلة (timeout) + إعادة محاولة معقولة + معالجة 401/403/500 بوضوح دون كشف تفاصيل تقنية.
  • refresh token (الخادم يدعمه) لتجديد الجلسة بأمان.
  • base URL من إعداد البيئة — لا أسرار داخل الكود.
  • تحقّق Zod لكل مدخلات المستخدم.
  • حزم جذور الشهادات داخل التطبيق (درس اليوم) ليثق بالخادم حتى على الأجهزة القديمة، دون إضعاف الأمان.

⚡ الأداء

  • تحميل كسول (lazy) للشاشات الثقيلة.
  • Pagination للقوائم + caching عبر TanStack Query.
  • تحسين الصور + منع إعادة الرسم غير الضرورية.
  • memoization عند الحاجة فقط (لا مبالغة).
  • تحديثات تفاؤلية فقط حيث تناسب (مثل تعديل السلة).

📴 الإنترنت الضعيف (مهم لليبيا)

  • كاش للقوائم الأساسية + حفظ السلة محلياً.
  • مؤشّر «غير متصل» + إعادة محاولة عند الفشل.
  • عدم فقدان الطلب قبل التأكيد، ورسائل خطأ مفهومة.
  • التطبيق لا ينهار عند انقطاع الشبكة (fail-safe).

🧪 الاختبارات

  • حسابات السلة (مجموع/خصم/توصيل).
  • تحويل حالات الطلب (status mapping).
  • تطبيع أخطاء API (error normalization).
  • تحقّق النماذج + حالة المصادقة.
  • مكوّنات حرجة.

أوامر جاهزة: lint · typecheck · test · format · start · إعداد eas build.

9) طبقة الـ API والمحاكاة (Mock) والتبديل للإنتاج

الخادم حيّ وجاهز، لكن لنطوّر بسرعة وبأمان نبني طبقة محاكاة بنفس شكل الإنتاج تماماً (نفس الأنواع)، ونبدّل بينها وبين الحقيقي بإعداد واحد.

المكوّنالدور
types/أنواع دقيقة لكل request/response (مأخوذة من عقد الخادم/الويب).
services/api/apiClientعميل مركزي: رؤوس، رموز، مهلة، إعادة محاولة/تراجع، تطبيع الأخطاء.
services/api/*.tsservice لكل ميزة (auth, providers, catalog, orders, addresses, wallet…) — مطابقة لوحدات الخادم.
hooks/hooks فوق TanStack Query (تحميل/خطأ/كاش/إعادة محاولة).
mocks/ردود محاكاة بنفس الشكل — للتطوير والاختبار دون انتظار الخادم.

التبديل: API_MODE=mock أو API_MODE=real في إعداد البيئة (app.config) — بلا أي تغيير في الشاشات.

واجهات حقيقية جاهزة سنبني عليها (أمثلة مؤكّدة): POST /auth/login · POST /auth/otp/request|verify · POST /auth/register · GET /providers/search · GET /orders · catalog · addresses · wallets · loyalty · support · GET /version/check.
