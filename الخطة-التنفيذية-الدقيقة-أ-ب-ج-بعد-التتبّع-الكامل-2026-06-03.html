① الخطوة أ — تنقيح عقوبة عدم الحضور: COD فقط

الخطوة أماليّ — قراركالفحص مؤكَّد بالكود

الخلل المؤكَّد (لطلب WALLET/مدفوع مسبقًا)

(1) محاسبة مزدوجة: عند إنشاء طلب WALLET يُحجز goods + delivery_fee في حجز HELD (الرصيد يُخصم فعلًا — يؤكّده أنّ release_reservation يُعيده). ثمّ settle_no_show يخصم الرسم ثانيةً عبر apply_debit + CustomerDebt.
(2) حجز معلَّق أبديّ: settle_no_show لا يلمس الحجز إطلاقًا (لا commit ولا release) → يبقى HELD للأبد، وأموال العميل محبوسة. (الأثر اليوم محدود لأنّ production_payment_enabled=false، لكنّه خطأ صريح يجب إغلاقه قبل الإطلاق.)

التصميم التفصيليّ

تفريع داخل settle_no_show على order.payment_method — دون لمس النقطة أو آلة الحالات:

طريقة الدفعالسلوكالقيود
CASH / COD كما هو تمامًا — رسم D + CustomerDebt(NO_SHOW) + تعويض المزوّد كامل السلع + خصم محفظة إن غطّت لا تغيير — العميل لم يدفع، العقوبة مشروعة
WALLET / مدفوع مسبقًا لا رسم ولا دَين — العميل دفع، حرّ في التخلّي. + تسوية الحجز HELD الموجود (إلزاميّ لإغلاق الحجز المعلَّق) القرار في كيف يُسوّى الحجز (أدناه)

قراراتك الثلاثة (الخطوة أ):
  1. تأكيد المبدأ: WALLET/البطاقة = لا عقوبة (لا رسم، لا دَين).
  2. اختيار نموذج تسوية الحجز المتخلّى: β (مُوصى) أم α أم γ.
  3. إذنٌ بالتعديل (يلمس منطق no_show_service + الحجز؛ بلا migration متوقَّع، FIN-COR يبقى PASS).

② الخطوة ب — سياسة تخلّي السائق (المنظومة تقرّر · المراجعة للبشر)

الخطوة بميزة جديدة — migrationالروافع مؤكَّدة

الفجوة الجوهريّة (مؤكَّدة)

السائق يقبل العرض → الطلب يصبح DRIVER_ASSIGNED → ثمّ لا يتقدّم (لا يذهب للمزوّد). لا توجد أيّ كنّاسة تكشف هذا؛ ولا شيء يُنقِص reliability_score اليوم. هذه الميزة تسدّ الفجوة بأربع طبقات.

التصميم الدقيق (4 طبقات)

الطبقة 1 — الكشف (كنّاسة جديدة بنمط main.py)

  • حلقة _driver_abandonment_sweep_loop كل 60ث، قفل Redis dispatch:abandonment:lock + حارس app_env not in ("test","testing") (مطابق لـmain.py:322-367).
  • المُطلِق (أ) الأثقل: طلب في DRIVER_ASSIGNED منذ أكثر من driver_pickup_window_seconds (config جديد) بلا تقدّم → تخلٍّ مؤكَّد. (لا نُطلِق على DRIVER_AT_PROVIDER — ذاك انتظار مسح المزوّد، ليس ذنب السائق.)
  • (ب) متوسّط: طوارئ REQUEST_REASSIGN بعد القبول (موجودة في DriverEmergency).
  • (ج) خفيف: سياقات أخرى لاحقًا (موسَّع).
  • عند الكشف: تسجيل حدث + إعادة-إدراج الطلب عبر OFFER_EXPIRED_REASSIGN (الهدف الجاهز بلا كاتب) ← يربط التعافي بآلية الإرسال القائمة.

الطبقة 2 — قرار المنظومة (آليّ، متدرّج)

  • نافذة متحرّكة (config) تعدّ أحداث التخلّي لكلّ سائق:
  • 1 حدث → تحذير + خصم reliability_score (قيمة config).
  • متكرّر ضمن النافذة → خصم أكبر + حجب مؤقّت من العروض عبر العمود الجديد Driver.dispatch_blocked_until (يُفحص في create_offer بجانب فحص النقد القائم).
  • تجاوز العتبة القصوى → تعليق ينتظر مراجعة بشريّة (لا حظر دائم آليّ — القرار الصارم للبشر).

الطبقة 3 — المراجعة البشريّة (مرآة OpsDriverEmergencies)

  • صفحة OPS جديدة (نسخة من نمط OpsDriverEmergencies.tsx): سجلّ تخلّي كل سائق + الحالة + القرار الآليّ.
  • إجراءات OPS: إبقاء / إلغاء (تبرئة) / تصعيد القرار الآليّ — كلّه مُدقَّق (audit) عبر البنية القائمة. الإلغاء يُعيد reliability_score ويرفع الحجب.
  • RBAC: require_role(OPERATIONS_AGENT, SUPER_ADMIN) (كنمط الراوترات القائمة).

الطبقة 4 — البُعد الماليّ (اختياريّ — نقطة قرار)

  • الافتراضيّ الموصى به: سمعة/حجب فقط (بلا أيّ لمسٍ للدفتر → بلا مخاطرة ماليّة).
  • الخيار الأقوى: + خصم ماليّ من الأجر عند تخلٍّ مُتحقَّق منه (يلمس الدفتر → يحتاج قرار نموذج قيد لاحقًا، يُؤجَّل للخارطة ج).

ما سيُبنى تقنيًّا

  • جدول جديد driver_abandonment_events (نمط DriverEmergency): id · driver_user_id · order_id · trigger_kind (CHECK) · weight · auto_action (CHECK) · review_status (CHECK) · created_at · resolved_at/by/note.
  • عمود جديد Driver.dispatch_blocked_until: timestamptz NULL — للحجب المؤقّت.
  • migration واحد (بإذنك): الجدول + العمود. سيُتحقَّق على PostgreSQL حقيقيّ (upgrade/downgrade/re-upgrade) كعادة aa05–aa24.
  • خدمة كشف + الكنّاسة في main.py + تطبيق القرار الآليّ (خصم score + ضبط dispatch_blocked_until).
  • حارس الحجب في dispatch_service.create_offer (بجانب حارس النقد القائم).
  • نقاط OPS: سجلّ + مراجعة + تجاوز، وصفحة OpsDriverAbandonment.
  • config: driver_pickup_window_seconds · عتبات النافذة + المدد + قيم الخصم (بقيم افتراضيّة محافظة).
  • اختبارات: كل مُطلِق + كل عتبة + كل تجاوز + استثناء الطوارئ المشروعة.
قراراتك الخمسة (الخطوة ب):
  1. نافذة الاستلام بعد القبول قبل عدّه «تخلٍّ» (مثلًا 15–20 دقيقة؟).
  2. العتبات + المدد: كم حدثًا / كم يومًا → تحذير · حجب مؤقّت (كم مدّته) · تعليق-للمراجعة؟
  3. خصم reliability_score لكل مُطلِق (أوزان مختلفة للأثقل/المتوسّط؟).
  4. البُعد الماليّ: سمعة/حجب فقط الآن، أم + خصم ماليّ (يؤجَّل قيده لـج)؟
  5. استثناء الطوارئ المشروعة (عطل مركبة VEHICLE_FAILURE): تُستثنى من العدّ، أم بوزن صفر حتى مراجعة OPS؟
