① الطلب ومبدأ القرار

الطلب الحرفيّ: «دقّق IDOR/الملكيّة عبر نقاط الموارد بالقرارات الموصى بها».

IDOR (Insecure Direct Object Reference) = أن يصل مستخدمٌ إلى مورد لا يملكه بمجرّد تبديل المُعرِّف في المسار (/orders/123 → /orders/124). الخطر: تسريب بيانات شخصيّة، أو تنفيذ إجراء (إلغاء/تقييم/دفع) على مورد الغير.

مبدأ القرار المُتّبع (تطبيقًا لقاعدة «ألّا نُفسد المشروع» وقواعد منع الهلوسة): تدقيق قراءة-فقط أوّلًا، إصلاح ما هو آمن وواضح فقط، ورفع ما هو واسع الأثر للمالك بدل تطبيقه تلقائيًّا. وحين يكون السطح محصَّنًا أصلًا — لا يُختلَق تغيير صوريّ؛ تُبلَّغ النتيجة النظيفة بالأدلّة.

② المنهجيّة والأدوات

اعتُمد منهج «المسح الآليّ ثمّ القراءة المباشرة» — لأنّ grep/rg في هذا المشروع يُشوّه أسماء الدوال والسلاسل (عيب موثَّق)، لذا استُخدمت سكربتات Python لاستخراج نقاط الوصول وأجسامها بدقّة.

  • الاستخراج: سكربت Python يقرأ كلّ ملفّات *router*.py، يلتقط كلّ @router.<verb>("...{id}...") ويحدّد نطاق جسم كلّ دالّة.
  • التصنيف: regex على رأس الدالّة (الأدوار) وجسمها (رموز الملكيّة) لفرز: مقيَّدة-بدور / محميّة-بالملكيّة / بلا حارس.
  • التحقّق: قراءة مباشرة (Read) للأجسام الحسّاسة، وللخدمات التي تُستدعى (لأنّ فحص الملكيّة كثيرًا ما يكون داخل طبقة الخدمة لا المُوجِّه).
الأسطح المُستهدَفة: العميل/السائق/المزوّد (حيث يمكن انتحال المُعرِّف). نقاط OPS تصل لأيّ مورد بصلاحيّة مشروعة بحكم الدور، فلا يُتوقَّع منها فحص ملكيّة.

③ التمرير ١ — سطح الطلبات + المحادثة (الأعلى خطرًا)

بدأتُ بأخطر سطح: قراءة العميل↔السائق ومحادثتهما (بيانات شخصيّة). قرأتُ القالب الرئيس GET /orders/{order_id} (السطر 563) ثمّ مُحقِّق الخدمة.

أ) GET /{order_id} — يفوِّض الملكيّة للخدمة

# order_router.py:563 if user.role == PlatformRole.DRIVER: safe_view = await service.get_order_for_driver(order_id, driver_user_id=user.user_id) # يرفع OrderForbiddenError ⟹ 403 إن لم يكن مُسنَدًا else: order = await service.get_order(order_id, actor_id=user.user_id, actor_role=user.role.value) # يلتقط OrderForbiddenError ⟹ 403

ب) تأكيد المُحقِّق في الخدمة OrderService.get_order

# order_service.py if actor_role == "CUSTOMER": if order.customer_id != actor_id: raise OrderForbiddenError(...) elif actor_role in ("PROVIDER_ADMIN", "PROVIDER_STAFF"): # يتحقّق ProviderModel.owner_user_id == actor_id AND id == order.provider_id elif actor_role in ("OPERATIONS_AGENT","SUPER_ADMIN","FINANCE_AGENT","ADMIN","SUPERVISOR"): pass else: raise OrderForbiddenError("Insufficient permissions")

إذن: عميل لا يصل إلّا لطلبه، مزوّد لا يصل إلّا لطلب يخصّ متجره، OPS كامل، غير ذلك 403.

ج) المحادثة GET/POST /{id}/messages — أعلى خطر PII

# order_router.py:1361 order = SELECT Order WHERE id == order_id # 404 إن غاب party = await _resolve_chat_party(db, order, user) if party is None: raise HTTPException(403, "Not a participant") # POST يضيف: party in ("customer","driver") + الحالة ضمن CHAT_ACTIVE_STATES

④ التمرير ٢ — المُحقِّق المركزيّ resolve_order_party

تتبّعتُ _resolve_chat_party فوجدتها تفوِّض لمُحقِّق مركزيّ مشترك في app/modules/orders/order_access.py — قرأتُه كاملًا (هو حجر الأساس لكلّ سطح الطلبات):

async def resolve_order_party(db, order, user, *, include_provider=False): if user.role in (OPERATIONS_AGENT, FINANCE_AGENT, SUPER_ADMIN): return "ops" if user.role == CUSTOMER: return "customer" if order.customer_id == user.user_id else None if user.role == DRIVER: drv = SELECT Driver WHERE user_id == user.user_id assigned = SELECT DispatchOffer.id WHERE order_id==order.id AND driver_id==drv.id AND state=="ACCEPTED" return "driver" if assigned else None if include_provider and user.role in (PROVIDER_ADMIN, PROVIDER_STAFF): provider = ProviderService(db).get_provider_for_user(user.user_id) return "provider" if provider.id == order.provider_id else None return None
دقّة مهمّة: السائق يُربَط عبر ملف Driver (بالـuser_id) ثمّ عرض ACCEPTED — وليس بمعرّف المستخدم مباشرةً، لأنّ DispatchOffer.driver_id هو مُعرِّف ملفّ السائق لا المستخدم.

ثمّ قرأتُ أجسام كلّ النقاط الفرعيّة الـ١٣ تحت /{order_id} وأثبتُّ فرض الملكيّة في كلٍّ منها:

⑤ التمرير ٣ — إجراءات السائق (Dispatch)

⑪ القرار والمخرجات

القرار الموصى به: لا اختلاق تغيير — السطح محصَّن بالكامل عبر مُحقِّقات مركزيّة مُختبَرة وفحوص ملكيّة متّسقة. هذا متّسق مع الإصلاحات السابقة المُسجَّلة (SEC-1 IDOR · C-2 ملكيّة العنوان · PROV-01 حارس مالك verify-pickup · D-5 حلّ هويّة السائق · ملكيّة طلب العميل) — تراكمها أنتج سطحًا محكمًا.

ما لم يُفعَل ولماذا

  • لا تغيير كود / لا migration: لا عيب يستوجب إصلاحًا.
  • لا نشر / لا تحقّق حيّ: لا سلوك جديد ليُتحقَّق منه على الإنتاج — التدقيق قراءة-فقط بالكامل.
  • FIN-COR: غير متأثِّر (لم تُمَسّ المالية).
