📄 صفحة الترحيب /welcome مهم
الصفحة موجودة وتعمل. لكن المشكلة: الجذر / يحتاج مصادقة ويعيد توجيه المستخدم غير المسجل — إلى أين؟ ProtectedRoute يعيد توجيه إلى /login. هذا صحيح. لكن المستخدم الجديد تماماً لن يجد /welcome تلقائياً ما لم يُكتب الرابط مباشرة.
لماذا لا يصل المستخدم الجديد لصفحة الترحيب تلقائياً؟
لأن الـ ProtectedRoute يعيد توجيه المستخدم غير المسجل إلى /login مباشرة، لا إلى /welcome. الحل: تغيير وجهة إعادة التوجيه أو إضافة زر "لست مسجلاً" في صفحة الدخول.
📄 صفحة الدخول /login جيدة
تدعم: كلمة مرور، TOTP ثنائية. تحتوي على: نسيت كلمة المرور، إنشاء حساب. ما ينقص: خيار تسجيل دخول بـ OTP (رمز SMS) للعملاء — المنصات العالمية توفر هذا الخيار. العملاء الليبيون قد يفضلون OTP على كلمة المرور.
هل يحتاج العميل كلمة مرور أم يكفي OTP؟
حالياً: مطلوبة كلمة المرور. الباك إند يدعم OTP عبر /auth/otp/verify ويعطي JWT. يمكن إضافة "دخول برمز SMS" كخيار بديل دون تغيير الباك إند.
📄 صفحة التسجيل /register شاملة
4 أدوار (عميل، مزوّد، سائق، موظف). متعددة الخطوات. تحقق من كلمة المرور. إرسال البيانات الخاصة بكل دور. ما ينقص: السائق — حقل المدينة موجود في الحالة (driverCity) لكن الكود يضيف payload.city فقط إذا كان غير فارغ — جيد. مشكلة: لا يطلب رقم الهاتف مسبقاً — الهاتف يُدخل مع بقية البيانات مما يطيل النموذج.
📄 TOTP Setup /ops/security/totp-setup جيدة
3 خطوات: idle → setup → done. تعرض QR URI نصياً (لا تصور QR كصورة — مشكلة!). المستخدم يحتاج نسخ URI ولصقه يدوياً في تطبيق المصادقة بدلاً من مسح QR برمجي.
لماذا لا يُعرض QR كصورة؟
الكود يعرض الـ URI النصي فقط: otpauth://totp/.... يحتاج مكتبة مثل qrcode.react لتوليد صورة QR. هذا يعيق المستخدمين غير التقنيين.

🌐 نقاط API — تحليل دقيق
GET /providers/search مشكلة
  • يُرجع eta_minutes: null دائماً — لم يُنفَّذ حساب ETA
  • يُرجع verification_badge من verification_tier — قد يكون "unverified" للجميع في البداية
  • cursor-based pagination تستخدم ID وليس وقتاً — غير متسقة مع /orders
  • lat/lng مُستقبَلة لكن لا تُستخدم في الترتيب أو حساب المسافة
  • لا تُرجع: صورة، رسوم توصيل، حد أدنى، تقييم — لأنها غير موجودة في النموذج
POST /auth/otp/request جيد
يدعم 5 أغراض (WALLET_ACCESS، PASSWORD_RESET، EMAIL_RECOVERY، PHONE_LOOKUP، PROVIDER_LOGIN). Rate limiting. Audit logging. الباك إند يدعم OTP login للجميع — الفرونت إند لا يعرض هذا الخيار للعملاء.
POST /orders جيد
يطلب Idempotency-Key إلزامياً (16-128 حرف). يتحقق من المخزون. الفرونت إند يرسل order-{providerId}-{Date.now()} — هذا طويل بما يكفي. مشكلة صغيرة: الاسم يحتوي على providerId مما يجعله مرتبطاً — يُفضَّل UUID.
PUT /providers/me ناقص
يقبل: business_name, city, lat, lng فقط. لا يقبل الحقول المفقودة (delivery_fee, min_order, opening_hours, logo_url) لأنها ليست في النموذج. يحتاج migration + schema update + API update.
بوابة OTP للمحفظة (Phase 199) مُنجز
wallet_session_token مطلوب في POST /wallets/topups. الفرونت إند ينفذ تدفق 3 خطوات (هاتف → OTP → شحن). الـ IdempotencyMiddleware يحرس هذا المسار لكن الفرونت إند لا يرسل X-Idempotency-Key — الحماية من التكرار غير مفعّلة لعمليات الشحن.
GET /wallets/me موجود
يُرجع: wallet_number, balance_minor, currency, closed_loop_only, cash_out_allowed. مفقود: سجل المعاملات. لا يوجد GET /wallets/transactions — يمكن استخدام OpsLedgerExplorer للـ ops، لكن العميل لا يملك endpoint لسجل معاملاته.
🔒 الأمان والبنية التحتية
تخزين التوكن ملاحظة
التوكنات مخزنة في localStorage. هذا يُعرّضها لـ XSS. المنصات الحديثة تستخدم httpOnly cookies. لكن للتطبيق المحمول (PWA) هذا مقبول نسبياً. يُنصح بإضافة Content-Security-Policy header.
Session Expiry للـ OPS ممتاز
الـ Layout ينفذ idle timeout بعد 30 دقيقة للمشغّلين. يراقب mouse/keyboard/click. يلوغ آوت تلقائياً. هذا أفضل ممارسة للأنظمة الحساسة.
Rate Limiting موجود
GlobalRateLimitMiddleware + AdminIPAllowlistMiddleware + OTP rate limiting في الخدمة. بنية أمان متعددة الطبقات.
SSE (Server-Sent Events) موجود
اللوحة OPS تستخدم SSE عبر useSSE hook لتلقي تنبيهات المنصة real-time. OpsAlertBanner يعرض التنبيهات. جيد للمشغّلين. العملاء والسائقون يستخدمون polling فقط — يمكن استبداله بـ SSE للتحديثات الفورية.

🔴 فجوة 2: رسوم التوصيل في فاتورة الطلب
نموذج Order لا يحتوي delivery_fee_minor. الفاتورة تعرض total_minor فقط. العميل يرى المبلغ النهائي دون تفصيل (سعر المنتجات + توصيل). هذا يسبب مفاجأة سعرية ويقلل الثقة.
الحل: إضافة حقل للـ schema + migration + API + فرونت إند.
🔴 فجوة 3: سجل معاملات المحفظة
الباك إند يملك LedgerService ولكن لا توجد نقطة API مخصصة للعميل لاسترجاع معاملاته. GET /wallets/transactions غير موجود. الفرونت إند لا يعرض سجل المعاملات في صفحة المحفظة.
الحل: إضافة endpoint في payment_router.py + واجهة في WalletPage.
🟠 فجوة 4: Idempotency-Key في wallet topup
الـ IdempotencyMiddleware يحرس /wallets/topups ويبحث عن رأس X-Idempotency-Key. الفرونت إند لا يرسل هذا الرأس عند الشحن. النتيجة: إذا ضغط المستخدم "شحن" مرتين سريعاً، قد تُنفَّذ المعاملة مرتين رغم وجود الـ middleware.
الحل: إضافة X-Idempotency-Key في paymentsApi.topupWallet().
🟠 فجوة 5: تسوية الكاش للسائقين
الباك إند يملك CashCollection model وخدمات تسوية. الفرونت إند يعرض "الكاش المستحق" في ملف السائق لكن لا يوجد تدفق لطلب التسوية أو تأكيدها.
🟡 فجوة 6: لا يوجد endpoint لملف المستخدم (Customer Profile)
صفحة الملف الشخصي للعميل تعرض فقط بيانات من JWT (role, wallet_number). لا يوجد GET /users/me (غير محمي بـ SUPER_ADMIN) لاسترداد: الاسم الكامل، تاريخ الإنشاء، البريد الإلكتروني.

الخطوة 1: العميل يفتح الرابط للمرة الأولى
ماذا يرى؟
يتم توجيهه مباشرة إلى /login لأن ProtectedRoute يرفضه. لا يصل إلى /welcome تلقائياً. المشكلة: المستخدم لا يعرف أن هناك منصة جديدة — يرى فقط نموذج دخول.
هل هذا صحيح؟
لا. المنصات العالمية (Talabat/Uber Eats) تعرض صفحة Landing مع قائمة المطاعم للزوار غير المسجلين. يسمحون بالتصفح ثم يطلبون التسجيل عند الدفع فقط.
الخطوة 2: العميل يسجّل ويدخل — يصل للصفحة الرئيسية
ماذا يرى في قائمة المطاعم؟
يرى: اسم المطعم + إيموجي النوع (🍔/🛒/💊) + badge مفتوح/مغلق + وقت ETA. لا يرى: صورة، رسوم توصيل، حد أدنى، تقييم. يتساءل: "هل هذا مطعم جيد؟ كم سيكلفني التوصيل؟"
هل يستطيع اتخاذ قرار بالدخول دون هذه المعلومات؟
صعب جداً. التقييمات والأسعار هي أهم عاملين للقرار في التجارة الإلكترونية. غيابهما يجعل الاختيار عشوائياً.
الخطوة 3: يدخل صفحة المطعم
ماذا يرى في رأس الصفحة؟
لا شيء. لا صورة غلاف، لا شعار، لا تقييم ملخص، لا ساعات العمل، لا رسوم التوصيل، لا الحد الأدنى. يقفز مباشرة إلى قائمة الأطعمة. كأنه يتسوق في ظلام.
ماذا يحدث لو أضاف للسلة واكتشف رسوم التوصيل لاحقاً؟
صدمة سعرية عند الدفع. يُلغي. Conversion rate ينهار.
الخطوة 4: ينتقل للدفع
ماذا يرى في صفحة الدفع؟
قائمة العناصر + اختيار العنوان + اختيار طريقة الدفع + "إرسال الطلب". لا يرى: سعر التوصيل، الإجمالي النهائي مع التوصيل، وقت التسليم المتوقع.
هل هذا مقبول؟
لا على الإطلاق. كل منصة عالمية تُظهر: سعر المنتجات + رسوم التوصيل + الضرائب = الإجمالي. غياب هذا يُفقد الثقة ويزيد النزاعات مع العملاء.

يضغط "متاح" ويمنح صلاحية GPS. الـ location يُرسل كل 15 ثانية. يرى قائمة العروض. يضغط قبول — هنا المشكلة: كيف يصل للمطعم؟
هل يرى رابط الخريطة في العرض؟
لا. بطاقة العرض تُظهر: المطعم، المنطقة، العدد. لا يوجد زر "افتح في خرائط Google". السائق يحتاج نسخ العنوان يدوياً وفتح تطبيق خرائط منفصل.
وعند التسليم؟
نفس المشكلة — عنوان التوصيل موجود نصياً لكن لا يوجد رابط خريطة. هذا يبطئ السائق ويزيد الأخطاء.

🎯 الخلاصة التنفيذية

منصة توا متقدمة تقنياً بشكل واضح: الباك إند يملك 133 ملفاً، نظام أمان متعدد الطبقات، TOTP، بوابة OTP للمحفظة، SSE، Idempotency، لوحة عمليات ضخمة تتفوق على كثير من المنصات الإقليمية.

لكن تجربة المستخدم النهائي تعاني من فجوة واحدة جوهرية: البيانات التي يحتاجها العميل لاتخاذ قرار الطلب (صور المطعم، رسوم التوصيل، التقييمات، ساعات العمل) غير موجودة لا في قاعدة البيانات ولا في الـ API ولا في الواجهة. هذا ليس مشكلة UI فحسب — إنها فجوة بنيوية تبدأ من schema قاعدة البيانات.

التوصية العاجلة: ابدأ بـ P1-1 (إضافة حقول المزوّد) لأنه ينفتح عليه كل شيء آخر. بعد الـ migration وتحديث الـ API، ستصبح P1-2 و P1-3 وP2-9 مجرد تحديثات في الفرونت إند.
نقاط القوة المُكتسبة: الـ backend architecture ممتاز. الـ testing framework جاهز. الـ i18n مُعدّ. الـ feature flags تحمي من القرارات المتسرعة. المنصة جاهزة للتوسع بعد إغلاق هذه الفجوات.
