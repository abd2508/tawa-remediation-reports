1) المنهجيّة — مطابقة الكود فعليّاً

لكلّ عيب ظهر على الاستاجينج، فتحتُ ملفّ المصدر في المسار المحلّي وطابقتُ السطور، وراجعتُ حالة git، ثمّ حلّلتُ هل يعتمد العيب على «سياق آمن» (HTTPS/localhost) أم لا — لتحديد أثره على الإنتاج.

  • الاستاجينج بُنِي من نفس المسار المحلّي (بصمة SHA256 مطابقة) → ما ظهر عليه كان موجوداً في المحلّي وقت البناء.
  • الإصلاحان (BUG-1/BUG-2) طُبِّقا على المحلّي ونُشِرا على الاستاجينج فقط، وهما غير مُلتزَمَين في git → لم يصلا الإنتاج.
  • الإنتاج (https://staging.tawanow.com) يعمل عبر HTTPS = سياق آمن (مؤكَّد من CLAUDE.md + إعداد nginx/Let's Encrypt).

3) BUG-1 — crypto.randomUUID في interceptor الطلبات HIGH

المطابقة في المسار المحلّي

16:   return crypto.randomUUID();        // داخل حارس السياق-الآمن (صحيح)
96: config.headers["X-Correlation-Id"] = genUUID();     // كان crypto.randomUUID()
100:  config.headers["Idempotency-Key"] = genUUID();     // كان crypto.randomUUID()
سؤالجواب
كان موجوداً في المحلّي وقت بناء الاستاجينج؟نعم — الاستاجينج بُنِي منه فظهر العيب
موجود في المحلّي الآن؟لا — مُصلَح (genUUID)، لكنّه غير مُلتزَم git
موجود على السيرفر الرئيسيّ؟نعم الكود الأصليّ (لم يُنشَر الإصلاح)
هل يُطلَق على الإنتاج (HTTPS)؟لا — crypto.randomUUID مُعرَّفة في السياق الآمن (HTTPS/localhost)

لماذا لا يُطلَق على الإنتاج؟

السياق الآمن (Secure Context) = HTTPS أو http://localhost ┌─────────────────────────────┬──────────────────────────────┐ │ الإنتاج: https://…tawanow.com │ الاستاجينج: http://192.168.178.194 │ │ crypto.randomUUID = دالة ✔ │ crypto.randomUUID = undefined ✘ │ │ interceptor يعمل → الطلب يُرسَل │ interceptor يرمي → كل طلب يفشل │ └─────────────────────────────┴──────────────────────────────┘

إذن BUG-1 عيب كود حقيقيّ، لكنّه «كامن»: لا يُصيب الإنتاج طالما HTTPS. يُصيب فقط أيّ نشر على HTTP عبر IP/شبكة (مثل الاستاجينج، أو بيئة معاينة داخليّة، أو reverse-proxy بلا TLS).

4) BUG-2 — /operations/document-policies يُعيد 403 للمزوّد/السائق الأخطر للإنتاج

🔴 هذا هو العيب الوحيد الذي سيظهر فعلاً على السيرفر الرئيسيّ — لأنّه لا يعتمد على HTTP/HTTPS إطلاقاً.

        PlatformRole.PROVIDER_ADMIN, PlatformRole.DRIVER,   # الإضافة المُصلِحة

الواجهة (صفحة وثائق المزوّد/السائق المعلّق) تستدعي هذا الـendpoint لتعرف أنواع الوثائق المطلوبة. قبل الإصلاح كان محصوراً بأدوار OPS فقط، فالمزوّد/السائق يحصل على 403 ← يُكسَر نموذج الرفع كلّه.

سؤالجواب
كان موجوداً في المحلّي وقت بناء الاستاجينج؟نعم — ظهر على الاستاجينج
موجود في المحلّي الآن؟لا — مُصلَح (أُضيف PROVIDER_ADMIN+DRIVER)، غير مُلتزَم git
موجود على السيرفر الرئيسيّ؟نعم الكود الأصليّ (403) — لم يُنشَر الإصلاح
هل يُطلَق على الإنتاج؟نعم — فحص الدور مستقلّ تماماً عن HTTP/HTTPS

لماذا لم يُلاحَظ على الإنتاج بعد؟ (مهمّ)

لأنّ المنصّة في وضع تجربة داخليّة فقط (external pilot غير جاهز)، والمزوّدون/السائقون التجريبيّون يُزرَعون مباشرةً في قاعدة البيانات بتجاوز تدفّق رفع KYC من الواجهة. لذلك لم يَمرّ أيّ مزوّد/سائق حقيقيّ بتدفّق رفع الوثائق الكامل على الإنتاج — فظلّ العيب كامناً.

🔑 تجربة الاستاجينج الوكيليّة هي أوّل تشغيل كامل لتدفّق KYC من الصفر عبر الواجهة — ولهذا كشفت عيباً كامناً سيَظهر فور أن يُسجِّل أوّل مزوّد/سائق حقيقيّ على السيرفر الرئيسيّ ويحاول رفع وثائقه.

على السيرفر الرئيسيّ (HTTPS) — مزوّد/سائق حقيقيّ يُسجِّل ويفتح صفحة الوثائق: GET /operations/document-policies (نفس كود الاستاجينج) x الدور = PROVIDER_ADMIN/DRIVER → 403 Forbidden | v «تعذّر تحميل الوثائق: 403» → لا نموذج رفع => المزوّد لا يستطيع رفع KYC → لا يُعتمَد → تسجيل المزوّد/السائق محجوب

الأثر: حاجب صلب لتسجيل المزوّدين والسائقين عبر الواجهة على الإنتاج. الإصلاح بسيط وآمن (توسعة قراءة لبيانات مرجعيّة غير حسّاسة) ويجب نشره على الإنتاج قبل أيّ تشغيل خارجيّ.
