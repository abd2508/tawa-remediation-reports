2) التتبّع الجذريّ المفصّل

البند 1 — التسجيل المكرر خاطئ (لكن ثغرة تطبيع جزئيّة حقيقيّة)

المسار

POST /auth/register  →  register()  registration_router.py:322
  canonical_phone = normalize_phone(body.phone)            :334
  phone_taken = SELECT User WHERE phone == canonical_phone  :≈350 (F-4)
  if phone_taken or email_taken or username_taken: return _conflict()  → 409
  ...
  User.phone  →  mapped_column(String(20), unique=True)  models/user.py:28

الحقيقة

  • الدليل الحيّ: الرقم نفسه بثلاث صيغ (+218910636580 · المحلّية 0910636580 · بمسافات) → كلّها 409. وقيد قاعدة البيانات unique=True يمنع أيّ تكرار حرفيّ مطلقاً (يرفع IntegrityError حتى لو فات الفحص).
  • إذن «حسابات لا محدودة بنفس الرقم» غير ممكن.

الثغرة الجزئيّة الحقيقيّة (سبب لبس المراجِع)

normalize_phone (registration_router.py:86) يوحّد 3 صيغ فقط؛ ما عداها يُعاد «كما هو». تتبّعتُ الحالات:

'+218910636580'   -> '+218910636580'   ✓
'00218910636580'  -> '+218910636580'   ✓
'0910636580'      -> '+218910636580'   ✓  (محلّي 10 خانات)
'+218 91 063...'  -> '+218910636580'   ✓  (المسافات تُزال)
'218910636580'    -> '218910636580'    ✗  بلا + (لا يُطبَّع)
'091063658'       -> '091063658'       ✗  محلّي 9 خانات (≠10)
'+218091063658'   -> '+218091063658'   ✗  +218 ثمّ 0 زائدة

فلو سجّل مستخدم بـ+218910636580 ثمّ آخر بـ218910636580 (بلا +)، يُعاملان كرقمين مختلفين → صفّان. هذا ليس «حسابات لا محدودة بنفس الرقم» (كل صيغة تُرفض إن كُرِّرت حرفيّاً) بل نقص تطبيع يسمح بازدواج عبر صيغ شاذّة. الخطورة LOW — تحسين لا عيب حرج.

الإصلاح المقترح: تقوية normalize_phone ليغطّي: بادئة 218… بلا +، إزالة الصفر الزائد بعد +218 0…، وتطبيع الأرقام لـ9 خانات. تنبيه أثر: الدالة مستخدمة في login + password-reset أيضاً → أي تغيير يجب أن يبقى متوافقاً (الصيغ الصحيحة الحاليّة لا تتغيّر) + اختبار وحدة شامل. لا migration (البيانات الحاليّة بصيغة canonical سليمة).

البند 2 — صفحة 404 مفقودة صحيح (UX)

web/nginx.conf:55
location / {
    try_files $uri $uri/ /index.html;   ← أي مسار غير موجود → index.html (200)
}

هذا سلوك SPA المتعمّد (يسمح بالتوجيه من جانب العميل). الجذر: لا يوجد مسار catch-all في React Router يعرض صفحة «404 غير موجودة» للمسارات غير المعرّفة → المستخدم يرى صفحة فارغة/الرئيسيّة بدل رسالة واضحة.

الإصلاح: إضافة مسار <Route path="*" element={<NotFoundPage/>}/> في router.tsx (+ مثله في opsRouter.tsx) + مكوّن NotFoundPage بسيط (رسالة + زر «العودة للرئيسيّة»). frontend فقط · لا backend · لا nginx (الـSPA fallback يبقى — React يقرّر داخليّاً).

البند 3 — CORS مفقودة صحيح (إعداد إنتاج — الأهمّ)

المسار الجذريّ

main.py:446 CORSMiddleware(allow_origins=settings.allowed_origins, ...)
config.py:38 allowed_origins: List[str] = ["http://localhost:5173"]   ← الافتراضي
# الحيّ على الخادم (.env):
ALLOWED_ORIGINS=["https://staging.tawanow.com"]   ← الدومين المهجور فقط!
APP_ENV=staging
# container introspection: settings.allowed_origins == ['https://staging.tawanow.com']

الحقيقة

  • السبب الجذريّ: .env الإنتاج يسمح بـstaging.tawanow.com فقط (الدومين المهجور)، وtawanow.com غير مدرَج → الـmiddleware لا يُصدِر ترويسات CORS لأصل tawanow.com، وOPTIONS preflight يفشل (400).
  • لماذا لم يظهر العطل للمستخدمين: الويب يُخدَم من نفس الأصل عبر nginx، فطلبات المتصفّح same-origin ولا تحتاج CORS. يظهر فقط لطلبات cross-origin (أدوات، نطاقات أخرى، تطبيقات).
  • قيد حرج اكتُشف بالتتبّع: allowed_origins نوعه List[str] عبر pydantic-settings → يجب أن تكون قيمة .env بصيغة JSON. اختبرتُ: صيغة CSV تُسقط بدء التطبيق بـSettingsError. فالتعديل يجب أن يبقى JSON.
  • حارس validate_production_settings يرفض * في الإنتاج → ممنوع استخدام wildcard؛ يجب سرد الأصول صراحةً.
الإصلاح (إعداد، لا كود): تعديل .env على الخادم: 
ALLOWED_ORIGINS=["https://tawanow.com","https://www.tawanow.com","https://staging.tawanow.com"]
ثمّ إعادة إنشاء backend-core (يقرأ .env عند الإقلاع). JSON إلزاميّ. لا تلمس الكود. تحقّق حيّ: OPTIONS /api/places بأصل tawanow.com → 200 + ACAO.

البند 4 — /api/auth/me → 404 جزئيّ (سوء تسمية)

  GET /customer/me               customer_router.py:22  (401 بلا توكن ✓)

المسار موجود بأسماء مختلفة. ليس عيباً وظيفيّاً. الواجهة الحاليّة تستخدم /customer/me فعليّاً (لا تطلب /auth/me).

الإصلاح (اختياريّ — توافق API): إضافة نقطة alias خفيفة GET /auth/me في auth_router تُرجع هويّة المستخدم الحاليّ (sub/role/role_status من التوكن عبر get_current_user) → 401 بلا توكن. backend فقط · لا migration. أولويّة منخفضة (لا شيء يكسر بدونه).

البندان 5 و 6 — خاطئان

  • #5 (message_ar مفقود): الردّ الحيّ يحوي "message_ar":"تعذّر إنشاء الحساب — راجع بياناتك وحاول مرة أخرى" (وضعتُها في F-4). العربيّة موجودة. لا إصلاح.
  • #6 (HEAD فارغ بدل 405): الحيّ يُرجع 405 فعلاً. الجسم الفارغ في ردّ HEAD هو سلوك HTTP صحيح بالمواصفة (RFC 9110: HEAD لا يحمل جسماً أبداً). لا عيب. لا إصلاح.

R-3 — تقوية normalize_phone

registration_router.py normalize_phone()
+  # 218… بلا + → +218…
+  if phone.startswith("218") and not phone.startswith("+"): phone = "+"+phone
+  # +218 ثمّ 0 زائدة → احذف الصفر
+  if phone.startswith("+2180"): phone = "+218"+phone[5:]
+  # محلّي 9 خانات (بلا صفر بادئ) → +218…

🧠 محاكاة: الصيغ الصحيحة الحاليّة لا تتغيّر مخرجاتها (اختُبرت)؛ الصيغ الشاذّة تُوحَّد. خطر: الدالة تُستخدم في login + password-reset → تطبيع أقوى قد يطابق مستخدماً مسجّلاً بصيغة قديمة (مفيد) لكن يجب ألّا يكسر دخول الصيغ الصحيحة. التخفيف: اختبار وحدة يثبّت 8+ صيغ، وتشغيل حزمة auth كاملة. لا migration (البيانات canonical). قرار المالك: هل نطبّع البيانات القديمة الشاذّة (إن وُجدت)؟ — مؤجّل، يحتاج فحص بيانات.

R-4 — alias /auth/me

auth_router.py
+@router.get("/me")
+async def auth_me(user: UserContext = Depends(get_current_user)):
+    return {"user_id": user.user_id, "role": user.role, "role_status": user.role_status}
# مُركّب على prefix="/auth" → GET /auth/me ؛ 401 بلا توكن عبر get_current_user

🧠 محاكاة: بتوكن صالح → 200 + الهويّة؛ بلا توكن → 401 (لا 404). خطر: تكرار منطق موجود في /customer/me — لكنّ /auth/me عامّ لكل الأدوار (لا customer-only). منخفض.

5) الاختبارات + النشر + المخاطر

الاختبارات

  • R-1: لا اختبار وحدة (إعداد)؛ تحقّق حيّ verify: OPTIONS /api/places بأصل tawanow.com → 200 + ACAO.
  • R-2: Vitest — مسار مجهول يعرض NotFoundPage؛ مسار معرّف لا يتأثّر.
  • R-3: pytest وحدة — 8+ صيغ هاتف تُطبَّع للقيمة الصحيحة؛ + حزمة auth كاملة بلا تراجع.
  • R-4: pytest — /auth/me بتوكن → 200؛ بلا توكن → 401.

النشر التدريجيّ

  1. R-1: تعديل .env + up -d backend-core + تحقّق CORS حيّ. (مستقلّ، فوريّ الأثر.)
  2. R-3+R-4: حزمة backend واحدة → deploy_be.sh + تحقّق.
  3. R-2: deploy_web.sh + fix_proxy.sh إن لزم (000/502) + تحقّق صفحة 404.

المخاطر

  • R-1 الأخطر تشغيليّاً: خطأ JSON في .env يُسقط backend. خفّفه بالتحقّق المحليّ + health check + إبقاء staging.
  • FIN-COR غير متأثّر (لا مساس بـfeature_flags/launch_gates). لا migration لأيّ بند. لا commit.
  • المناطق المحظورة: R-3/R-4 في backend/app/modules → إذن تجاوز كالعادة. R-1 إعداد خادم (خارج الريبو). R-2 frontend (مسموح).

نهاية الخطة — كل بند تُتُبِّع إلى جذره في الكود (أرقام أسطر فعليّة) واختُبر السلوك حيّاً على tawanow.com. 3 إصلاحات حقيقيّة (R-1 CORS · R-2 صفحة 404 · R-3/R-4 backend) + بندان خاطئان (5/6) + البند 1 تحسين تطبيع لا عيب حرج. تنتظر إذنك للتنفيذ.
