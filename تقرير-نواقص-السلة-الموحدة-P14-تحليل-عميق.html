🔍 المشكلة بلغة بسيطة

G-CRIT-2 أكواد الأخطاء الحرجة لم تُعالَج في الدفع الموحّد حرج
🔍 المشكلة بلغة بسيطة

عندما ترفض الخلفية الطلب لسبب قابل للحل (مثل: احتاج رمز OTP، أو يجب قبول الشروط، أو لديه دين مستحق)، صفحة الدفع الجماعي تعرض رسالة خطأ خام باللغة الإنجليزية بدون أي زر للتصرف.

G-CRIT-3 لا يوجد دعم للمحفظة في الدفع الموحّد — نقداً فقط حرج
🔍 المشكلة بلغة بسيطة

الزبون الذي يملك رصيداً في المحفظة ويريد الدفع منها لن يستطيع استخدام الدفع الجماعي. رغم أن الخلفية تدعم WALLET للمجموعات، الواجهة تُجبر الكل على النقد.

⚡ السيناريو المتأثر

زبون رصيد محفظته 200 دينار، إجمالي السلة 80 دينار ← يُجبَر على الدفع نقداً بينما لديه رصيد كافٍ.

إضافة [paymentMethod, setPaymentMethod] state، جلب الرصيد مثل CheckoutPage (paymentsApi.getWallet())، عرض خيار CASH/WALLET مثل CheckoutPage، تمرير المتغير بدلاً من "CASH" الثابت.

G-CRIT-4 لا توجد صفحة تتبّع المجموعة — group_id يختفي حرج
🔍 المشكلة بلغة بسيطة

بعد الدفع، الزبون يرى قائمة الطلبات المنفصلة في سجل الطلبات — لا يعرف أن "طلب متجر A" و"طلب متجر B" كانا من نفس سلة الدفع الواحدة. وإذا أراد تتبّعهم معاً لا يستطيع.

إنشاء صفحة /group/:groupId تستدعي cartsApi.getGroup() وتعرض بطاقات المتاجر مع حالة كل منها. في سجل الطلبات، الطلبات التي لها group_id يمكن تجميعها بصرياً.

G-CRIT-5 لا واجهة لإلغاء متجر أو صنف من السلة بعد الدفع حرج
🔍 المشكلة بلغة بسيطة

الزبون دفع لثلاثة متاجر، ثم أراد إلغاء واحد منهم فقط (مثلاً المتجر أعلمه بانقطاع الكهرباء). الخلفية تدعم هذا تماماً — لكن الواجهة لا تُظهر أي زر "إلغاء المتجر" أو "حذف صنف".

📡 الـ API الجاهزة تماماً
POST /carts/orders/{order_id}/cancel → يلغي متجراً بأكمله ويُعيد رصيد المحفظة كاملاً ← { order_id, order_state: "CANCELLED" } POST /carts/orders/{order_id}/items/{item_id}/cancel → يلغي صنفاً واحداً ويُعيد قيمته فقط من المحفظة ← { order_id, order_state, total_minor } // carts.ts ← كلاهما مفقود من عميل الـ API
⚡ سيناريوهات بدون هذه الميزة
متجر يُبلّغ بانقطاع → لا زر إلغاء → الزبون يتصل بالدعم
إضافة صنف بالخطأ → لا حذف صنف → يدفع مبلغاً خاطئاً
✅ الحل المقترح

إضافة cancelSubOrder و cancelItem لـ carts.ts، ثم عرض زر "إلغاء هذا المتجر" في صفحة تتبع المجموعة (G-CRIT-4) وزر "حذف صنف" في OrderTrackingPage عندما الطلب ينتمي لمجموعة وفي حالة AWAITING_PROVIDER_ACCEPTANCE.

G-CRIT-6 أسماء المتاجر لا تُحمَّل — يظهر "متجر 1" و"متجر 2" فقط حرج

صفحة الدفع الموحّد تُظهر "متجر 1" و"متجر 2" بدلاً من "مطبخ أبو علي" و"البقالة الأخضر". الزبون لا يعرف أي سلة تتبع أي متجر.

زبون لديه 3 سلال: مطعم + صيدلية + بقالة. الصفحة تُظهر "متجر 1، متجر 2، متجر 3" — لا يعرف أيّها أيّها.

🟠 النواقص المهمة (تجربة رديئة)

G-SIG-1 واجهة اختيار العنوان متراجعة — select بسيط بدلاً من AddressSelector مهم
🔍 المشكلة

CartGroupCheckoutPage تستخدم <select> عادياً. CheckoutPage تستخدم <AddressSelector requireCoords /> التي تدعم إضافة عنوان جديد inline. إذا لم يكن للزبون عناوين محفوظة، في الدفع الجماعي يرى فقط "لا توجد عناوين — إضافة عنوان" بزر ينقله بعيداً عن الصفحة وقد يخسر الجلسة.

✅ الحل

استبدال <select> بـ <AddressSelector ... onCreated={...} requireCoords /> مع تحديث addresses state عند إضافة عنوان جديد.

G-SIG-2 لا يُتحقّق من الحدّ الأدنى للطلب لكل متجر قبل الإرسال مهم
🔍 المشكلة

إذا متجر A يشترط 20 دينار حدٍّ أدنى والسلة فيها 12 دينار فقط، الزبون يضغط "تأكيد" ويرسل للخلفية → الخلفية ترفض 422 → رسالة خطأ تقنية. CheckoutPage تعرض التحذير مسبقاً وتُعطّل الزر.

✅ الحل

في useEffect عند تحميل provider names (G-CRIT-6)، أحضر minimum_order_minor أيضاً. إذا أي سلة أقل من الحد → اعرض تحذيراً أصفر في بطاقة المتجر وعطّل زر التأكيد.

G-SIG-3 لا توجد ملاحظات توصيل لكل متجر مهم
🔍 المشكلة

الزبون يريد قول "اطرق الباب" لسائق متجر A، و"اتصل قبل الوصول" لسائق متجر B. الدفع الجماعي لا يتيح ذلك. CheckoutPage تتيح ملاحظات + 7 زرّ سريع (chips).

الخلفية تدعم delivery_notes_for_driver لكل sub_order في OrderCreateRequest، والـ SubOrderRequest في carts.ts يحتوي الحقل — لكن الواجهة لا تسأل عنه.

✅ الحل

إضافة Record<string, string> state للملاحظات، عرض حقل textarea صغير بجانب كل بطاقة متجر مع أزرار (chips)، تمريره عند البناء في sub_orders.

G-SIG-4 واجهة TypeScript SubOrderRequest ناقصة حقول مهمة مهم
🔍 المشكلة

الـ interface في carts.ts لا تعكس كل الحقول التي تقبلها الخلفية في OrderCreateRequest. المطوّر القادم قد يحتاج هذه الحقول ولن يجدها في TypeScript.

الحقلفي OrderCreateRequest (خلفية)في SubOrderRequest (TS)

otp_action_token✅❌ مفقود

✅ الحل

تحديث SubOrderRequest interface في carts.ts لتطابق OrderCreateRequest الخلفية بالكامل. كل الحقول الجديدة اجعلها optional (?).

G-SIG-5 سجل الطلبات لا يعرف مفهوم المجموعة مهم
🔍 المشكلة

الزبون الذي دفع لثلاثة متاجر معاً يرى في سجل الطلبات ثلاثة طلبات منفصلة — لا يعرف أنها كانت من دفعة واحدة. كل طلب له group_id في الخلفية لكن OrderHistoryPage لا تقرأه ولا تعرضه.

✅ الحل

في OrderHistoryPage: عند تحميل الطلبات، جمّع الطلبات التي لها نفس group_id تحت عنوان "سلة موحّدة". أضف group_id? إلى واجهة TypeScript للطلب وتأكد من أن API يُعيده.

G-SIG-6 لا يوجد فحص لتعليق المنطقة مهم
🔍 المشكلة

CheckoutPage يستخدم <ZoneSuspendedBanner lat lng /> ليُحذّر الزبون إذا منطقته معلّقة قبل الدفع. CartGroupCheckoutPage لا يفعل ذلك.

✅ الحل

إضافة ZoneSuspendedBanner في CartGroupCheckoutPage مثل CheckoutPage بالضبط.

G-SIG-7 مفتاح Idempotency في CheckoutPage يستخدم Date.now() — غير آمن مهم
🔍 المشكلة

CheckoutPage (الدفع الفردي) السطر 611 يُولّد المفتاح هكذا:

const key = `order-${providerId}-${Date.now()}`; // إذا ضغط الزبون الزر مرتين سريعاً → مفتاحان مختلفان → طلبان مزدوجان!

CartGroupCheckoutPage يفعل الصواب:

const idemKeyRef = useRef<string>(genUUID()); // مُولَّد مرة عند mount، يتغير فقط بعد خطأ
✅ الحل

في CheckoutPage: استبدال Date.now() بنمط useRef(genUUID()) المستخدَم في CartGroupCheckoutPage، مع إعادة التوليد فقط عند الخطأ.

🟡 النواقص الثانوية (مستوى تشطيب)

G-MIN-1 مفتاح localStorage لا يزال "toowa_cart" (الاسم القديم) ثانوي

CartContext.tsx السطر 22: const CART_STORAGE_KEY = "toowa_cart" — "toowa" هجاء قديم للعلامة التجارية. المستخدمون الذين أنشأوا حسابات باسم "tawa" سيجدون السلة فارغة. لا يُسبب خطأً لكنه غير متناسق.

G-MIN-2 لا دعم لـ SELF_PICKUP في الدفع الجماعي ثانوي

recipient_mode مُضمَّن كـ "delivery_to_address" دائماً. إذا الزبون يريد استلام ذاتي من جميع المتاجر، لا يستطيع استخدام الدفع الجماعي. نادر الحدوث لكن ناقص من المنطق.

G-MIN-3 لا دعم للجدولة (schedule_for) في الدفع الجماعي ثانوي

CheckoutPage يدعم "جدولة لوقت لاحق" (Wave 5). CartGroupCheckoutPage لا يمرر scheduled_for للخلفية.

G-MIN-4 لا كود خصم (promo_code) لكل متجر في الدفع الجماعي ثانوي

CheckoutPage له حقل كود الخصم. CartGroupCheckoutPage لا يتيح الكودات. الخلفية تدعمه لكل sub_order.

G-MIN-5 لا إكرامية (tip) لكل سائق في الدفع الجماعي ثانوي

CheckoutPage يتيح إكرامية للسائق (B1). CartGroupCheckoutPage لا يُرسل tip_minor. سيُحرم سائقو الدفع الجماعي من الإكراميات دائماً.

G-MIN-6 لا تفويض مستلم (delegate recipient) لكل متجر ثانوي

CheckoutPage يتيح "المستلم شخص آخر؟" مع اسم وهاتف. CartGroupCheckoutPage لا يدعمه. السيناريو: الزبون يرسل هدايا من متاجر متعددة لشخص واحد.
