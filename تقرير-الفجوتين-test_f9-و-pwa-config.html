ما يفعله الاختبار

الاختبار يتحقق من أن حساب التسوية اليومية للسائق يستثني البقشيش من المبلغ المُسلَّم. منطقياً صحيح: السائق يحتفظ بالبقشيش، فلا يجب أن يسلّمه للمشغّل.

مشكلة الاختصار (FK Shortcut): الاختبار يُنشئ سجل CashCollection بـorder_id = uuid.uuid4() عشوائي — لا طلب حقيقي في جدول orders يقابله. هذا اختصار لتفادي بناء سجل طلب كامل، لكنه انتهاك لقيد FK الصريح في النموذج.

114 order_id=str(uuid.uuid4()), # ← طلب وهمي! لا وجود له في orders
115 driver_id=str(d.id),
116 amount_minor=10000, tip_minor=1000, ...))
117await db_session.commit() # ← PostgreSQL: FK ERROR هنا

نفس الكود — سلوكان مختلفان حسب قاعدة البيانات

السبب العميق لـ SQLite السلوك

في الـ conftest، يُطبَّق PRAGMA foreign_keys=ON داخل async with test_engine.begin() as conn — وهو connection منفصل عن الـ db_session fixture. مع StaticPool، تُعيد SQLAlchemy نفس الـ connection تقنياً، لكن aiosqlite يُشغّل كل عملية عبر thread worker خاص، وقد لا يحتفظ الـ PRAGMA بحالته عبر الـ event loop boundaries بنفس الطريقة. النتيجة: FK قد تكون غير مُطبَّقة فعلياً في وقت الـ commit.

السبب الأول للإخفاق الدوري (قبل Wave-T T1)

المشكلة الجذرية القديمة: قاعدة البيانات في الاختبارات هي SQLite in-memory واحدة مشتركة بين جميع الاختبارات (StaticPool). أي اختبار يستدعي .commit() يترك بيانات في قاعدة البيانات تنتقل للاختبارات التالية. هذا جعل النتائج تعتمد على ترتيب تشغيل الاختبارات.
  • المشكلة المُكتشَفة
    اختبارات soft-launch تُحصي نسب أدوار/طلبات — إذا أبقى اختبار سابق بيانات في DB، تتغير النسب وتفشل الاختبارات. test_f9 كان ينجح منفرداً ويفشل في المجموعة لأن اختباراً سابقاً أضاف بيانات تُغيّر نتيجة استعلام التسوية.
  • الإصلاح المطبَّق — Wave-T T1 (_isolate_db)
    أُضيف fixture جديد _isolate_db يعمل قبل كل اختبار: يمسح جميع الجداول (بالترتيب العكسي لحل تبعيات FK)، ثم يُمكّن اختبار كل حالة من نقطة صفر نظيفة.
  • الحالة الآن
    المجموعة الكاملة تعمل: 3104 نجاح. لكن الهشاشة الهيكلية لا تزال موجودة — الاختبار يعتمد على SQLite وسيفشل عند تشغيله ضد PostgreSQL.
# conftest.py — Wave-T T1: الحل المطبَّق
 
@pytest_asyncio.fixture(autouse=True)
async def _isolate_db(create_tables):
# مسح كل الجداول قبل كل اختبار
async with test_engine.begin() as conn:
if IS_SQLITE:
await conn.exec_driver_sql("PRAGMA foreign_keys=OFF")
for table in reversed(Base.metadata.sorted_tables):
await conn.execute(table.delete())
if IS_SQLITE:
await conn.exec_driver_sql("PRAGMA foreign_keys=ON")
yield # ← الاختبار يعمل هنا

الهشاشة المتبقية

الاختبار ناجح في SQLite لكنه غير موثوق في PostgreSQL: إذا أُعِيد تشغيل الاختبارات بـTEST_DATABASE_URL=postgresql+asyncpg://... (كما تُوصي الـ conftest للتحقق من pg_trgm وغيرها)، سيفشل test_f9 فوراً عند await db_session.commit() بسبب FK violation.

ما هو سلوك كل إعداد؟

الإعدادالقيمةالمعنى
registerType: "prompt" prompt التطبيق يتحكم متى يُسجَّل الـ SW (لا تسجيل تلقائي) — الـ PwaReloadPrompt يتولى هذا
skipWaiting: true true (حالي) عند اكتشاف SW جديد: ينشّط فوراً دون انتظار إغلاق جميع التبويبات
skipWaiting: false false (قديم) SW جديد ينتظر في الـ "waiting" حتى تُغلق جميع التبويبات — يحتاج مستخدماً يغلق المتصفح
clientsClaim: true true SW الجديد يتولى جميع التبويبات المفتوحة فوراً بعد التنشيط
الفهم الكامل: registerType: "prompt" + skipWaiting: true + PwaReloadPrompt (auto-update) تُشكّل تصميماً متسقاً: التطبيق يكتشف SW جديداً ← يُنبَّه تلقائياً ← يُعيد التحميل فوراً. لا حاجة لتدخل المستخدم. هذا النمط أحدث من P-2 وأكثر عملية للنشرات المتكررة.

القاعدة الحديثة: اختبار التكوين يجب أن يوثّق القرار المطبَّق حالياً مع شرح للسبب — لا القرار الذي كان صحيحاً في السابق. تحديث الاختبار ليعكس السلوك المقصود هو الإصلاح الصحيح — ليس حذف الاختبار.

اختبار إضافي موصى به — تحقق من PwaReloadPrompt

الأسلوب الحديث في اختبار التكوين: ليس فقط التحقق من قيم الإعدادات، بل التحقق من اتساق السلوك بين الإعدادات والمكوّنات. أُضف هذا الاختبار لتوثيق أن الـ auto-update pattern مكتمل:

const pwaPrompt = fs.readFileSync(

المبادئ العامة المستخلصة

مبدأ 1 — اختبارات التكامل يجب أن تصمد في PostgreSQL: لا اختصارات FK. أي اختبار يُنشئ سجلاً بـForeignKey يجب أن يبني البيانات المرتبطة فعلياً. SQLite يُخفي هذه المشاكل — PostgreSQL يكشفها.
مبدأ 2 — اختبارات التكوين توثّق السلوك الحالي المقصود: عندما يتغير قرار التصميم (P-2 → auto-update)، يجب تحديث الاختبار فوراً كجزء من نفس الـ commit. اختبار يفشل لأن التطبيق تطور هو فشل في الانضباط، ليس فشلاً في الكود.
مبدأ 3 — الفشل الدوري خطير أكثر من الفشل الثابت: الفشل الثابت واضح ويُصلَح. الفشل الدوري يبني ثقة زائفة ويُخفي أخطاء حقيقية. _isolate_db حلّ الجزء الأكبر، لكن البنية الهشة تبقى وتنتظر بيئة CI حقيقية.
