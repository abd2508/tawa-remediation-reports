WP1 — مُعرّفات آمنة في كل سياق + ترقية UUIDv7 أولويّة: متوسّطة→عالية للمسار المالي

🟦 شرح بسيط: التطبيق يصنع «أرقاماً عشوائيّة فريدة» (UUID) لتمييز كل طلب ومنع تكراره. الطريقة المستخدَمة (crypto.randomUUID) تعمل فقط على HTTPS أو localhost؛ على أيّ رابط HTTP عبر IP تختفي وتُعطّل الميزة. الحلّ: دالّة واحدة موحّدة تعمل في كل مكان، وترقية نوع الرقم إلى الجيل السابع (UUIDv7) الذي يجعل قواعد البيانات أسرع.
🟨 لماذا: crypto.randomUUID() واجهة «سياق آمن فقط». على HTTP-LAN تكون undefined → تكسر الميزة (كما حدث في الاستاجينج). وcrypto.getRandomValues() ليست مقيّدة بالسياق الآمن → هي البديل الصحيح. UUIDv7 (RFC 9562، مايو 2024) مرتّب زمنيّاً → إدراج متسلسل في فهرس B-tree: فهرس أصغر ~27% وORDER BY أسرع ~3× وإدراج أسرع ~49% مقارنةً بـv4 العشوائيّ.

🟪 محاكاة أثناء البناء (أخطاء متوقّعة):
  • فخّ replace-all: عند استبدال crypto.randomUUID() آليّاً، لا تستبدل النداء داخل دالّة genUUID نفسها (فرع السياق الآمن) — وإلّا تكرار لانهائيّ. (وقع فعليّاً أثناء إصلاح الاستاجينج وصُحِّح.)
  • تسريب الوقت: لا تُرقّ الرموز العامّة (إعادة تعيين كلمة المرور، رموز OTP-action) إلى v7 — تبقى v4.
  • المنوتونيّة لكل عمليّة: v7 ليست تسلسلاً عالميّاً؛ صالحة كمفاتيح فريدة فقط (لا تعتمد عليها للترتيب الصارم عبر عمّال متعدّدين).
  • التوافق client↔server: اجعل مولّد الواجهة والخادم بايت-متوافقَين (مكتبة edwh-uuid7 متوافقة مع pg_uuidv7 وPG18 وPython 3.14).

WP2 — RBAC للبيانات المرجعيّة + حارس آليّ يمنع تكرار BUG-2 أولويّة: عالية (نشر) + متوسّطة (تعميم)

🟦 شرح بسيط: صفحة رفع وثائق المزوّد/السائق كانت تسأل الخادم «ما الوثائق المطلوبة؟» عبر رابط مخصّص للإدارة فقط، فيُرفَض (403) ويُكسَر النموذج. القاعدة الصحيحة: «قراءة معلومة مرجعيّة غير سرّيّة» متاحة لأيّ مستخدم مُسجَّل، بينما «تعديل تلك المعلومة» للإدارة فقط. ونضيف فحصاً آليّاً يمنع تكرار هذا الخطأ مستقبلاً.
🟨 لماذا: الخلط بين «قراءة إعداد مرجعيّ» و«إدارة» هو جذر BUG-2. النمط الحديث: تقسيم المورد حسب حساسيّة العمليّة لا حسب بادئة الرابط. قائمة أنواع الوثائق «عقد» لا «سرّ». (المشروع نفسه له سوابق صحيحة: المرحلة 399 المزوّد يقرأ الشكاوى ضدّه؛ المرحلة 403 /providers/me يكشف حقول المالك دون تسريب في البحث العامّ.)

  • OPS تحتاج الكتابة (POST/PATCH) → لا تُوسّع الكتابة، القراءة فقط.
  • اختبار الانحدار: شغّل تدفّق KYC من الصفر لكل دور (مزوّد/سائق) — هو ما كشف BUG-2 أصلاً.

WP3 — خطّ أنابيب رفع KYC الحديث: presigned + مسح فيروسات + تجريد EXIF أولويّة: عالية (أمان/خصوصيّة) منطقة محظورة

🟦 شرح بسيط: اليوم تمرّ صورة الوثيقة عبر خادم التطبيق ثم تُخزَّن. الأفضل: (1) المتصفّح يرفع مباشرةً إلى المخزن (MinIO) برابط موقّع مؤقّت — أسرع وأأمن. (2) تُفحَص بمضادّ فيروسات قبل أن يراها أحد. (3) تُجرَّد بيانات الصورة الخفيّة (مثل موقع GPS داخل صورة الهويّة) حمايةً للخصوصيّة. (4) المُراجِع يراها برابط موقّع قصير العمر.
🟨 لماذا: الرفع الحاليّ قويّ التحقّق (MIME + magic-byte + سقف 5MiB + MIME معياريّ لا من العميل — file_router.py) لكنّه server-proxied (يُحمّل خادم التطبيق) وبلا مسح فيروسات ولا تجريد EXIF. صور الهويّة قد تحمل إحداثيّات GPS → تسريب خصوصيّة حقيقيّ (يكمل عمل المرحلة 392 على Permissions-Policy للكاميرا/الموقع).

        |  حدث MinIO --> Redis/worker
        v

🟪 محاكاة أثناء البناء:
  • يتم -presign- ثمّ ينجح PUT لكن «تسجيل المستند» يفشل → كائن يتيم في MinIO. الحلّ: تسجيل أوّلاً بحالة pending ثم presign، ومهمّة تسوية تحذف اليتامى.
  • تجاوز سقف الحجم في presigned-PUT: PUT لا يفرض الحجم بإحكام → استخدم presigned-POST policy مع content-length-range عند الحاجة للسقف الصارم.
  • الإعادة (idempotency): احمل Idempotency-Key + dedupe على content_sha256 حتى لا تتكرّر صفوف المستند أو يُعاد المسح.
  • بوّابة الاعتماد: اربط «قابل للمراجعة/الاعتماد» بـ scan_status=clean — لا يُعتمَد مستند لم يُمسَح.
  • الـEXIF: أعد الترميز فعليّاً (لا مجرّد حذف الوسم) وإلّا تبقى البيانات.

اختياريّ لاحقاً (استراتيجيّ): تحقّق آليّ OCR/MRZ/liveness كخطوة بعد المسح تُغذّي درجة ثقة لطابور مراجعة OPS — تُكمل المراجعة البشريّة ولا تستبدلها.

WP4 — تيليمتري الأخطاء وكشف «الفشل الصامت» أولويّة: عالية

🟦 شرح بسيط: عندما انكسر كل شيء في الاستاجينج، ظهرت رسالة عامّة «حدث خطأ غير متوقع» بلا أيّ أثر — فاختفى العيب الحقيقيّ. السبب أنّ axios يبتلع الأخطاء المرميّة داخل الـinterceptor بصمت. الحلّ: تصنيف الخطأ بدقّة (خادم / شبكة / إعداد) + جعل أخطاء الـinterceptor مرئيّة + إرسال تقرير خطأ منظّم لقاعدة بياناتنا.
🟨 لماذا: سلوك axios موثّق (issue #2640): رمي داخل interceptor الطلب يرفض السلسلة بلا console وبلا طلب شبكة. ومُطبِّعنا الحاليّ يجمع كل ذلك في UNKNOWN_ERROR. هذا هو ما أخفى العيب طويلاً (يكمل المرحلة 398 WP-7 «أوقف الكتم المضلّل»).

// تصنيف صريح لوضع الفشل (لا تجمعها في «خطأ شبكة»)
function normalizeAxiosError(e) {
  if (axios.isAxiosError(e)) {
    if (e.response) return { kind:"http",    status:e.response.status, body:e.response.data };
    if (e.request)  return { kind:"network", code:e.code };   // ERR_NETWORK / timeout
    return            { kind:"config",  message:e.message };   // خطأ interceptor/بناء — يجب ألّا يُعرَض كشبكة
  }
  return { kind:"unknown", error:String(e) };
}
// الإرسال: navigator.sendBeacon على window.onerror + unhandledrejection (يصمد عند إغلاق الصفحة)
🟪 محاكاة أثناء البناء:
  • PII في الأخطاء: أجسام الأخطاء قد تحوي هاتف/إيميل/توكن → نقِّها قبل التخزين، وحدّ المعدّل لتفادي إغراق السجلّ.
  • CSP: connect-src 'self' الحاليّ يسمح بـ /telemetry (نفس الأصل)؛ لو استُخدِم Sentry SaaS يجب توسيع CSP + استضافة الـSDK ذاتيّاً (script-src 'self').
  • حلقة لا نهائيّة: لا تُبلِّغ عن خطأ من داخل مُبلِّغ الأخطاء نفسه (احرسه بعلم).
  • OpenTelemetry وحده لا يلتقط الأخطاء (هو traces/metrics)؛ تحتاج SDK التقاط أخطاء أو endpoint الابتلاع الذاتيّ.

WP5 — حلّ nginx الديناميكيّ: لا 502 بعد إعادة بناء الحاوية أولويّة: متوسّطة

🟦 شرح بسيط: عند إعادة بناء حاوية الخلفية تأخذ عنواناً جديداً، لكن nginx يتذكّر العنوان القديم فيُرجِع 502 لثوانٍ حتى نُعيد تشغيله (حدث في الاستاجينج). الحلّ: نجعل nginx يسأل عن العنوان الجديد لحظيّاً عبر خادم أسماء Docker.
🟨 لماذا: nginx يحلّ اسم الـupstream مرّة واحدة عند الإقلاع ويُخزّن الـIP. وضعه في متغيّر + resolver يجبره على إعادة الحلّ وقت الطلب، ويُصلِح أيضاً سباق ترتيب الإقلاع.
🟩 أين بالكود (مطابَق): web/nginx.conf:60 (و:47 لـ SSE) — حاليّاً proxy_pass http://backend-core:8000/; ثابت. (داخل nginx.conf فقط — لا يلمس docker-compose.yml المحظور.)
server {
  resolver 127.0.0.11 valid=10s ipv6=off;     # خادم أسماء Docker المدمج
  location /api/ {
    set $upstream http://backend-core:8000;     # المتغيّر يفرض إعادة الحلّ وقت الطلب
    proxy_pass $upstream$request_uri;            # أعِد المسار يدويّاً مع المتغيّر
    # أبقِ proxy_set_header كما هي
  }
}
🟪 محاكاة أثناء البناء:
  • فقدان المسار: proxy_pass $upstream; بلا مسار يحذف /api/ rewrite → أضِف $request_uri صراحةً (خطأ شائع جدّاً).
  • SSE: طبّق نفس النمط على location /api/sse/ (سطر 47) وإلّا يبقى عرضة للـ502.
  • شكل المتغيّر يتجاوز كتلة upstream{} → تفقد keepalive/LB؛ لخدمة بنسخة واحدة هذا هو الصحيح تماماً.

WP6 — HTTPS في كل بيئة: الدواء الجذريّ لفئة «يعمل على الإنتاج ويكسر على HTTP» أولويّة: عالية

🟦 شرح بسيط: الكاميرا، تحديد الموقع، مفتاح المرور (WebAuthn)، عامل الخدمة، وcrypto.randomUUID — كلّها تعمل فقط على HTTPS. لو جعلنا كل بيئة (تطوير/معاينة/استاجينج) تعمل على HTTPS، تختفي عائلة كاملة من الأخطاء دفعةً واحدة (BUG-1 ما كان ليظهر أصلاً).
🟨 لماذا: العلاج الجذريّ ليس fallback لكل واجهة، بل HTTPS في كل مكان يلمسه متصفّح. WP1 (البديل) هو التخفيف؛ WP6 هو الدواء.
🟩 أين بالكود (مطابَق): الإنتاج HTTPS بالفعل (https://staging.tawanow.com). الناقص: HTTPS لبيئات المعاينة/الاستاجينج المحلّي + HSTS الحاليّ ضعيف: nginx.conf:37 = max-age=86400 (يوم واحد فقط).

WP7 — متانة الواجهة وترطيب الحالة من الخادم أولويّة: منخفضة→متوسّطة

🟦 شرح بسيط: عند إعادة تحميل صفحة التسليم وسط العمل، عادت مطالبة «سجّل الكاش» رغم تسجيله — لأنّ الواجهة لا تقرأ الحالة من الخادم عند التحميل (تعتمد علماً محلّيّاً يُصفَّر). الحلّ: عند التحميل، اسأل الخادم «هل سُجِّل الكاش؟ هل أُثبِت التسليم؟» واضبط الأعلام تبعاً لذلك.
🟩 أين بالكود (مطابَق): DriverDelivery.tsx:75 cashDone=useState(false) ولا يُرطَّب من حالة الطلب؛ يوجد علاج ذاتيّ جزئيّ عند إعادة الضغط (سطر 300-304، 409 → cashDone=true) لكنّه يتطلّب تفاعلاً. useEffect (104/138) لا يجلب حالة التحصيل.
🟨 لماذا: «الحالة مشتقّة من الخادم» مبدأ متانة: الواجهة لا تملك الحقيقة، الخادم يملكها. هذا يحصّن ضدّ إعادة التحميل/تبديل الجهاز/استئناف التطبيق.
🟪 محاكاة أثناء البناء: اجلب حالة التحصيل/الإثبات ضمن استعلام الطلب الموجود (لا طلب إضافيّ)؛ احذر التعارض مع العلاج الذاتيّ 409 (اجعل المصدر الوحيد هو حالة الخادم).

معايير القبول (لكل حزمة)
