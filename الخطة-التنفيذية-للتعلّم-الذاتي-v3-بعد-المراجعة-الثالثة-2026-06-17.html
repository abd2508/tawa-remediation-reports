لماذا هذا المرور الثالث مهمّ

المروران السابقان عالجا المعماريّة (E1–E7: B3 يحتاج migration، B2 في الأغلفة async…). هذا المرور غاص في صحّة الحساب وجودة البيانات وتغطيتها والإفراط الهندسيّ، فاكتشف خطأً حسابيًّا حقيقيًّا (المعامل سيُكرّر زمن التسليم عند الباب)، وتناقضًا محتملًا يراه العميل (زمنان مختلفان)، وأنّ بناء كامل آليّات الأمان الآن — قبل وجود بيانات نختبرها بها — إفراطٌ هندسيّ بذاته. هذه «العيوب الخطيرة» التي يصعب رؤيتها إلّا بمحاكاة التشغيل الحقيقيّ.

① العيوب الأعمق (المرور الثالث)

F1 — خطأ حسابيّ حقيقيّ (تكرار handoff)

التتبّع: صيغة ETA (eta_service.py:57): total = prep_remaining + travel + handoff_min — والمعامل يضرب travel فقط. لكنّ النتيجة الأرضيّة delivered_at − picked_up_at تشمل السفر + التسليم عند الباب (handoff/تحصيل نقد). فمعايرة factor = (delivered−picked)/estimate تجعل المعامل يبتلع handoff، ثمّ الصيغة تضيف handoff ثانيةً ⇒ تضخيم ETA بمقدار handoff تقريبًا.

الإصلاح: اطرح handoff قبل المعايرة: actual_travel = (delivered_at − picked_up_at) − eta_handoff_minutes، ثمّ factor = actual_travel / estimate_eta_minutes(distance). (إن صار actual_travel ≤ 0 ⇒ استبعد العيّنة.)

F5 — دالّتا ETA نقيّتان يجب أن تتّفقا (تناقض يراه العميل)

التتبّع: توجد دالّتا ETA نقيّتان («No DB query»): time_to_door_minutes (شاشة التتبّع) و_wismo_eta في state_transitions.py:178 (رسالة «في الطريق») — والكود يوثّق صراحةً أنّهما يجب أن تتّفقا. لو عايرنا واحدة بمعامل متعلّم وتركنا الأخرى على الثابت ⇒ العميل يرى زمنين متناقضين.

الإصلاح: كلتاهما تتلقّى نفس المعامل المتعلّم من غلافها async (E1)؛ المعامل يُجلَب مرّة في المسار async ويُمرَّر للدالّتين. الدالّتان النقيّتان بلا تغيير. كلّ أسطح ETA تستخدم مصدر معامل واحدًا.

F2 — فلتر جودة بيانات صريح (B2)

معايرة من delivered_at − picked_up_at تحتاج فلترًا صريحًا (لا median وحده): picked_up_at IS NOT NULL AND delivered_at IS NOT NULL AND delivered_at > picked_up_at + المدّة ضمن [1, 120] دقيقة (تستبعد «نسيَ السائق التأشير 5 ساعات» أو خلل ساعة). (ملاحظة: OPS قد يصفّر picked_up_at — operations_router:783.)

F3 — تغطية: تراجع هرميّ بدل خلايا مسطّحة

المعامل = مضاعِف زمن-لكلّ-مسافة (المسافة تحمل الهندسة؛ المنطقة×الساعة تحمل المرور/الظروف). لكن خلايا (منطقة×ساعة) مسطّحة + MIN_SAMPLES ⇒ معظم الخلايا تبقى باردة شهورًا (قلّة العيّنات). الإصلاح: تراجع هرميّ منطقة×ساعة → منطقة → عامّ → 1.0 ⇒ تغطية أسرع وأمتن.

F4 — خمول العلَم (B2)

عند eta_learning_enabled=OFF (الافتراضي): الأغلفة لا تقرأ Redis إطلاقًا وتستخدم الثابت eta_correction_factor ⇒ سلوك حاليّ بايت-بايت (لا قراءة، لا كلفة، لا سطح فشل). صريحٌ في الخطّة.

F6 — كشف الانحراف لا يفرط في التراجع

الانحراف قد يكون خطأ نموذج (بيانات سيّئة ⇒ تراجع صحيح) أو تغيّر عالم (طريق مغلق ⇒ النموذج يجب أن يتكيّف لا يتراجع). الخلط ⇒ إلغاء تكيّفات جيّدة. الإصلاح: الحارس يتراجع فقط عند خطأ متطرّف بمستوى عُطل (مع clamp + تنبيه)، لا عند تغيّر طبيعيّ.

F7 — الأهمّ: إفراط هندسيّ قبل الإطلاق

الملاحظة الجوهريّة: المنصّة قبل الإطلاق (0 طلب/24س). بناء كامل آليّات الأمان (champion-challenger + backtest + drift) الآن يعني بناء آلة معقّدة لا نملك بيانات لاختبارها أو التحقّق منها ⇒ كود غير مُختبَر يجلس خاملًا. الإصلاح الاستراتيجيّ: ابدأ أصغر ما يمكن — (الأغلفة تقرأ معاملًا من Redis + بداية باردة + clamp + فلتر + علَم) — وأجِّل champion-challenger/backtest/drift حتى تتراكم بيانات حقيقيّة تُبرّرها وتختبرها. «لا تبنِ ما لا تستطيع اختباره.»

② B2 المنقّح (الحدّ الأدنى الآمن أوّلًا)

المرحلة 1أ — B2 الأدنى (يُبنى الآن، يعمل بالبداية الباردة)

  • القراءة (E1+F5): غلاف async واحد resolve_eta_factor(order) يحسب الخليّة + يجلب المعامل (Redis، await، fail-open) مع تراجع هرميّ (F3) + clamp (F2/F4)؛ يُمرَّر للدالّتين النقيّتين عبر travel_factor ⇒ اتّساق. عند العلَم OFF ⇒ لا قراءة، الثابت (F4).
  • الاشتقاق: مهمّة _scheduled_eta_calibration (نسخة حلقة الثقة 6س): طلبات DELIVERY مُسلَّمة مع فلتر F2 ⇒ actual_travel = (delivered−picked) − handoff (F1) ⇒ median/خليّة بشرط ≥MIN_SAMPLES ⇒ كتابة مفتاح JSON ذرّيّ واحد (E4).
  • بلا migration · علَم eta_learning_enabled OFF.

المرحلة 1ب — آليّات الأمان (تُؤجَّل حتى وجود بيانات — F7)

backtest + champion-challenger + drift detection + لوحة مراقبة ⇒ تُبنى بعد تراكم تسليمات حقيقيّة تُختبَر بها (post-launch). قبلها = إفراط غير قابل للاختبار.

محاكاة (post-launch): تسليم ينتهي ⇒ delivered_at ⇒ بعد 6س المهمّة: تفلتر (F2)، تطرح handoff (F1)، تحسب median/خليّة (≥20)، تكتب ذرّيًّا (E4) ⇒ الطلب التالي في الخليّة يقرأ المعامل (هرميًّا F3) ⇒ ETA أدقّ، ومتّسق عبر التتبّع والرسالة (F5). Redis معطّل/علَم OFF ⇒ ثابت 1.0 (F4، بلا كسر).

④ حالة التقارب + الحوكمة

التقارب: بعد 3 مرورات عدائيّة، خطّة B2 مُتتبَّعة إلى السطر مع مخاطرها (E1–E7 + F1–F7): F1 (تكرار handoff) وF5 (اتّساق الدالّتين) إصلاحان حسابيّان يُدمَجان؛ F7 يعيد تشكيل التسلسل (حدّ أدنى الآن، أمان بعد البيانات). المخاطر البنيويّة الكبرى استُخرِجت. أيّ مرور رابع سيدخل تفاصيل تنفيذ دقيقة تُحسَم وقت البناء لا التخطيط.
