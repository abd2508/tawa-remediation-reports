🧠 200+ سيناريو F-03 — فئات أساسية

● فئة A: كوارث الإنتاج الحالية (بدون إصلاح)

A-01 🔴 حرجمتجر يفتح → 5 طلبات auto-assign لموظف A → active_orders=5 → موظف A مجمَّد تماماً للأبد. لا حل بدون restart خادم أو SQL reset
A-02 🔴 حرج3 موظفين × 5 طلبات = 15 → بعد 15 طلب من الفتح → محرك التوزيع لا يُرسل أي طلب جديد للمتجر كله
A-03 🔴 عاليموظف A self-claim 4 طلبات → active_orders=0 → auto يختاره "الأخف" → يأخذ 5 طلبات إضافية → يحمل 9 في الواقع لكن النظام يظن 5
A-04 🔴 عاليموظف يُنهي وردية بـ active_orders=7 → يبدأ وردية جديدة يوم التالي → لا يحصل على أي طلب حتى نهاية اليوم
A-05 🟡 متوسطموظف جديد ينضم → active_orders=0 (لا صف metrics) → يحصل على كل الطلبات لأنه "الأخف" → إرهاق الموظف الجديد فوراً
A-06 🔴 حرجVolume عالي (30 طلب/ساعة) + 3 موظفين → خلال 30 دقيقة من الفتح → كل الموظفين عند cap=5 → النظام يتوقف كلياً

● فئة B: سيناريوهات تطبيق الإصلاح

B-01 🟡 هامتطبيق الإصلاح بدون SQL recalculation → موظف A لا يزال بـ active_orders=7 → لا يحصل على طلبات → إصلاح جزئي فقط. الحل: SQL أولاً
B-02 🟢 آمنrace: موظفان يتنافسان على self-claim → optimistic lock → واحد فقط ينجح → record_assignment يُستدعى مرة واحدة → صحيح
B-03 🟢 آمنcancel مزدوج (race) → record_cancellation يُستدعى مرتين → floor-at-zero في SQL يحمي → active_orders لا تصبح سالبة
B-04 🟡 يتطلب حذرطلب بدون assigned_staff_id (قبل deploy الإصلاح) → decrement يُستدعى → يجب فحص: if order.assigned_staff_id: فقط ثم نستدعي
B-05 🟢 آمنfail-open wrapper (try/except) يحمي من تعطيل accept_order إذا فشل record_assignment بسبب DB timeout مؤقت
B-06 🟡 مراقبةبعد deploy: active_orders تعمل صح → إذا ظهر أي موظف عند cap دون سبب → يعني طلباً انتهى بدون تخفيض → جدول audit يساعد

● فئة C: حالات حافة (edge cases) ذات خطورة

C-01 🔴 يتطلب حلإعادة إسناد A→B ثم B→C: A يجب أن يكون 0، B يجب أن يكون 0، C يجب أن يكون 1. الإصلاح 1.2 يتعامل مع step-by-step لكن يجب التأكد
C-02 🟢 آمنموظف يُحذف من النظام → FK على staff_user_id → cascade delete على staff_load_metrics → لا أيتام
C-03 🟢 آمنDISPUTE_RESOLVED بعد DELIVERED → order في حالة terminal منذ DELIVERED → لا تغيير في active_orders مرة ثانية
C-04 🟡 تحققEXPIRED بدون assigned_staff_id (لم يُرسَل لأحد قبل انتهاء المهلة) → if guard يحمي → لا استدعاء غير ضروري
⚠️ F-03-K — race condition: reassign يتسابق مع completion

شرح: الـ workflow اكتشف أن إعادة الإسناد اليدوي + إنهاء الطلب في نفس اللحظة قد يسبب double-decrement. لكن floor-at-zero الموجود في DB يحميه من القيم السالبة. الحل الكامل: SELECT FOR UPDATE على صف الطلب.

F-04: موظف موقوف يخترق الحماية

🔐 الجذر + الحل العالمي الأمثل

شرح مبسّط: تخيّل بطاقة دخول. الحارس البسيط يفحص فقط: هل البطاقة صالحة؟ لكن الموظف الموقوف لا تزال بطاقته صالحة لـ15 دقيقة. الحارس القوي يفحص أيضاً: هل هذا الشخص موقوف في السجل؟

الممارسة العالمية (Stripe / Shopify / Twilio): لا يعتمدون على JWT فقط للتحقق من الحظر. يُضيفون DB check خفيف في كل طلب محمي. البديل الأذكى مستقبلاً: Redis blocklist (O(1)) للموظفين المُوقَفين — لكن للحجم الحالي DB check مقبول تماماً.

📊 WLC: Weighted Least Connections

DoorDash/Uber: يستخدمون atomic SQL UPDATE مع floor-at-zero لإحصاءات worker. للحجم الصغير والمتوسط (< 50K طلب/يوم): PostgreSQL مباشرة أفضل من Redis.

Pattern: UPDATE SET active = GREATEST(active-1, 0)

🔐 Suspension Guard

Stripe/Shopify: DB check على كل request protected. مستقبلاً: Redis SET للـ suspended users (O(1)). للحجم الحالي: PostgreSQL query مقبول تماماً.

Pattern: if is_suspended: raise 403

Pattern: npm ci + cache-dependency-path

Uber Eats: non-critical operations (counters, analytics) wrapped in try/except. الطلب لا يُرفض بسبب فشل metric update. أسلوب "fail-open" للعمليات non-transactional.

Pattern: try/except BLE001 around metrics
