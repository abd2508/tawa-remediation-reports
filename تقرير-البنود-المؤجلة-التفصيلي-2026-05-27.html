🔌 Offline Queue لإثبات تَسليم السائق

١. ما هو؟

سَيناريو واقعي يومي:

السائق وَصل لِبَيت العميل في حَيّ بَعيد، شَبكة الإنترنت ضَعيفة جداً. يُدخل رمز التَّحقُّق (4 أرقام) + يُحَصِّل النقد + يَنقُر "تأكيد التَّسليم". الـrequest يَفشل بسبب timeout. السائق يَجد نَفسه في وَرطة: العميل دَفع، السلع تُسَلَّمت، لكنّ المنصّة لا تَعرف. يَجب أن يَعود لِمكان فيه شَبكة + يَعيد المحاولة يَدوياً.

الـoffline-queue يَحلّ هذا: عند فشل الـrequest بسبب شَبكة، يُحفَظ محلياً في المتصفّح/التَّطبيق، ويُعاد إرساله تلقائياً فور عَودة الاتصال. السائق لا يُحس بشيء.

٢. الوَضع الحالي في الكود

الملفweb/src/pages/driver/DriverDelivery.tsx
الـAPI callordersApi.submitDeliveryProof(orderId, { proof_type, proof_nonce, client_operation_id, lat, lng })
ما يَحدث عند فشلsetError(extractError(err)) — السائق يَرى رسالة خطأ ويَجب أن يَنقُر "إعادة المحاولة" يدوياً
الـIdempotency✅ موجود — client_operation_id يُمَرَّر لـbackend، فلا duplicate حتى لو أُعيد الإرسال 10 مرات
Service Worker⚠️ مَوجود (vite-plugin-pwa) لكن للـprecache فقط — لا BackgroundSync

٣. ما الذي يَحتاجه (4 طَبقات)

الطَّبقة ١: Workbox BackgroundSync plugin

الـService Worker الحالي مُهَيَّأ لـprecache + runtime cache. يَحتاج إضافة plugin جَديد:

// web/vite.config.ts — workbox config
workbox: {
  // ... existing config ...
  runtimeCaching: [
    {
      urlPattern: /\/api\/dispatch\/orders\/[^\/]+\/proof$/,
      handler: "NetworkOnly",
      method: "POST",
      options: {
        backgroundSync: {
          name: "delivery-proof-queue",
          options: {
            maxRetentionTime: 24 * 60,  // 24 ساعة
          },
        },
      },
    },
  ],
}

الـworkbox سيُرتِّب الـqueue تلقائياً في IndexedDB ويُعيد المحاولة عَبر sync event.

الطَّبقة ٢: تَحَقُّق المتصفّح من دَعم BackgroundSync

BackgroundSync مَدعوم في Chromium (Android/Desktop) لكنّه غير مَدعوم في iOS Safari. يَحتاج fallback:

// hooks/useOfflineProof.ts
if ('serviceWorker' in navigator && 'SyncManager' in window) {
  // BackgroundSync available
} else {
  // Fallback: store in IndexedDB manually, retry on `online` event
  window.addEventListener('online', flushQueue);
}

الطَّبقة ٣: UI feedback للسائق

السائق يَجب أن يَعرف أنّ الإثبات محفوظ محلياً وسَيُرسَل عند عَودة الشَّبكة:

// DriverDelivery.tsx
if (!navigator.onLine) {
  setProofDone(true);  // اِعرض شاشة النجاح
  setOfflineQueued(true);  // مَع badge "📡 سَيُرسَل فور عودة الإنترنت"
} else {
  // النَّمَط الحالي online
}

الطَّبقة ٤: Backend lock — مَنع double-commit

إذا الـqueue أَرسل نَفس الـrequest مَرَّتَين (مَرَّة من البَكلوغ، مَرَّة من المُحاولة اليَدوية)، الـbackend يَجب أن يَرفض الثَّانية:

الحالي✅ موجود — backend/app/modules/dispatch/dispatch_service.py يَتَحقَّق من client_operation_id + يَفشل بـ409 لو مُكَرَّر
المَطلوب الإضافيRedis lock بـTTL قصير (5 ثوانٍ) لمنع race بين الطلبَين المُتَزامِنَين

٤. لماذا أُجِّل؟

  • تَعَدُّد الطبقات: 4 طبقات مُختلفة (frontend SW + IndexedDB + UI + backend lock) — كل طبقة يَجب أن تَتَكامل مع الأُخرى
  • اختبار شَبكي حقيقي: الاختبارات الـunit لا تَكفي — يَحتاج اختبار يَدوي مع حالات حَقيقية (Airplane Mode، 3G ضَعيف، انقطاع متقطع)
  • iOS fallback: BackgroundSync غير مَدعوم في Safari — يَحتاج كود مُختلف لـiPhones
  • قابلية الانعكاس: bug في الـqueue قد يُسَبِّب double-submit في الإنتاج → خطر مالي (cash collection مُكَرَّرة)

٥. الحلّ المؤقَّت الموجود الآن

  • إذا انقطع النِّت، السائق يَرى خطأ صَريح (ليس صَامتاً)
  • الـclient_operation_id ثابت في الـsession → السائق يَنقُر "إعادة المحاولة" بأمان (لا duplicate)
  • الـcash_collection مُنفصل عن proof_submission → السائق يُحَصِّل النقد أوّلاً ثم proof يَأتي لاحقاً

٦. الأثر اللاحق إن تَم بناؤه

المَنفعة للسائقلا يَحتاج العَودة لِمنطقة بِشَبكة قَوية
الأَمان الماليغَير قابل للـdouble-charge بفَضل client_operation_id
الخَطرإذا الـqueue تَالف، السائق قد يَظنّ التَّسليم تَم بَينما الـbackend لا يَعرف لِساعات
متى يَجب تَنفيذهعند توَسُّع المنصّة لِمناطق ذات إنترنت ضَعيف (الصحراء، الأرياف الليبيَّة)

🏪 صَفحة Verify-Pickup للمزوّد في الويب

١. ما هو؟

📞 إخفاء رَقم العميل عن السائق (Number Masking + Call Relay)

١. ما هو؟

سَيناريو: السائق يَستلم طلباً، يَحتاج الاتِّصال بالعميل ليقول "أَنا عند البَوّابة". حالياً السائق يَرى رقم العميل الحقيقي ويَتَّصل به مُباشَرة. هذا يَخلق:
  • السَّائق قد يَحفظ الرقم ويَستخدمه لاحقاً (تَحَرُّش، إعلانات شَخصية، إلخ)
  • العَميل قد يَرفض السماح برؤية رَقمه → يُلغي الطَّلب
  • المنصّة لا تَستطيع تَسجيل المُكالمة (لِفَضّ النِّزاعات)

الـnumber-masking يَحلّ هذا: السائق يَرى رقماً وَسيطاً (مثلاً +218900XXXX12) يُحَوِّل المُكالمة عَبر مَزوّد خارجي إلى الرقم الحقيقي. السائق لا يَرى الرقم الأَصلي أَبداً.

٢. الوَضع الحالي في الكود

الـtoggle في الواجهة✅ مَوجود وفَعَّال في CustomerSettings.tsx:188
تَخزين الـpreference في DB✅ hide_phone_from_driver: boolean في backend/app/models/customer_extra.py:71
الـbackend يَحترم الـflag✅ order_service.py:1190 — customer_phone = cust.phone if not prefs.hide_phone_from_driver else None
الـUI السائق✅ DriverDelivery.tsx:326 — يَعرض رقم العميل فقط لو مُرسَل (tap-to-call)
الـcall relay الفعلي❌ غير موجود — لا integration مع Twilio/Sinch/مَحلِّي

٣. السلوك الفعلي الحالي (مُرَّ بدون masking)

  • إذا العميل أَبقى الـtoggle مُفَعَّلاً (default) → السائق يَرى رقم العميل الحقيقي + يَتَّصل مُباشَرة
  • إذا العميل أَطفأ الـtoggle → السائق لا يَرى رَقماً إطلاقاً → لا يَستطيع الاتِّصال (يَستخدم الـin-app chat فقط)

الفجوة: كل-أو-لا شيء. لا حلّ وَسط (relay number).

٤. ما الذي يَحتاجه (4 مَكوّنات)

المكوّن ١: مزوّد masking خارجي (مَدفوع)

الخيارات المُتاحة لليبيا:

Twilio Proxy ~$0.05 لكل session + $0.13/min — يَدعم MENA لكنّ ليبيا قد تَكون مُقَيَّدة
Sinch Verification أَرخص قليلاً لكن دَعم ليبيا غير مُؤَكَّد
Plivo Voice API simple، asseر، يَحتاج اختبار في ليبيا
مزوّد ليبي مَحلِّي الأَفضل — Libyana / Almadar قد يُوَفِّرون SIP trunk → يَحتاج اتفاقية تجارية

المكوّن ٢: Backend integration

  • أو يدوياً عند DELIVERED + ساعة

٥. لماذا أُجِّل؟

  • عَدَم وضوح دَعم ليبيا: Twilio/Sinch قد لا يَدعموا أرقام +218 مَباشَرة — اختبار مَطلوب
  • عَوامل تَجارية: هل تَستحقّ الميزة تَكاليف شَهرية مُتزايدة؟ يَعتمد على عَدَد الطلبات
  • تَكامل أَفضل مع مَزوّد ليبي: Libyana/Almadar كحلّ مَحلِّي قد يَكون أَرخص لكن يَحتاج وَقت مُفاوضات
  • قابلية الانعكاس: إذا الـmasking سَيِّء (تأخُّر، انقطاع)، تَجربة سَيِّئة جداً لِكِلا الطَّرفَين

٦. الحلّ المؤقَّت المَوجود الآن

  • الـin-app chat (Phase 447) مَوجود ويُعَوِّض المُكالمات لِأَغلب الحالات
  • لو احتاج العميل/السائق التحدُّث → يُلجَأ للـOPS كَوَسيط
