وثيقة تنفيذ دقيقة لمطوّر تطبيق السائق الجوّال. الهدف: تمكين سائقي الجوّال من إكمال طلبات «اطلب أيّ شيء / مشوار» — تمامًا كما يعمل الآن في بوّابة السائق على الويب. كلّ نقاط الـAPI الخلفيّة منشورة وحيّة بالفعل؛ المطلوب تغييرات تطبيق الجوّال فقط. · 2026-06-21
🔌 API حيّ (لا تغيير backend) ✅ المرجع: بوّابة السائق على الويب (مُنفَّذة) 📦 Flutter · mobile_app/
الفكرة بإيجاز: «المشوار» طلب بلا متجر — العميل يصف ما يريده ويحدّد ميزانيّة (مدفوعة مسبقًا من محفظته). لا يوجد مزوّد يُسلّم الطلب للسائق، فالسائق هو المتسوّق. لذلك شاشة الاستلام في الجوّال يجب أن تعرض — لطلبات المشوار فقط — قائمة التسوّق وزرًّا واحدًا «تمّ الشراء — في الطريق» بدل «قائمة الفحص + مسح المزوّد».

١ عقد الـAPI (حيّ ومنشور — لا تعديل)

أ) جلب تفاصيل الطلب للسائق — مُحدَّث بحقلين جديدين

// GET /orders/{order_id} (دور السائق — موجود مسبقًا) // الاستجابة الآن تتضمّن حقلين إضافيّين: { "id": "…", "order_state": "DRIVER_ASSIGNED", "payment_method": "WALLET", "total_minor": 25000, "currency": "LYD", "fulfillment_type": "ERRAND", // ← جديد: "DELIVERY" | "SELF_PICKUP" | "ERRAND" "errand_description": "عشرة أرغفة خبز + علبة حليب + ملح", // ← جديد: نصّ المشوار (null لغير المشوار) "dropoff_info": { "address_hint": "طرابلس - حي الأندلس" }, "delivery_notes": [ … ] }

ب) نقطة جديدة — تأكيد استلام المشوار (تحلّ محلّ مسح المزوّد)

POST /dispatch/orders/{order_id}/errand-picked-up // Headers: Authorization: Bearer <driver JWT> · Body: {} (فارغ) // الدور: DRIVER (السائق المقبول لهذا الطلب فقط) // 200 OK: { "order_id": "…", "order_state": "EN_ROUTE" } // أخطاء محتملة: // 403 — السائق غير مصرَّح له بهذا الطلب (ليس المقبول) // 422 — ليس طلب مشوار / حالة غير صالحة للاستلام // 404 — ملف السائق غير موجود
ما تفعله النقطة: تنقل الطلب DRIVER_ASSIGNED → DRIVER_AT_PROVIDER → PICKED_UP → EN_ROUTE دفعةً واحدة (النظام يؤكّد نيابةً عن السائق لأنّه لا مزوّد). بعدها يُكمِل السائق بتدفّق التسليم العاديّ (وصول → إثبات تسليم).

٢ تدفّق حالات المشوار (للسائق)

مهمّ: المشوار دائمًا محفظة (WALLET) — مدفوع مسبقًا. لا تحصيل نقد عند التسليم. الميزانيّة محجوزة وتُثبَّت عند DELIVERED تلقائيًّا (لا عمل من السائق).

٤ المرجع: التنفيذ على الويب (انسخ سلوكه حرفيًّا)

الويب مُنفَّذ ومنشور — هو مصدر الحقيقة للسلوك والنصوص:
  • web/src/pages/driver/DriverPickup.tsx — فرع isErrand (قائمة التسوّق + زرّ «تمّ الشراء»).
  • web/src/api/dispatch.ts — errandPickedUp(orderId).

٥ حالات الحافّة ومعالجة الأخطاء

الحالةالسلوك المطلوب
الطلب غير مشوار (fulfillmentType != "ERRAND")لا تغيير — الشاشة الحاليّة (قائمة الفحص + مسح المزوّد) كما هي.
errand_description فارغ/nullاعرض «—» (لا تتعطّل).
الضغط على «تمّ الشراء» والحالة ليست DRIVER_ASSIGNED/AT_PROVIDERالخادم يردّ 422 — اعرض message_ar.
السائق ليس المقبول للطلبالخادم يردّ 403 — اعرض الرسالة.
نجاح (200، EN_ROUTE)انتقل لشاشة التسليم (delivery) — السائق يُكمل: وصول → إثبات تسليم.
الدفعالمشوار دائمًا محفظة — لا تعرض أيّ واجهة تحصيل نقد للمشوار.

٦ معايير القبول (الاختبار)

  • ☑ طلب مشوار (DRIVER_ASSIGNED) ⇒ شاشة الاستلام تعرض «قائمة التسوّق» + زرّ واحد (لا قائمة فحص، لا رمز مزوّد).
  • ☑ الضغط على «تمّ الشراء» ⇒ نداء POST /dispatch/orders/{id}/errand-picked-up ⇒ 200 + الحالة EN_ROUTE ⇒ الانتقال للتسليم.
  • ☑ طلب عاديّ (DELIVERY) ⇒ الشاشة بلا تغيير (قائمة الفحص + مسح المزوّد كما كانت).
  • ☑ لا واجهة تحصيل نقد تظهر في مسار المشوار.
  • ☑ أخطاء 403/422 تُعرَض رسالتها العربيّة للسائق.
  • ☑ اختبار widget للحالتين (مشوار / عاديّ) — كما في web .../DriverPickup.test.tsx.
