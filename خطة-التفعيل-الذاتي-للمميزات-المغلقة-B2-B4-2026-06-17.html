النموذج: off · auto · on الافتراض الجديد: auto (يفتح نفسه عند الجاهزيّة) migration: لا شيء قابل للعكس + fail-open: دائمًا

الفكرة في سطر

🧑 بلغة بسيطة: بدل أن «نضغط زرًّا يدويًّا» لاحقًا لتشغيل كلّ ميزة، نجعلها تشغّل نفسها تلقائيًّا في اللحظة التي تصبح فيها بياناتها كافية وموثوقة — ونضع لها «حسّاس جاهزيّة» يمنعها من العمل ببيانات سيّئة، و«مفتاح إيقاف طوارئ» يبقى بيد المالك. فلا ننسى تفعيلها، ولا تشتغل قبل أوانها.
🔧 باللغة الفنية الثقيلة: نستبدل العلَم الثنائيّ (bool) بحالة ثلاثيّة <feature>_mode ∈ {off, auto, on} (الافتراض auto). feature_active(mode, ready_fn) = (mode=="on") or (mode=="auto" and ready_fn())؛ ready_fn تُحسَب من meta/مفاتيح Redis للدولاب. التطبيق لكلّ خليّة ذاتيّ أصلًا (resolve يستعمل المتعلَّم عند وجوده). نُضيف: عتبات جودة + هيستيريسيس (منع التذبذب) + رؤية في health + سطر سجلّ عند الانتقال. كلّه fail-open · قابل للعكس · بلا migration.

① النموذج: من «علَم يدويّ» إلى «تفعيل ذاتيّ واعٍ بالبيانات»

ثلاث حالات لكلّ ميزة:

  • off — مفتاح إيقاف طوارئ (قرار بشريّ صريح). يفوز دائمًا. عودة byte-for-byte.
  • auto — الافتراض: الميزة «مسلَّحة» وتفتح نفسها لكلّ خليّة فور بلوغ بياناتها عتبة الجودة، وتبقى خاملة قبل ذلك.
  • on — فرض التشغيل (تجاوز حسّاس الجاهزيّة — للاختبار/الطوارئ فقط).
توافق رجعيّ: ENABLED=true القديم → on · false → off · غير مضبوط → auto.
الكود الأساس (يُبنى مرّة، يخدم الكلّ):
// app/core/feature_gate.py  (جديد — مساعد نقيّ)
def resolve_mode(raw) -> str:           # توافق رجعيّ
    s = str(raw).lower()
    return {"true":"on","1":"on","on":"on","false":"off","0":"off","off":"off"}.get(s,"auto")

async def feature_active(mode: str, ready) -> bool:
    if mode == "off": return False      # مفتاح الطوارئ يفوز دائمًا
    if mode == "on":  return True       # فرض
    return await ready()                # auto → حسّاس الجاهزيّة (يقرأ meta، fail-open=False)

② لكلّ ميزة: شرط الجاهزيّة الدقيق + ماذا يتفاعل تلقائيًّا

المحور 1+2 — عوامل ETA المتعلّمة (بطل/متحدٍّ + EWMA) يتفاعل تلقائيًّا لكلّ خليّة

🧑 بسيط: هذا يتفاعل ذاتيًّا أصلًا: حين تجمع منطقةٌ-ساعة ما يكفي من التوصيلات، يظهر لها «معامل» ويُستعمل فورًا لتلك المنطقة فقط؛ والمناطق التي لم تنضج بعد تبقى على الوقت الثابت. لا زرّ ولا انتظار.
🔧 تقنيًّا: resolve_eta_factor يُرجِع المتعلَّم فقط للخلايا الموجودة في champion (لا تدخل خليّة إلّا بـ≥MIN_SAMPLES=20)؛ غيرها → ثابت. ⇒ التطبيق per-cell تلقائيّ. التحويل الوحيد: eta_learning_mode بدل البول؛ في auto الحلقة تعمل وresolve يقرأ Redis (رخيص، fail-open).
شرط جاهزيّة المستوى-العامّ (للرؤية فقط): ready_eta() = champion غير فارغ (≥1 خليّة متعلَّمة). per-cell يبقى الحاكم الفعليّ.

المحور 4 — نطاق ETA (p90 «بحلول HH:MM») يتفاعل تلقائيًّا + إصلاح

🧑 بسيط: يفتح نفسه لكلّ منطقة بمجرّد توفّر «ذيلٍ موثوق» (عيّنات كثيرة كفايةً)، ويظهر النطاق فقط حين يكون «أسوأ» فعلًا من النموذجيّ. حتى ذلك الحين لا شيء يظهر — صفر وعود خاطئة.
🔧 تقنيًّا: resolve_eta_range يُرجِع p90 فقط للخلايا في p90:v1؛ والواجهة تعرض فقط حين p90>p50 ⇒ حماية مزدوجة per-cell. التحويل: استبدال eta_range_enabled بـeta_range_mode؛ ready_range() = p90 map فيه ≥ N خلايا.
الإصلاح المُدمَج (يجعل التفعيل الذاتيّ آمنًا): عتبة p90 منفصلة أعلى _MIN_SAMPLES_P90=50 (الكمّيّة 90 تحتاج عيّناتٍ أكثر من الوسيط) ⇒ لا تدخل خليّة p90 map إلّا بذيلٍ موثوق ⇒ التفعيل الذاتيّ لا يُشغّل نطاقًا رديئًا.

B4 — تنبّؤ الطلب يتفاعل تلقائيًّا (OPS فقط)

🧑 بسيط: يملأ نفسه تلقائيًّا كلّما تراكمت طلبات؛ غرفة العمليّات ترى الرقم حين يوجد، و«—» حين لا يوجد. لا يمسّ العميل إطلاقًا.
🔧 تقنيًّا: demand_forecast_mode=auto ⇒ الحلقة تحسب دائمًا (الإخراج {} حتى توجد بيانات)؛ ready_demand() = forecast غير فارغ. النقطة OPS تُرجِع ما هو موجود. آمن للتشغيل الدائم.

المحور 3ب — كشف الانحراف PSI يتفاعل تلقائيًّا بعد جولتين

🧑 بسيط: «جهاز إنذار» يشغّل نفسه فور وجود تاريخٍ كافٍ ليقارن به (جولتان فأكثر)، ويُنبّه استشاريًّا إن تغيّر سلوك الطلبات فجأةً — بلا أيّ إجراء تلقائيّ.
🔧 تقنيًّا (إضافيّ، بعد البيانات): ready_psi() = meta.round≥2 AND total_samples≥T؛ يحسب PSI=Σ(curr%−base%)·ln(curr%/base%) من توزيعات الخلايا، يخزّنه في meta.drift_psi، ويُنبّه عبر alert_webhook القائم عند >0.2. استشاريّ بحت.
الميزةشرط الجاهزيّة (auto يُفعّل عند…)يتفاعل تلقائيًّا عند مستوىالإصلاح المطلوب

③ ما الذي لا يتفاعل تلقائيًّا (ولماذا) — صراحةً

لا يتفاعل تلقائيًّالماذاكيف يُفعَّل إذًا
🛑 مفتاح الإيقاف (off)قرار بشريّ مقصود — لا يجب أن «يُلغي» نفسهالمالك يضبط mode=off (يفوز فورًا)
🔵 G4 (الذاكرة المؤقّتة)تحسين أداء لا بيانات — لا يوجد «حدّ بيانات» يُشغّله؛ ويبقى مغلقًا (لا مشكلة يحلّها)يدويّ + قياس حِمل يُثبت الحاجة (request-scoped)
📣 وجهة التنبيه (PSI alert)تحتاج ALERT_WEBHOOK_URL خارجيًّا (Slack/…)المالك يضبط الـwebhook (مورد خارجيّ)
🗺️ ميزات الموارد الخارجيّة (OSRM/ETA-ML)تحتاج بيانات OSM ليبيا/بنية تدريب — لا تُولَد ذاتيًّاالمالك يُجهّز المورد ثمّ علَمه
🔒 الختم الماليّ / production_paymentحوكمة — لا يُفتح تلقائيًّا أبدًاقرار حوكمة صريح (خارج هذه الخطّة)
🗄️ أيّ تغيير مخطّط (migration)لا يوجد هنا، ومبدئيًّا لا يُطبَّق تلقائيًّا—
القاعدة: يتفاعل تلقائيًّا ما كان مُحرّكه تراكم البيانات (قابل للقياس داخليًّا). لا يتفاعل ما كان مُحرّكه قرارًا بشريًّا أو موردًا خارجيًّا (الإيقاف، الموارد، الحوكمة، الأداء).

④ إصلاح الميزات «ذات المشاكل»

المشكلة 1 — عتبة p90 منخفضة (ذيل غير موثوق) إصلاح يُبنى الآن (خامل)

🧑 بسيط: حساب «أسوأ حالة» من 20 توصيلة فقط متذبذب. الحلّ: لا نعرض «بحلول HH:MM» إلّا لمنطقةٍ جمعت ≥50 توصيلة ⇒ الرقم يصير جديرًا بالثقة قبل أن يراه العميل.
🔧 تقنيًّا: ثابت منفصل _MIN_SAMPLES_P90=50 في eta_learning.py؛ في حلقة المعايرة: if len(vals)>=_MIN_SAMPLES → p50، وif len(vals)>=_MIN_SAMPLES_P90 → p90 (شرطان منفصلان). تسجيل p90_cells في meta لحسّاس الجاهزيّة. خامل حتى توجد بيانات ⇒ صفر خطر اليوم.

المشكلة 2 — G4 كسر اختبار + تسرّب حالة الحلّ: يبقى مغلقًا

🧑 بسيط: «اختصار السرعة» الذي اقترحناه كان يكسر اختبارًا، وفائدته معدومة عمليًّا. الإصلاح الأصحّ = عدم بنائه الآن. وإن لزم مستقبلًا، له تصميم بديل آمن.
🔧 تقنيًّا: سبب الكسر: ذاكرة على مستوى الوحدة تخدم قيمةً قديمة لاستدعاءاتٍ متتالية + حالة عامّة تتسرّب بين الاختبارات. المستدعي وحيد (order_router.py:654) ⇒ لا تضخّم. البديل الآمن إن فُتح: ذاكرة request.state (request-scoped، لا حالة عامّة). لا تفعيل ذاتيّ — مُحرّكه أداء لا بيانات.

المشكلة 3 — PSI لا يُختبَر قبل البيانات إصلاح: بناء مؤجَّل + تفعيل ذاتيّ

🧑 بسيط: لا يمكن اختبار «جهاز إنذار» بلا حركةٍ يرصدها. الحلّ: نبنيه لاحقًا كإضافةٍ تشغّل نفسها فور وجود تاريخٍ كافٍ، وتبقى استشاريّة (لا تتخذ قرارًا).
🔧 تقنيًّا: دالّة compute_drift(prev_meta, curr) نقيّة قابلة للاختبار بمعطياتٍ مُصطنعة الآن (وحدة)؛ تُوصَل في _publish_factors وتُحرَّس بـready_psi(). صفر إجراء على العميل/التوزيع.

⑤ أمان التفعيل الذاتيّ نفسه (كيلا يتحوّل لمشكلة)

التفعيل الذاتيّ يُدخل خطرًا جديدًا: أن «تشتغل الميزة في توقيتٍ خاطئ». نحييّده بأربع طبقات:

1) عتبات جودة في حسّاس الجاهزيّة: per-cell MIN_SAMPLES(20)/MIN_SAMPLES_P90(50) + حارس تغطية الخلايا ⇒ لا تنشط على بياناتٍ رقيقة.
2) هيستيريسيس (منع التذبذب): لا «تتخرّج» الميزة للنشاط إلّا بعد R جولات متتالية جاهزة، ولا تنطفئ إلّا بعد grace. يمنع on/off كلّ 6 ساعات.
3) مفتاح الطوارئ يفوز: off يُلغي كلّ شيء فورًا، byte-for-byte.
4) رؤية + سجلّ الانتقال: health يُظهر الحالة، وسطر سجلّ + تنبيه استشاريّ عند كلّ تحوّل ⇒ لا «مفاجأة صامتة».

⑥ كيف يرى المالك الحالة الذاتيّة (الرؤية)

🔧 نقطة GET /operations/eta-factors/health تُوسَّع لتُظهر لكلّ ميزة:
{ "eta_factors": { "mode":"auto", "ready":true,  "active":true,  "cells":34, "since_round":12 },
  "eta_range":   { "mode":"auto", "ready":false, "active":false, "p90_cells":3, "need":"≥N cells @≥50 samples" },
  "demand":      { "mode":"auto", "ready":false, "active":false, "slots":0 },
  "drift":       { "mode":"auto", "ready":false, "psi":null, "need":"round≥2" } }
🧑 بسيط: شاشة واحدة تقول لكلّ ميزة: «وضعها auto · جاهزة؟ نشطة؟ منذ متى؟ وما الذي ينقصها لتنشط». فلا شيء يحدث في الظلام.

⑦ خطّة البناء بالمراحل (بلا migration · كلّ مرحلة خاملة وقابلة للعكس)

  1. P1 — الأساس: core/feature_gate.py (resolve_mode + feature_active) + الحالات الثلاثيّة في config.py (eta_learning_mode/eta_range_mode/demand_forecast_mode/drift_mode، افتراض auto، توافق رجعيّ مع البولات القديمة). اختبارات: off/on/auto × (جاهز/غير جاهز).
  2. P2 — إصلاح p90: _MIN_SAMPLES_P90=50 + تسجيل p90_cells في meta. اختبار: خليّة 30 عيّنة لها p50 بلا p90؛ 50 عيّنة لها الاثنان.
  3. P3 — توصيل الحسّاسات: دوالّ ready_eta/ready_range/ready_demand (تقرأ meta، fail-open=False) + استبدال البولات في resolve_eta_factor/resolve_eta_range/الحلقتين بـfeature_active. اختبارات: auto خامل بلا بيانات؛ auto نشط ببيانات؛ off يُلغي؛ on يفرض.
  4. P4 — هيستيريسيس + رؤية: عدّاد جولات-جاهزة + grace في meta (graduated_round) + توسيع health + سطر سجلّ عند الانتقال. اختبار: لا تخرّج قبل R؛ لا انطفاء قبل grace.
  5. P5 — PSI (بعد بيانات): compute_drift نقيّة + توصيلها محروسةً بـready_psi + تنبيه استشاريّ. اختبار وحدة بمعطيات مصطنعة الآن.
  6. G4: لا مرحلة — يبقى مغلقًا.
لكلّ مرحلة: بوّابة انحدار (0 فشل جديد) · FIN-COR · محاكاة عدائيّة · نشر خامل · تحقّق حيّ. الافتراض auto آمن لأنّه خامل حتى البيانات — أسوأ ما يحدث من النشر = «مسلَّح بلا أثر».
