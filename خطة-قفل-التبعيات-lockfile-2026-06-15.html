منصّة تووا (Tawa) — الخلفيّة (FastAPI/Python) — الانتقال من نطاقات مفتوحة الحلّ إلى بناء حتميّ مُثبَّت بالكامل
التاريخ: 2026-06-15 · النوع: خطّة (لم تُنفَّذ — تنتظر إذن المالك) · النطاق: backend/pyproject.toml · backend/Dockerfile · إعداد البوّابة
السياق: متابعة لـ«تثبيت التبعيّات الحرج» + «إغلاق العقد الكامل (23 حدًّا)» — الحدود حدَّت المباشرة؛ هذا يُلغي التباعد والانتقاليّة جذريًّا.

1 · لماذا — المشكلة المُثبَتة بالكود

كشفت جلسة اليوم سلسلةً من الأدلّة المباشرة على أنّ بناء الخلفيّة غير حتميّ:

  • لا lockfile. backend/Dockerfile يفعل حرفيًّا pip install --no-cache-dir -e "backend/.[dev]" ⇒ يُحلّ محلّل pip نطاقات pyproject.toml طازجةً في كلّ بناء.
  • الحادثة الأمّ: بناء نظيف سحب fastapi 0.137.1 (حدّ أعلى مفتوح) ⇒ AttributeError في تَجهيز Prometheus ⇒ HTTP 500 على كلّ طلب. الإنتاج نجا فقط لأنّ صورته أقدم من 0.137.
  • اكتشاف التباعد (تحقّق متقاطع بين بيئة البوّابة والحاوية المنشورة): الاختبارات تُحقَّق على مجموعة، والإنتاج يشغّل أخرى — عبر نسخ رئيسيّة.

الخلاصة: الحدود العليا (المُضافة اليوم) تمنع القفزة الكاسرة التالية، لكنّها تحدّ التبعيّات المباشرة فقط. يبقى خطران:
  1. التبعيّات الانتقاليّة (transitive) غير مثبَّتة إطلاقًا — أيٌّ منها قد ينكسر في بناء نظيف.
  2. التباعد بوّابة↔إنتاج مستمرّ ضمن الحدود — الاختبارات لا تتحقّق ممّا يشغّله الإنتاج فعلًا.
الـlockfile يُغلق الاثنين معًا.

2 · الهدف

بناء حتميّ بالكامل
كلّ بناء (إنتاج + بوّابة) يثبِّت مجموعة نسخ متطابقة بايتًا — تشمل كلّ تبعيّة انتقاليّة — مع بذور --require-hashes (مناعة ضدّ تبديل الحِزَم وتلف الشبكة).
تحديثات مُتعمَّدة ومُراجَعة
ترقية أيّ تبعيّة تصبح خطوة واعية: تعديل الحدّ → إعادة توليد القفل → بناء → بوّابة → تحقّق. الاحتكاك هو آليّة الأمان.

تتكامل مع الحدود لا تستبدلها: الحدود في pyproject.toml = السياج الخارجيّ (ما يُسمح لمولّد القفل باختياره) · القفل = التثبيت الدقيق للاختيار. حزام وحمّالة.

4 · التصميم

4.1 — ملفّا قفل (تشغيل / تطوير)

pyproject.toml يفصل أصلًا dependencies عن [project.optional-dependencies] dev. نولّد قفلين مثبَّتين بالـhash:

الملفّالمصدرالاستخدام
backend/requirements.lockdependencies فقطصورة الإنتاج (وقت تشغيل، أصغر، سطح هجوم أقلّ)
backend/requirements-dev.lockdependencies + [dev]البوّابة + الـ.venv المحلّيّ (نفس مجموعة التشغيل + أدوات الاختبار)
# توليد القفل — داخل حاوية python:3.12-slim لمطابقة معماريّة البناء تمامًا
# (الصورة linux/amd64؛ توليده على بيئة مختلفة قد يثبّت wheels خاطئة)
pip install pip-tools
pip-compile --generate-hashes --output-file backend/requirements.lock      backend/pyproject.toml
pip-compile --generate-hashes --extra dev \
            --output-file backend/requirements-dev.lock backend/pyproject.toml

4.2 — تعديل Dockerfile

الحاليّ — هشّ

COPY backend/pyproject.toml backend/
RUN pip install --no-cache-dir \
    -e "backend/.[dev]"
# ↑ يُحلّ النطاقات طازجةً
#   كلّ بناء = نسخ مختلفة محتملة

الهدف — حتميّ

COPY backend/pyproject.toml \
     backend/requirements.lock backend/
RUN pip install --no-cache-dir \
    --require-hashes \
    -r backend/requirements.lock
COPY backend/ backend/
RUN pip install --no-cache-dir \
    --no-deps -e backend/
# ↑ نسخ مثبَّتة + الحزمة بلا إعادة حلّ

ملاحظة: صورة الإنتاج تنتقل إلى قفل التشغيل فقط (لا [dev]) — صورة أصغر وأأمن. هذا تغيير سلوك مقصود (الحاليّ يثبّت dev في الإنتاج)؛ مخاطره منخفضة (أدوات الاختبار غير مستخدَمة وقت التشغيل). البوّابة/الـCI تستخدم requirements-dev.lock.

4.3 — مواءمة البوّابة (يُلغي التباعد)

يُعاد بناء الـ.venv المحلّيّ من requirements-dev.lock ⇒ الاختبارات تشغّل نفس مجموعة التشغيل المثبَّتة التي يشغّلها الإنتاج (+ أدوات). هذا يلغي فجوة redis 7.4↔8.0 / structlog 25↔26 جذريًّا.

# إعداد/مواءمة بيئة البوّابة
python -m venv backend/.venv
backend/.venv/bin/pip install --require-hashes -r backend/requirements-dev.lock
⚠️ هذه الخطوة قد تكشف فروقًا: مواءمة الـvenv إلى redis 8 / structlog 26 (ما يشغّله الإنتاج) قد تُظهر اختبارات تتصرّف مختلفًا تحت النسخ الأحدث. هذه ميزة لا عيب — نكتشف الفرق في البوّابة قبل الإنتاج. تتطلّب جلسة عمل لمعالجة أيّ انكسار يظهر.

5 · خطّة الطرح — مراحل آمنة

1
التوليد. إضافة pip-tools لـ[dev]؛ توليد القفلين داخل حاوية python:3.12-slim (مطابقة المعماريّة). المخرجات: requirements.lock + requirements-dev.lock مرتكزان على المجموعة المعروفة-الجيّدة الحاليّة.
2
مواءمة البوّابة + بوّابة كاملة. إعادة بناء .venv من قفل التطوير → تشغيل predeploy_gate.sh الكامل. نقطة الحسم: هنا تُحَلّ فجوة البوّابة↔الإنتاج، وقد تظهر فروق سلوك تحت redis 8/structlog 26 — تُعالَج قبل المتابعة.
3
تعديل Dockerfile. التثبيت من القفل بـ--require-hashes (تشغيل) + --no-deps -e للحزمة.
4
بناء محلّيّ نظيف + إقلاع + دخان. تأكيد أنّ القفل يثبِّت ويُقلع (النقاط 200/401 · /metrics 200) — كما في تحقّق التثبيت.
5
النشر. عبر deploy/deploy_be.sh (يعيد بناء الإنتاج من القفل) → تحقّق حيّ على tawanow.com. (يحتاج «واصل النشر».)
6
التوثيق. backend/DEPENDENCIES.md + سكربت deploy/lock_deps.sh لإعادة توليد القفل بشكل مُعاد الإنتاج، وخطوات الترقية المُتعمَّدة.
