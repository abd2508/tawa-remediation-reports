١) ماذا حدث بالضبط — التسلسل الحيّ

#الإجراءالنتيجة الحيّة
1اكتشاف عنوانك العامّIPv4 217.228.240.34 · IPv6 2003:c4:7f09:… (يختلف عن السابق …7f40… → متغيّر)
2ضبط ADMIN_IP_ALLOWLIST=217.228.240.34 + إعادة إنشاء backendbackend صحّيّ · المتغيّر داخل الحاوية ✓
3اختبار /control-panel من جهازك403 IP_NOT_ALLOWED — محجوب!
4قراءة سجلّ الخادمAdmin IP blocked: 172.25.0.1 path=/control-panel — الخادم رأى بوّابة Docker، لا عنوانك!
5إرجاع فوريّ: ADMIN_IP_ALLOWLIST="" (فارغ=مفتوح) + إعادة إنشاء/control-panel = 401 UNAUTHORIZED (مفتوح، لا IP_NOT_ALLOWED) → وصولك مُستعاد ✓
6فحص الطوبولوجياأُكِّد: nginx على المضيف (:443 TLS) → nginx الحاوية (127.0.0.1:8080) → backend
المهمّ: لم تُقفَل. الحالة الآن = قفل IP مُطفأ (مفتوح) تماماً كما كان، وMFA الصارم فعّال يحمي لوحة التحكّم (كلمة مرور + كود TOTP).

٢) السبب الجذريّ: البروكسي المزدوج

🟦 بلغة بسيطة: طلبك يمرّ عبر بوّابتين (حارسين) قبل الخادم. الحارس الثاني (داخل Docker) يكتب على «بطاقة هويّة الزائر» عنوانه هو بدل عنوانك الحقيقيّ. فحين يصل الطلب للخادم، يرى عنوان الحارس الثاني (172.25.0.1) لا عنوانك.
رحلة الطلب الفعليّة (مُثبَتة حيّاً): [ متصفّحك ] عنوانك الحقيقيّ = 217.228.240.34 │ HTTPS ▼ [ nginx على المضيف ] :443 (إنهاء TLS) │ remote_addr = 217.228.240.34 ← يرى عنوانك الصحيح │ يضبط X-Real-IP = 217.228.240.34 ✓ (صحيح هنا) │ proxy_pass → 127.0.0.1:8080 ▼ [ nginx داخل الحاوية ] :80 (المنفذ 127.0.0.1:8080) │ remote_addr = 172.25.0.1 (بوّابة Docker — لا عنوانك!) │ proxy_set_header X-Real-IP $remote_addr ← يكتب فوق X-Real-IP │ X-Real-IP الآن = 172.25.0.1 ✗ (دُمِّر عنوانك) ▼ [ backend ] _get_client_ip() يقرأ X-Real-IP = 172.25.0.1 → قفل IP يقارن 172.25.0.1 ≠ 217.228.240.34 → 403 حجب

الدليل المؤكَّد: سجلّ app.core.ip_allowlist: "Admin IP blocked: 172.25.0.1" · فحص المنافذ: nginx مضيف على 0.0.0.0:443 + تعيين الحاوية 80/tcp → 127.0.0.1:8080.

لماذا «يكتب فوق»؟ تفصيل تقنيّ

nginx الحاوية فيه السطر proxy_set_header X-Real-IP $remote_addr;. الـ$remote_addr عنده = من يتّصل به مباشرةً = nginx المضيف عبر شبكة Docker = البوّابة 172.25.0.1. فبدل تمرير الـX-Real-IP الصحيح القادم من المضيف، يستبدله بعنوان البوّابة. (الـX-Forwarded-For يُلحَق لا يُستبدَل، فعنوانك الحقيقيّ ما يزال داخله بترتيب 217.228.240.34, 172.25.0.1 — لكن _get_client_ip يقرأ X-Real-IP أولاً فلا يصل لـXFF.)

٣) لماذا قفل IP لا يعمل كما هو — وضعان فاشلان

الوضع (أ): أضع عنوانك الحقيقيّ ADMIN_IP_ALLOWLIST = 217.228.240.34 الخادم يرى الجميع كـ172.25.0.1 ≠ 217.228.240.34 → يُحجَب الجميع (وأنت) — 403 ✗ (هذا ما حدث فعلاً) الوضع (ب): أضع عنوان البوّابة ADMIN_IP_ALLOWLIST = 172.25.0.1 الخادم يرى الجميع كـ172.25.0.1 = 172.25.0.1 → يُسمح للجميع — بلا أيّ قيمة أمنيّة ✗ (قفل وهميّ)

أيّ قيمة أضعها تقع في أحد هذين الفخّين. لا يمكن التمييز بين زائر وآخر ما دام الخادم يرى عنواناً واحداً للجميع. الحلّ الوحيد = إصلاح سلسلة البروكسي ليصل العنوان الحقيقيّ.

٤) العائق الثاني (مستقلّ): عنوانك ديناميكيّ

🟦 بلغة بسيطة: حتى لو أصلحنا البروكسي ورأى الخادم عنوانك الحقيقيّ، فعنوانك السكنيّ يتغيّر (مزوّدو الإنترنت في ألمانيا غالباً يُدوّرون العنوان كلّ ~24 ساعة أو عند إعادة تشغيل الراوتر). فالقفل المضبوط على عنوان اليوم سيرفضك غداً.
  • IPv4 217.228.240.34 — سكنيّ ألمانيّ، شبه مؤكَّد أنّه ديناميكيّ.
  • IPv6 2003:c4:7f09:ee00:… — تغيّر فعلاً عن قراءة سابقة (2003:c4:7f40:a300:…) → دليل حيّ على التغيّر.
  • القفل يطابق العنوان بالضبط (لا نطاقات CIDR) → أيّ تغيّر = حجب فوريّ → تحتاج break-glass.

الخلاصة: قفل IP مصمَّم لعنوان ثابت (مكتب/خادم/VPN بعنوان خروج ثابت). عنوان سكنيّ ديناميكيّ خيار هشّ بطبيعته — مهما أصلحنا البروكسي.

٥) اكتشاف جانبيّ مهمّ: rate-limit + قفل الدخول يُصابان بنفس العلّة

الدالّة _get_client_ip نفسها يستخدمها أيضاً مُحدّد المعدّل (rate limiter) وقفل محاولات الدخول. وبما أنّها ترى الجميع كـ172.25.0.1:

الميزةالمقصودالواقع الآن (بسبب العلّة)
Rate limit (60/دقيقة لكل IP)لكلّ زائر دلوهالجميع في دلو واحد (172.25.0.1) → الحدّ شبه عالميّ
قفل الدخول per-(user, ip)عزل المهاجم عن الضحيّةالـIP ثابت للجميع → التمييز per-IP ضائع
الجانب المضيء: إصلاح _get_client_ip (الخيار ٢ و٣) يُصلح هذه الثلاثة معاً (قفل IP + rate-limit + قفل الدخول) — تحسين أمنيّ حقيقيّ بصرف النظر عن قفل IP.

٦) الخيارات الثلاثة — تفصيل عميق

موصى به الخيار ١: لا تُفعّل قفل IP (MFA يكفي)

ماذا يحدث: نترك قفل IP مُطفأً (فارغ=مفتوح) كما هو الآن. لا تغيير في الكود ولا البنية. الحماية تعتمد على MFA الصارم الفعّال (كلمة مرور + كود TOTP).

الجانبالتفصيل
✅ المخاطرصفر — لا تغيير، لا خطر قفل، لا لمس بنية
✅ الجهدصفر (الحالة الحاليّة)
✅ الحمايةMFA الصارم قويّ: كلمة المرور المسروقة عديمة الجدوى بلا هاتفك. هذا هو الضابط الأهمّ أصلاً.
⚠️ ما يفوتكطبقة دفاع شبكيّة إضافيّة (defense-in-depth) — لكنّها هشّة لعنوان ديناميكيّ على أيّة حال · يبقى rate-limit/قفل-الدخول يريان بوّابة واحدة

لمن يناسب: إن كان MFA كافياً لراحتك (وهو معيار صناعيّ قويّ للأدمين)، وعنوانك ديناميكيّ.

توازن الخيار ٢: أصلِح سلسلة البروكسي فقط (بلا قفل IP)

ماذا يحدث: أُعدّل _get_client_ip ليقرأ العنوان الحقيقيّ في هذه الطوبولوجيا المزدوجة (يُفضّل X-Forwarded-For بعدد قفزات صحيح، أو يتجاهل X-Real-IP المكتوب فوقه). أترك قفل IP مُطفأً حتى يكون لديك عنوان ثابت/VPN.

الجانبالتفصيل
✅ يُصلح 3 معاًقفل IP (يصبح جاهزاً) + rate-limit per-IP حقيقيّ + قفل الدخول per-IP حقيقيّ — تحسين أمنيّ ملموس فوريّ
✅ بلا خطر قفلقفل IP يبقى مُطفأً → لا أحد يُقفَل
⚠️ يلمس كوداًbackend/app/core/rate_limiter.py (نطاق التقوية — مأذون) + ربّما config قفزات · يحتاج اختبار حذِر (يؤثّر على rate-limit/lockout)
⚠️ لا قفل IP بعدطبقة الشبكة لا تُفعَّل الآن (تنتظر عنوانك الثابت)
الجهدمتوسّط: تعديل + اختبار على الاستاجينج المعزول أولاً ثم نشر مُتحقَّق
الإرجاعسهل (تعديل دالّة واحدة قابل للعكس)

لمن يناسب: تريد تحسين rate-limit/قفل-الدخول الحقيقيّ الآن، وتؤجّل قفل IP حتى تجهّز عنواناً ثابتاً/VPN.

هشّ الخيار ٣: أصلِح السلسلة + فعّل القفل الآن على عنوانك الحاليّ

ماذا يحدث: كالخيار ٢ ثم أُفعّل القفل على 217.228.240.34. يعمل الآن — لكن يكسر عند تغيّر عنوانك السكنيّ.

الجانبالتفصيل
✅ دفاع شبكيّ كاملقفل IP فعّال + الإصلاحات الثلاثة
🔴 خطر قفل عالٍعنوانك ديناميكيّ → عند تغيّره (ربّما خلال ساعات/أيّام) تُقفَل خارج لوحة التحكّم وتحتاج break-glass عبر SSH
⚠️ صيانة مستمرّةكلّ تغيّر عنوان = تحديث القائمة + إعادة إنشاء backend
الجهدمتوسّط (كالخيار ٢) + متابعة دائمة
الإرجاعbreak-glass: ADMIN_IP_ALLOWLIST="" عبر SSH (يتطلّب وصول الخادم)
تحذير: هذا الخيار يضع عبئاً تشغيليّاً ومخاطرة قفل متكرّرة بسبب طبيعة عنوانك السكنيّ. لا يُنصَح به إلّا إن كان لديك يقين بثبات العنوان أو وصول SSH دائم سريع.

٨) التوصية + الحالة الآمنة + break-glass

توصيتي: الخيار ② (أصلِح السلسلة فقط) كأفضل توازن — يمنحك تحسيناً أمنيّاً حقيقيّاً فوريّاً (rate-limit + قفل الدخول per-IP) بلا أيّ خطر قفل، ويجعل قفل IP جاهزاً للحظة تحصل فيها على عنوان ثابت/VPN. وإن كان MFA كافياً لراحتك، فالخيار ① سليم تماماً. الخيار ③ لا أنصح به لعنوان ديناميكيّ.
