ما هو موجود ✅

  • Root migration: c648957b778e ← يبني كل شيء من صفر
  • سلسلة كاملة: 180 ترحيل حتى ab20

البند الأول — Stage-2: الحقيقة الكاملة من الكود

كيف يعمل النظام الآن بالضبط

السلوك الحالي عند docker compose up

# docker-compose.yml (مقتطف مُبسَّط)
postgres:
  image: postgres:16-alpine@sha256:4e6e670b...  # vanilla — لا init SQL
  volumes: [pg_data:/var/lib/postgresql/data]    # يحفظ البيانات بين الإعادات

# backend entrypoint.sh
alembic upgrade head   # يُشغَّل في كل بدء تشغيل — آمن (idempotent)
uvicorn app.main:app ...
✅ الوضع الطبيعي الآن: Volume موجودة → postgres تحمّل بياناتها → alembic يرى ab20 already → لا يفعل شيئاً → يبدأ uvicorn.
⚠ الخطر: Volume pg_data تُحذف (down -v، تلف، هجرة خادم) → postgres تبدأ من صفر → alembic يُشغّل 180 ترحيلاً (~40-90 ثانية) → ثم يبدأ الخادم. لا انكسار، لكن تأخير وخطر أثناء النشر الأول.

لماذا السيناريو المؤلم أخطر مما يبدو

# سيناريو: خادم Hetzner يُعاد بناؤه بعد فشل
docker compose down -v   # البيانات تُحذف
docker compose up        # postgres تبدأ من صفر (vanilla image)
# backend يبدأ — entrypoint يُشغّل alembic upgrade head
# 180 ترحيل × 0.5 ثانية = ~90 ثانية فشل في healthcheck
# إذا healthcheck retries = 5 × 5s = 25s → يفشل قبل انتهاء migrations!
# الحل الحالي: backend يُعيد المحاولة تلقائياً بعد restart

المشكلة الحقيقية: start_period=20s في healthcheck backend. إذا 180 ترحيلاً أخذت > 20s، قد يبدأ health-check قبل جاهزية الخادم. هذا مشكلة في الإنتاج خاصة.
