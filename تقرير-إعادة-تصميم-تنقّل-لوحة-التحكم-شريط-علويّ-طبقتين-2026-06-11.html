١. فهم الطلب بدقّة

المطلوب تحويل تنقّل لوحة التحكم (OPS) من شريط جانبيّ عموديّ إلى تنقّل أفقيّ من طبقتين:

  • الطبقة العليا (Tier 1): صفٌّ أفقيّ من أيقونات الأقسام الرئيسيّة في أعلى الصفحة — الرئيسية · الكيانات · الكتالوج والأماكن · المالية · تسويات ومخاطر السائقين · الوثائق والجغرافيا · التحكّم والإطلاق · البيانات والتدقيق · الأمان والإدارة.
  • الطبقة الثانية (Tier 2): عند الضغط على قسم رئيسيّ، يُكشف صفٌّ أفقيّ ثانٍ أسفله يحوي كلّ الأيقونات الفرعيّة لذلك القسم (صفحاته).

هذا النمط يُسمّى عالميًّا «التنقّل الأفقيّ ثنائيّ المستوى» (Two-Level Horizontal Navigation)، وهو في جوهره قريب من «شريط الأوامر السياقيّ» (Ribbon / Contextual Tabs) الذي تستخدمه Microsoft Office.

٣. التصميم المقترح + مخطّطات بصريّة

نقل التنقّل إلى أعلى الصفحة في طبقتين أفقيّتين، وتحرير العرض الكامل للمحتوى:

┌──────────────────────────── top-bar ───────────────────────────────────────┐ │ ⚙️ تووا 🔗 🔔 ⌘K AR │ ├─ Tier 1 · أقسام رئيسيّة (أفقيّ، RTL) ───────────────────────────────────────┤ │ ‹📊 الرئيسية› «🏢 الكيانات» «🍽️ الكتالوج» «💵 المالية» «🧾 السائقون» … ⋯المزيد│ ├─ Tier 2 · عناصر القسم النشط (يُكشف) ────────────────────────────────────────┤ │ 📊 لوحة العمليات 📈 المؤشّرات 🗺️ الأسطول 📤 التوزيع 🔔 الشكاوى 💬 … │ ├─────────────────────────────────────────────────────────────────────────────┤ │ │ │ محتوى الصفحة (.ops-main) — بعرض كامل الآن │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ ‹ › = القسم النشط (مظلَّل) ⋯ = قائمة «المزيد» عند ضيق الشاشة (Priority+)

سلوك التفاعل

  • عند فتح اللوحة: تُحدَّد تلقائيًّا طبقة Tier 2 للقسم الذي تنتمي إليه الصفحة الحاليّة (لا تبدأ فارغة).
  • الضغط على قسم في Tier 1 ⟵ يكشف عناصره في Tier 2 (بحركة سلسة)، ويبقى مظلَّلًا.
  • الضغط على عنصر في Tier 2 ⟵ ينتقل للصفحة، ويبقى القسم مفتوحًا، ويُظلَّل العنصر النشط.
  • القسم النشط = قسم المسار الحاليّ يُظلَّل دائمًا في Tier 1 (تغذية راجعة «أين أنا»).
  • لوحة ⌘K تبقى كمسار سريع للقفز لأيّ صفحة دون فتح قسمها (مكمّل، لا بديل).

٤. أحدث التقنيات والأفكار والأساليب (بحث 2025–2026)

4.1 — التنقّل الأفقيّ ثنائيّ المستوى (Two-Level Horizontal Nav)

أنظمة التصميم المؤسّسيّة (PatternFly · ServiceNow Horizon) توصي: المستوى الأوّل مكشوف دائمًا، والمستوى الثاني إمّا دائم أو يُكشف عند الطلب. القسم الرئيسيّ يأخذ «حالة محدَّد» متى كانت أيّ صفحة فرعيّة بداخله نشطة — وهو بالضبط سلوك Tier 1 المقترح. مناسب عندما تكون الأقسام ثابتة ومعدودة وتريد إبراز الفئات الرئيسيّة أسفل ترويسة الصفحة مباشرة.

4.2 — الشريط السياقيّ / Ribbon (تحديث Office 2025)

«التخطيطات السياقيّة» (Contextual Layouts) في Office 2025: الشريط يتغيّر ديناميكيًّا حسب المهمّة/التحديد فيُظهر الأدوات ذات الصلة فقط، ويقلّل الفوضى. الاتجاه الجماليّ: مسطّح، أنظف، صديق للّمس، مع خيار «العرض الكلاسيكيّ» للرجوع — درس مهمّ: امنح المستخدم تحكّمًا/تفضيلًا.

4.3 — لوحة الأوامر (Command Palette) كمكمّل لا كبديل

النمط السائد 2025: التنقّل المرئيّ (شريط) + لوحة ⌘K للوصول السريع للخبراء. لديكم هذا أصلًا (E6) — يجعل المقايضة «نقرة إضافيّة للوصول للعنصر» مقبولة لأنّ مسار الخبير موجود.

4.4 — قاعدة كثافة العناصر

عدد عناصر التنقّلالتوصية العالميّة
أقلّ من 5الشريط العلويّ هو الأفضل (يوفّر مساحة)
5–10كلاهما يعمل؛ الجانبيّ أسهل مسحًا
كثيرة + تسلسل عميقالجانبيّ تقليديًّا أفضل — إلّا إذا قُسِّمت أفقيًّا
💡 لوحتكم بها 9 أقسام + 62 وجهة — وهو ما يُرجِّح الجانبيّ تقليديًّا. لكنّ نمط الطبقتين الأفقيّ هو الحلّ الذي يمنحك «إحساس الشريط العلويّ» مع إدارة الكثافة: 9 عناصر فقط في Tier 1 دائمًا، وتُكشف عناصر قسم واحد فقط في كلّ مرّة → كثافة مُدارة.

4.5 — ARIA الصحيحة (تحذير مهمّ)

تحذّر W3C/MDN/Level Access: لا تستخدم role="menu"/"menubar" لتنقّل الصفحات — فهي للأوامر التطبيقيّة لا للروابط. لأنّ Tier 1 يكشف لوحة (لا ينتقل)، فالأنسب: Tier 1 = role="tablist" (تبويبات أفقيّة + roving tabindex)، وTier 2 = <nav> + روابط <a> (تنقّل صفحات حقيقيّ). يربطهما aria-controls.

4.6 — التقنيات التنفيذيّة الحديثة

  • Roving tabindex: عنصر واحد tabindex=0 والبقيّة -1؛ تنقّل بـ→ ← Home End (نمط W3C APG للتبويبات).
  • Priority+ Navigation: إظهار ما يسع، وطيّ الفائض في قائمة «المزيد ⋯» تلقائيًّا (لـ9 أقسام على شاشات أضيق).
  • خصائص CSS المنطقيّة (margin-inline, inset-inline) بدل الفيزيائيّة → RTL سليم بلا انعكاس يدويّ.
  • حركة بلا تبعيات: انتقال CSS (max-height/opacity) لكشف Tier 2 — بلا framer-motion (غير موجودة في المشروع)، مع احترام prefers-reduced-motion.

تصميم المكوّن OpsTopNav

// مُشتقّ بالكامل من OPS_NAV_SECTIONS (نفس مصدر الشريط الجانبيّ و⌘K)
state activeKey            // titleKey للقسم المفتوح
const sections = OPS_NAV_SECTIONS
    .map(s => ({...s, items: s.items.filter(it => canAccessOpsPath(it.to, role))}))
    .filter(s => s.items.length > 0)        // قسم بلا عناصر مسموحة ⟵ يُخفى (كالحاليّ)
default activeKey = sectionOf(location.pathname) ?? sections[0].titleKey
                  // + يُسترجَع من localStorage("ops_nav_section")
Tier1: <div role="tablist"> <button role="tab" aria-selected aria-controls="ops-subnav"> لكلّ قسم
Tier2: <nav id="ops-subnav" aria-label="عناصر {القسم}"> <NavLink> لعناصر القسم النشط

الحالة والاستمراريّة

  • activeKey يبدأ من قسم المسار الحاليّ (خريطة path → section مبنيّة من opsNav)، أو من آخر قسم محفوظ في localStorage.
  • عند التنقّل لصفحة من قسم آخر (مثلًا عبر ⌘K)، يتبع Tier 2 القسم الجديد تلقائيًّا.

٧. الاستجابة · التحميل الزائد · RTL · الجوّال

  • تحميل زائد (9 أقسام): نمط Priority+ — تُعرض الأقسام التي تسع، ويُطوى الفائض في «المزيد ⋯». بديل أبسط: تمرير أفقيّ لصفّ Tier 1.
  • RTL: خصائص منطقيّة فقط؛ تدفّق الأقسام يمين⟶يسار؛ قائمة «المزيد» تُفتح في الاتجاه الصحيح؛ مراعاة أنّ النصّ العربيّ أطول 20–30% فلا عرض ثابت للعناصر.
  • الجوّال/اللوحيّ: خياران (يُحسَم في §٨): (أ) صفّان قابلان للتمرير الأفقيّ، أو (ب) Tier 1 فقط ثمّ Tier 2 كقائمة منسدلة، مع الاعتماد على ⌘K كمسار سريع. توصية: تمرير أفقيّ على اللوحيّ + كشف منسدل على الهاتف.
  • المساحة العموديّة: الطبقتان تستهلكان صفّين؛ يمكن إخفاء Tier 2 تلقائيًّا عند التمرير لأسفل لإعادة المساحة للجداول.

٨. خيارات قرار للمالك (قبل البناء)

قرار A — آليّة الكشف موصى به: «بالضغط»
بالضغط (ثابت للقسم النشط، نمط Ribbon) — أوضح وأصدق للمس وأفضل وصوليًّا · مقابل بالمرور (hover) — أسرع لكنّه ضعيف على اللمس والوصوليّة
قرار B — هيئة Tier 1
أيقونة + نصّ (موصى به للوضوح) · أم أيقونة فقط مع tooltip (أوفر للمساحة، أصعب للمستخدم الجديد)؟
قرار C — Tier 2 عند فتح اللوحة
مكشوف تلقائيًّا لقسم الصفحة الحاليّة (موصى به) · أم مطويّ حتّى يضغط المستخدم قسمًا؟
قرار D — تفضيل المستخدم
إبقاء خيار «العودة للشريط الجانبيّ» (كـOffice «العرض الكلاسيكيّ») كتبديل محفوظ؟ أم استبدال كامل؟
قرار E — سلوك الجوّال
تمرير أفقيّ للصفّين · أم Tier 1 + منسدلة لـTier 2؟ (مع بقاء ⌘K)

١٠. خطة مراحل + بوّابات التحقّق

  1. م1 — المكوّن: بناء OpsTopNav (Tier 1 tablist + Tier 2 nav) من OPS_NAV_SECTIONS، مفلتر بالدور، افتراض قسم المسار، حركة CSS بلا تبعيات.
  2. م2 — الدمج: ربطه في Layout (استبدال الجانبيّ)، تعديل .ops-body/CSS لعرض كامل، إبقاء ⌘K.
  3. م3 — الاستجابة: Priority+ «المزيد» + سلوك الجوّال (قرار E) + RTL + prefers-reduced-motion.
  4. م4 — الحالة: الاستمراريّة (localStorage) + تظليل القسم/العنصر النشط في الطبقتين + (اختياريّ) تبديل «الشريط الكلاسيكيّ» (قرار D).
  5. م5 — التحقّق: تحديث اختبارات Layout + اختبارات OpsTopNav + بوّابات tsc 0 lint 0 build Vitest ثمّ نشر وتحقّق حيّ بالصور (62 مسارًا 0-مكسور · فلترة الدور · الطبقتان).
صفر تغيير خلفيّ · بلا migration · بلا مساس بـFIN-COR (واجهة بحتة). يبقى مصدر opsNav.ts ولوحة ⌘K دون تعديل جوهريّ.

الخلاصة

النمط المطلوب (شريط علويّ من طبقتين) مدعوم عالميًّا ومتوافق مع أنظمة التصميم المؤسّسيّة والـRibbon الحديث. التنفيذ مُجدٍ ونظيف على بنيتكم: يُعاد استخدام OPS_NAV_SECTIONS وcanAccessOpsPath دون منطق جديد، بلا تبعيات (لا Tailwind ولا framer-motion)، مع وصوليّة سليمة (tablist + nav) و RTL منطقيّ، ولوحة ⌘K تبقى مسارًا سريعًا مكمّلًا. هذا تقرير/خطة — لم يُبنَ شيء؛ بانتظار موافقتك على القرارات A–E ثمّ أبدأ بالمراحل م1→م5.
