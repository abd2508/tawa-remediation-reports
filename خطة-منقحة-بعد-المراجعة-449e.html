١. ملخّص المراجعة — ماذا تَغيّر؟

🔑 الاكتشاف الأهمّ: الـrootcause لـP0-1 (accept_timeout sweep failure) أَعمق ممّا ظَننّا: الـSSE handlers (7 منها في الـrepo) يَفتحون AsyncSessionLocal داخل streams طويلة. عند انقطاع العميل، CancelledError يُلغي coroutine، لكنّ get_db() لا يَفعل rollback في finally → asyncpg connection يَبقى aborted في pool → كل background job يَستعيره يَفشل.

الإصلاح المُقترَح في 449d (pool منفصل للـsweep) يَحلّ الأعراض فقط. الحلّ الجذريّ يَحتاج: (أ) تَعديل get_db() ليَفعل rollback، (ب) تَعديل SSE handlers لإغلاق الـsession قبل بدء stream الطويل، (ج) pool منفصل للـbackground (دفاع في العمق).
🎯 الاكتشاف الثاني الأهمّ: الـrootcause لـP0-3 (wallet topup 500) مَزدوج:
  1. الـbackend يَفشل بـ500 بدل 422 (السبب المعلوم في الخطّة)
  2. الجزء الجديد: GET /customer/me يُرجع user_id (لا id)! الـsim D2 فعل customer_id = me.get("id") → None → fallback "self" → FK violation → 500. هذا نفسه عيب M11 (API contract drift) الذي صَنّفناه P2. إنّه P0 لأنّه يَكسر مَسار wallet كامل.
🚨 ثلاثة بنود تَحتاج إعادة تَخطيط جوهريّ:
  • W3-1 (H2): الـdiff في الخطّة يَستخدم item.base_price_minor — هذا الحقل غير موجود في CatalogItem (السعر على ItemVariant.base_price). الكود المُقترَح يَفشل بـAttributeError. + اكتشاف منفصل: GET /providers/{id}/catalog العام لا يَفلتر بـprovider.status ⇒ مُزوّد PENDING بصنف PUBLISHED يَظهر علناً (تَسرّب مُختلف عمّا ظَننّا).
  • W3-4 (H8): الـquery الذي اقترحناه إصلاحه في /operations/dashboard — هذا الـendpoint لا يُرجع pending_onboarding أصلاً. الحقل في /operations/kpi (سطر 1190) والـquery يَستخدم Provider.status='PENDING' فقط (يَفوت السائقين كاملاً).
  • W4-4 (M11): «backward-compatible» مع تَحويل detail:[] → envelope مُتناقضان. اختبارات قائمة تَفحص detail[0] ستَنكسر. الحلّ: إبقاء detail تَحت details في الـenvelope.
❌ بَندان يُلغيان (مُنفَّذان فعلاً):
  • W5-2 (M5): شَرح delivery_handoff_code — مُنفَّذ بالفعل عبر مكوّن HandoffCodeCard الموجود (لكن D1 لم تَره ربّما لأنّ الطلب لم يَصل EN_ROUTE). يَجب التَّحقّق لماذا لم يَظهر بدل إعادة بنائه.
  • W6-4 (M9): endpoint عام للشكاوى — موجود فعلاً عبر POST /support/sessions (مرحلة 151). لا حاجة لـmigration aa17 لـnullable order_id.
💡 عيب جديد كَشفته المراجعة (يَحتاج موجة جديدة): 5 تَعريفات مختلفة لـclass ValidationError عبر الـapp + make_localized_error() كُتب ولم يُستخدَم + middleware Idempotency يَنطبق على 4 مَسارات فقط من ~150 POST. هذه «hardening عَرضيّ» تَحتاج موجة W0 (دفاع في العمق) منفصلة.

٣. 7 أسئلة قرار قبل أن أُنفّذ

س-1 (P0-1 root cause): هل أَعمل الإصلاحات الـ3 معاً (pool منفصل + get_db rollback + SSE session-close مبكر) أم فقط pool منفصل (الأقلّ مخاطرة لكن لا يَحلّ السبب)؟
س-2 (Wallet semantics): هل العميل يَستطيع شَحن محفظة شخص آخر (مثل والده)؟ أم الـsemantic «شَحن محفظتي فقط»؟
توصيتي: CUSTOMER → self فقط، SUPER → أيّ شخص. تَوافق؟
س-3 (Catalog price model): اكتشاف D-3: السعر على ItemVariant لا CatalogItem. هل نُحدّد «الصنف منشور = على الأقلّ variant واحد بـbase_price > 0»؟ أم نُضيف base_price_minor لـCatalogItem كـmigration؟
توصيتي: الأوّل (لا migration، يَتّفق مع تَصميم الـvariants).
س-4 (KPI pending): هل نَدمج DRIVER + PROVIDER في رقم واحد، أم نُعطي 3 أرقام منفصلة (pending_providers, pending_drivers, pending_documents)؟
توصيتي: 3 أرقام منفصلة + إجمالي (أوضح للمشرف).
س-5 (Mobile 308): إصلاح Dio mobile لاتّباع 308 يَحتاج commit في mobile_app. هل نَفعل aliases على الـbackend فقط (يَكسر mobile) أم نُؤجّلها حتى نُحدّث mobile معاً؟
توصيتي: aliases تَعمل لـweb + curl، mobile يَستخدم paths صحيحة من بداية اليوم → آمن.
س-6 (W5-2 handoff code): مُنفَّذ فعلاً عبر HandoffCodeCard. لماذا لم يَره D1؟ نَتحقّق أوّلاً قبل إلغائه أم نَحذفه من الخطّة؟
توصيتي: نَتحقّق (sim ثانٍ يَصل EN_ROUTE)، الأرجح أنّه يَعمل ولم تَرَه D1 لأنّ الطلب لم يَتجاوز AWAITING_PROVIDER.
س-7 (Address phone): Address model لا يَحوي phone أصلاً. هل نُضيفه بـmigration (لكلّ عنوان رقم بديل) أم نَستخدم customer.phone فقط؟
توصيتي: إضافة phone nullable على Address (سياق طرابلس: يَطلب من المنزل ويُريد رقم زوجته للسائق).

W1-1 المُنقَّح · إصلاح accept_timeout sweep إعادة تَخطيط

🚨 تَغيّر جذريّ: الإصلاح الأصلي (pool منفصل) يُعالج الأعراض. الحلّ الكامل يَحتاج 3 طبقات:

الطبقة 1 (السبب الجذريّ في get_db):

async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
async def get_db():
    async with AsyncSessionLocal() as session:
        try:
            yield session
        except BaseException:  # incl. CancelledError, GeneratorExit
            await session.rollback()
            raise

الطبقة 2 (SSE handlers — 7 ملفّات): فَصل auth check (session قصيرة) عن stream (لا session). نَمَط:

async def stream_endpoint(...):
    # short-lived session for auth check ONLY
    async with AsyncSessionLocal() as auth_db:
        order = await auth_db.get(Order, order_id)
        if order is None:
            return Response(404)
        # validate ABAC, then RELEASE session
    # stream loop uses Redis only (no session held)
    return StreamingResponse(_redis_subscribe_loop(...))

الطبقة 3 (دفاع في العمق — sweep pool منفصل):

from sqlalchemy.pool import NullPool
sweep_engine = create_async_engine(
    settings.database_url, pool_pre_ping=True, poolclass=NullPool,
)
SweepSessionLocal = async_sessionmaker(sweep_engine, ...)
# الـsweep يَستخدمه:
async with SweepSessionLocal() as db:
    try:
        ...
    except InFailedSQLTransactionError:
        await db.rollback()
        continue

الملفّات: backend/app/db/session.py · backend/app/modules/sse/{order_tracking,provider_stream,fleet_stream,sse_router}.py · backend/app/main.py

⚠ مخاطر: 7 SSE handlers تَحتاج تَعديل + 3 background loops يَجب تَحويلها لـSweepSessionLocal. لكنّ الطبقة 1 وحدها تَكفي للـPOST/PUT (90% من الطلبات).
✓ القبول: 0 InFailedSQLTransactionError في logs ساعة كاملة بعد النشر + tests stress: 100 SSE connect/cancel متوالية لا تَفسد الـpool.
⏱ تَقدير مُحدَّث: 1.5 ساعة (كان 30 دقيقة) — بسبب 7 SSE handlers + اختبارات stress.

W1-3 المُنقَّح · إصلاح wallet topup 500 إضافة جوهريّة

✓ topup ينجح / لا 500 ضدّ user غير موجود (422) / CUSTOMER لا يَستطيع شَحن شخص آخر (403) / `/customer/me` يَحوي id + user_id.
