٢) لماذا أُجِّل كل ذلك؟ (شرح دقيق لكل بند)

البند المؤجَّلالسبب الدقيقالتصنيف
⑤أ نسبة الالتفاف (detour-ratio)أُنجِز الأساس (مرشّح الاتّجاه الذي يُصلح «الاتّجاهين المتعاكسين»). نسبة الالتفاف تُضيف نداء شبكة غير-متزامن (OSRM) داخل مسار التوزيع الحيّ → تحتاج تحقّقاً تحت حِمل قبل إثقال المسار الحرِجتحسين مؤجَّل
⑤أ إعادة فحص المنطقة المُعلَّقة وقت التجميععَرَض جانبيّ صغير كشفه التدقيق (الفحص عند الإنشاء فقط) — ضُمّ مع نسبة الالتفافتحسين مؤجَّل
⑤ب VROOM + تداخل الهندسةيحتاج خادم VROOM قائماً + بناء بيانات خرائط ليبيا (OSRM) — بنية يُجهّزها المشغّل؛ لا تُبنى بدونهامحجوب-بنية
⑤ج تعدّد المزوّدينمحجوب بعيب FIN-COR حقيقيّ: حدّ نقد السائق تنبّؤ لا حجز (create_offer يقرأ النقد بلا FOR UPDATE). نشره قبل إصلاح حجز النقد + قفل صفّ السائق قد يجعل السائق يتجاوز الحدّ النقديّ → خطر ماليّمحجوب-ماليّ/حِمل
⑤د شاشة متعدّدة المحطّاتتحتاج migration (batch_sequence) + تعديل تطبيق الموبايل — كلاهما منطقة محظورة تتطلّب إذنكمحجوب-منطقة-محظورة
الإكرام الرقميّ بعد التسليملا يوجد endpoint بقشيش بعديّ أصلاً + الدفع الإلكترونيّ مُبوَّب (production_payment_enabled=false) → بناء مسار يحرّك مالاً يخالف بوّابة الدفع. اليوم تذكير نقديّ فقطمحجوب-دفع
اختبارات pytest الخلفيّةحاوية الإنتاج بلا pytest والبيئة المحلّيّة تنقصها deps → تحقّقتُ بـفحص منطق مباشر + endpoints حيّة بدلاً منهاقيد بيئيّ
الجوهر: لم أؤجّل شيئاً اعتباطاً — كل بند مؤجَّل إمّا (أ) محجوب بعيب ماليّ يجب إصلاحه أوّلاً (تعدّد المزوّدين)، أو (ب) يحتاج بنية خارجيّة (VROOM/OSRM)، أو (ج) منطقة محظورة (migration/موبايل) تتطلّب إذنك، أو (د) محجوب ببوّابة الدفع المختومة (الإكرام الرقميّ). الباقي تحسينات تحتاج اختبار حِمل.

٣) لماذا لا تظهر كل التعديلات؟ وأيقونة الخريطة

السبب الرئيس: كاش الـPWA (Service Worker)

🟦 التطبيق ويب-تقدّميّ (PWA) فيه service worker يُخزّن النسخة القديمة ويخدمها حتى يُحدّث نفسه. فبعد أيّ نشر، ترى الواجهة القديمة حتى يحدث تحديث فعليّ — لذلك «لا تظهر كل التعديلات» فوراً. (أكّدتُ وجود sw.js على الإنتاج.)
لماذا تبقى القديمة: متصفّحك ──► service worker (sw.js) ──► يخدم الأصول المخزّنة (القديمة) حتى: إعادة تحميل / تحديث قسريّ → يجلب الجديد الحلّ: Ctrl+Shift+R أو إغلاق التطبيق وفتحه مرّتين أو مسح بيانات الموقع

أيقونة الخريطة تحديداً

الدورهل توجد أيقونة خريطة؟السبب
العميللا — بالتصميمتبويب الخريطة في شريط السائق السفليّ فقط (الخطة جعلته للسائق، لا العميل)
السائقنعم — موجودة ومنشورة/driver/map في الـJS المنشور على الإنتاج (chunk) + الأيقونة في Layout.tsx شريط السائق

إن لم تظهر للسائق عندك، فهو الكاش أعلاه: حدّث قسريّاً وادخل بحساب سائق → تظهر «الخريطة» في الشريط السفليّ بين «الرئيسية» و«سجلّي».

٤) السوبر أدمين الدائم — أُنشئ ومُتحقَّق ✅

البندالقيمة
اسم المستخدمadmin
كلمة المرورadmin
الدور · المُعرِّفSUPER_ADMIN · id 88a35dcf… · ACTIVE
الدخول من الواجهةصفحة الدخول → حقل المُعرِّف: admin + كلمة المرور: admin → يوجّهك مباشرةً إلى لوحة التحكم (/ops/admin/accounts)
الدوامصفّ دائم في قاعدة بيانات الإنتاج + سكربت backend/scripts/seed_super_admin.py (أصلحتُ القديم المكسور) قابل لإعادة التشغيل

كيف أُنجِز (الجذر التقنيّ)

معالِج الدخول (registration_router.py:770-784) يحلّ المُعرِّف: فيه "@" → بحث بـ User.email هاتف/+218… → normalize_phone → بحث بـ User.phone غير ذلك → بحث بـ User.username ← "admin" يقع هنا │ ▼ أنشأتُ User: username="admin" · password_hash=bcrypt("admin") · status=ACTIVE + Role: SUPER_ADMIN · ACTIVE │ ▼ login admin/admin → توكن role=SUPER_ADMIN → RoleHomeRedirect → /ops/admin/accounts

لماذا bcrypt مباشرةً؟ حدّ المنصّة 8 أحرف يرفض «admin» (5 أحرف) عبر hash_password، لكن verify_password (bcrypt.checkpw) لا يفحص الطول → التهشير المباشر يعمل ويتطابق عند الدخول.

التحقّق الحيّ على الإنتاج

# POST /auth/login (admin/admin)
role في التوكن: SUPER_ADMIN
GET /control-panel/customers   = 200
GET /operations/users/search   = 200

المُلفّ القديم seed_super_admin.py كان مكسوراً (يكتب أعمدة users.role/role_status التي حُذِفت بعد نقل الأدوار لجدول roles منفصل) — استبدلتُه بنسخة صحيحة تستخدم نماذج ORM الحاليّة.

٥) ردّ مراجعة الأمان الآليّة

رصدت المراجعة الآليّة: [CRITICAL] بيانات اعتماد افتراضيّة ضعيفة في seed_super_admin.py (admin/admin).

الموقفالتفصيل
السبب المقبول للمتابعة (من إرشادات المراجعة نفسها)«المستخدم طلبها صراحةً وقد عرضتَ المقايضات الأمنيّة» — وكلاهما متحقّق: طلبتَ admin/admin صراحةً، وعرضتُ التحذير CRITICAL + توصية التقوية في ردّي السابق
ما حسّنتُه استجابةًجعلتُ بيانات الاعتماد قابلة للتجاوز عبر متغيّرات بيئة (SUPER_ADMIN_USERNAME/PASS/PHONE) مع بقاء admin/admin افتراضيّاً → التقوية تصير أمراً واحداً بلا تعديل كود
ما لم أُغيّره (عمداً)لم أفرض كلمة مرور قويّة إلزاميّة (كان سيكسر طلبك). وثّقتُ سبب تجاوز حدّ الطول
⚠️ التحذير الأمنيّ قائم: admin/admin لـSUPER_ADMIN على خادم مكشوف للإنترنت = خطر جسيم (تحكّم ماليّ كامل لمن يخمّنه). أنصح بشدّة بتغيير كلمة المرور أو تقييد لوحة التحكم بـIP/VPN قبل أيّ إطلاق عامّ. القرار قرارك، والخطر مكشوف لك بوضوح.

٦) كيف تدخل + كيف تُقوّي لاحقاً

الدخول الآن

  • افتح صفحة تسجيل الدخول على tawanow.com (إن لم تظهر التعديلات: تحديث قسريّ Ctrl+Shift+R أوّلاً).
  • حقل المُعرِّف: admin · كلمة المرور: admin → يدخلك مباشرةً لوحة التحكم.

تقوية كلمة المرور لاحقاً (أمر واحد، بلا تعديل كود)

docker exec tawa-backend-core-1 sh -c \
  'cd /app && SUPER_ADMIN_PASS="<كلمة-قويّة-طويلة>" python backend/scripts/seed_super_admin.py'

السكربت idempotent — يُحدّث نفس الحساب «admin» بكلمة المرور الجديدة فوراً (والاسم يبقى admin، أو غيّره بـSUPER_ADMIN_USERNAME).
