إصلاح nginx.conf — Cache-Control الصحيح

إصلاح بنيوي ملف واحد

المشكلة الحالية

الـnginx.conf الحالي (مقتطف مهم)

location / {
    try_files $uri $uri/ /index.html;
    # ← لا يوجد Cache-Control هنا أبداً
    # ← Cloudflare يرى: لا تعليمات → يخزّن 4 ساعات
}

sw.js و index.html يقعان تحت location / — بلا توجيهات cache.

الحل المطلوب

ما يجب إضافته (3 location blocks)

# 1. sw.js — لا تخزين أبداً (critical!)
location = /sw.js {
    add_header Cache-Control "no-store, no-cache, must-revalidate";
    add_header Pragma "no-cache";
    try_files $uri =404;
}

# 2. index.html — يتحقق دائماً
location = /index.html {
    add_header Cache-Control "no-cache, no-store";
    try_files $uri =404;
}

# 3. الـassets المُهشَّشة — كاش دائم
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

🧠 سيناريوهات ذهنية (ماذا سيحدث إذا...)

✅ سيناريو 1 (الصحيح)
المستخدم يفتح الموقع بعد النشر → browser يطلب sw.js → nginx يرد بـno-store → Cloudflare لا يخزّن → المستخدم يحصل على sw.js الجديد فوراً → Workbox يكتشف التحديث → يظهر banner "تحديث متاح".
⚠️ سيناريو 2
نضيف no-store لـsw.js لكن نسينا index.html → browser يخزّن index.html قديم → sw.js الجديد يُعمل لكن يقرأ revision من index.html القديم → لا اكتشاف تحديث. الحل: يجب إضافة كلاهما معاً.
❌ سيناريو 3 (خطأ شائع)
نضيف no-store لـ/assets/ بدل immutable → كل مستخدم يُعيد تحميل كل ملف JS كبير في كل زيارة → ضغط شبكة ضخم + بطء واضح. يجب immutable للـhashed files فقط.
⚠️ سيناريو 4 — Cloudflare Page Rules
حتى لو أضفنا no-store في nginx، إذا كان هناك Cloudflare Page Rule يُجبر cache → يُلغي الهيدر. يجب التحقق من لوحة Cloudflare أن لا قواعد تُعيق sw.js.
✅ سيناريو 5 — أول زيارة بعد الإصلاح
مستخدم يفتح الموقع للمرة الأولى بعد الإصلاح → sw.js الجديد يُسجَّل فوراً → يُعمل في الخلفية → يُحضر الأصول الجديدة → عند إعادة الفتح يُفعَّل تلقائياً.
❌ سيناريو 6 — المستخدمون القديمون
مستخدمون عندهم sw.js قديم مُسجَّل + Cloudflare خزّنه → حتى بعد الإصلاح، Cloudflare قد يُعيد sw.js القديم من الكاش لمدة 4 ساعات إضافية. الحل: Purge Cloudflare cache لـ/sw.js عند كل نشر.

⚠️ الأعراض الجانبية للإصلاح

🟡 زيادة طلبات الشبكة لـindex.html (كل زيارة = طلب شبكة) — لكن الفائدة تفوق التكلفة بكثير. الملف صغير (كيلوبايت قليلة).
🟢 الـassets المُهشَّشة (main-xxx.js) ستُخزَّن إلى الأبد = أسرع تحميل للزيارات اللاحقة.
🔴 خطر: إذا أضفنا Cache-Control headers داخل location / مع headers عامة موجودة (مثل X-Frame-Options) → التعارض ممكن. يجب استخدام location = (exact match) لـsw.js و index.html للحصول على أعلى أولوية.

🧠 100+ سيناريو ذهني — منتخبات

❌ SIM-1: ضغط مزدوج
موظف يضغط Off-Shift مرتين متتاليتين بسرعة → يُرسل طلبين POST → Backend idempotent (يضع is_off_shift=true مرتين) = لا خطر. لكن الـUI يجب disable الزر أثناء الطلب لمنع ضغطة ثانية.
⚠️ SIM-2: انقطاع الشبكة
موظف يضغط Off-Shift → شبكة تنقطع → لا response → الـUI يظل يقول "في الخدمة" لكن الـbackend قد أُرسل أو لا. الحل: optimistic update مع rollback عند الخطأ.
✅ SIM-3: آخر موظف
موظف آخر موجود + هذا آخر واحد يضغط Off → backend يُوقف الطلبات (intake_auto_stopped: true) → الـUI يُظهر: "تم إيقاف استقبال الطلبات تلقائياً. المالك يحتاج إعادة التفعيل."
❌ SIM-4: عودة بعد إيقاف cascade
موظف يعود للخدمة (on-shift) لكن intake_restorable: true → إذا لم نُخبر المستخدم بذلك، يظن أن الطلبات عادت لكنها لم تعد. يجب banner يقول "عدت للخدمة. الطلبات لا تزال موقوفة — يجب على المالك إعادة التفعيل."
⚠️ SIM-5: مالك يرى الموظف off-shift
المالك لا يرى حالة الوردية للموظفين في قائمة الموظفين حالياً. يجب إضافة is_off_shift كعلامة في ProviderStaff.tsx.
✅ SIM-6: طلب جديد والموظف off-shift
طلب جديد يأتي → النظام يوزّعه تلقائياً → موظف off-shift لا يحصل عليه (distribution_service.auto_assign_order تتجاهله). هذا يعمل بدون أي تغيير frontend.
❌ SIM-7: تسجيل الخروج أثناء off-shift
موظف يُغادر الوردية ثم يُسجّل خروج دون العودة → في جلسته القادمة، my-profile سيظل يقول is_off_shift: true. الـUI يجب أن يقرأ الحالة من الـAPI عند كل تسجيل دخول.
⚠️ SIM-8: موظف معلّق يحاول off-shift
الـbackend يرفض (403) لأن require_provider_permission يتحقق من الـsuspension. الـUI يجب إظهار رسالة واضحة بدل خطأ 403 خام.
✅ SIM-9: SSE يُحدّث الحالة
بعد off-shift، النظام يُرسل SSE event → Dashboard يُحدّث عدد الموظفين النشطين فوراً (بدون refresh).

🧠 سيناريوهات ذهنية

✅ SIM-1: أرشفة إشعارات غير مقروءة
API يُؤرشف فقط المقروءة (status=READ). إذا المستخدم ضغط أرشفة وعنده إشعارات غير مقروءة → هذه تبقى في الجرس. Response يعطي archived_count الفعلي → الـUI يُحدّث العداد.
❌ SIM-2: ضغط أرشفة على جرس فارغ
لا إشعارات مقروءة → archive-day يُعيد {archived_count: 0} → يجب عدم إظهار toast "تمت الأرشفة" لأن لا شيء أُرشف. الـUI يتحقق من الـcount أولاً.
⚠️ SIM-3: تزامن tabs متعددة
مستخدم له tab1 و tab2 مفتوحتين. يُؤرشف من tab1 → tab2 لا يزال يُظهر الإشعارات القديمة. الحل: invalidate React Query cache عند focus الـwindow.
✅ SIM-4: pagination الأرشيف
أرشيف ضخم (200 إشعار) → نطلب 20 في المرة → زر "تحميل المزيد" يُرسل طلب بـoffset=20 → نُضيف للقائمة. تُتجنب pagination ذات أعداد لأنها تتطلب COUNT() ثقيل.
❌ SIM-5: إشعارات في الأرشيف بدون order_id
بعض الإشعارات (system notifications) ليس لها order_id. الـUI يجب التعامل مع order_id: null → لا يُعرض رابط "عرض الطلب".
⚠️ SIM-6: تقادم الإشعارات
الإشعارات القديمة جداً (6+ أشهر) قد تكون كثيرة. نقترح في المستقبل: soft-delete بعد 90 يوم. حالياً لا حذف (by design: "soft-archive, never delete").

🟡 إضافة Tab "الأرشيف" يزيد حجم الـpanel dropdown. يجب اختبار على موبايل (شاشات 360px).

API يُرسل notification للمزوّد (catalog.item_ops_paused event). الـbackend يُرسل تلقائياً.
❌ SIM-4: إيقاف منتج غير موجود
item_id خاطئ → 404. الـUI يجب معالجة هذه الحالة.
⚠️ SIM-5: تكرار الإيقاف (idempotent)
OPS agent يضغط pause مرتين → backend يُحدّث الـreason فقط (ليس idempotent كلياً — يُعيد الرد بحالة جديدة). الـUI يجب disable الزر بعد أول ضغطة.
✅ SIM-6: استئناف يُعيد الحالة السابقة
منتج كان PUBLISHED → أُوقف → استُؤنف → يعود PUBLISHED. منتج كان DRAFT → أُوقف → استُؤنف → يعود DRAFT. ops_pause_prev_status يحفظ هذا.

الأعراض الجانبية

🔴 خطر: الـops_paused_at يمنع المزوّد من التعديل على المنتج. يجب الحرص على إضافة تعليق واضح في ProviderCatalog.tsx عند رؤية منتج مُقفَّل.
🟡 يجب إضافة مسار (route) جديد في لوحة OPS للوصول لهذه الوظيفة.
🟢 الـgrandfathering migration (ab14) أعطى الموظفين الحاليين صلاحية provider_catalog:manage — لا انقطاع.

🧠 سيناريوهات ذهنية

❌ SIM-1: اسم أقل من 3 كلمات
مدخل: "محمد علي" → backend يرفض (422) لأن validation يشترط ثلاثي. الـUI يجب Validate client-side قبل الإرسال: name.trim().split(/\s+/).length >= 3
⚠️ SIM-2: ضغط مزدوج خلال 30 يوم
المستخدم يُغيّر الاسم اليوم، ثم يحاول غداً → 409 مع next_allowed_at. الـUI يُظهر التاريخ المحدد بشكل جميل.
✅ SIM-3: تحديث فوري في الـUI
بعد نجاح التغيير → invalidate user profile query → الاسم يتحدث في الـnavbar/header فوراً دون refresh.
❌ SIM-4: أحرف خاصة أو رموز
مدخل: "محمد 123 أحمد" → يجب رفضه (الـbackend يُطبّق regex). الـUI يوضح: "الاسم يجب أن يحتوي على أحرف فقط."
✅ SIM-5: أول مرة (لا cooldown)
مستخدم جديد last_name_change_at = null → يمكنه التغيير فوراً. الـUI لا يُظهر أي قيود.
⚠️ SIM-6: الاسم يظهر في سجل الطلبات
الطلبات القديمة ستبقى بالاسم القديم (إنها سجل تاريخي). الطلبات الجديدة ستحمل الاسم الجديد.

الأعراض الجانبية

🟢 لا تأثير على الطلبات القديمة — الاسم مُخزَّن في الطلب نفسه وليس مرجعاً.
🟡 تحديث full_name يُعدّل أيضاً display_name في الـbackend — يجب أن يُعكس في كل مكان يُستخدم فيه display_name.
🔴 لا يوجد Audit trail للتغييرات في الـfrontend — لكن الـbackend يُسجّل في audit log.

❌ SIM-1: طلبان متزامنان
مزوّد يضغط تغيير الاسم مرتين بسرعة → backend يرفع IntegrityError (partial unique index uq_name_change_pending) → يُعيد 409 مع الطلب الموجود. الـUI يجب disable الزر فوراً.
⚠️ SIM-2: رفض OPS بدون سبب
OPS agent يرفض دون سبب → يجب على الـUI إلزام إدخال سبب قبل الإرسال. ثم المزوّد يرى السبب ويُصحّح.
✅ SIM-3: موافقة OPS
OPS يوافق → backend يُحدّث provider.business_name مباشرةً + يُرسل notification للمزوّد. الـUI في جهة المزوّد يتحدث (invalidate profile query).
❌ SIM-4: اسم مكرر مع مزوّد آخر
مزوّد يطلب اسماً موجوداً لمزوّد آخر → هذا يُحدّد في مرحلة المراجعة اليدوية من OPS (لا validation تلقائي). OPS مسؤول عن التحقق يدوياً.
⚠️ SIM-5: تغيير بدون approval flag
إذا name_change_require_approval=false في config → التغيير مباشري. الـUI يجب التعامل مع الحالتين: المباشر (يُعرض الاسم الجديد فوراً) والـpending (يُعرض حالة انتظار).
✅ SIM-6: السائق (DRIVER)
نفس الـworkflow لكن عبر PATCH /drivers/me بـfull_name. الـfrontend في DriverSettings.tsx يُعامَل بنفس الطريقة.

الأعراض الجانبية

🔴 إذا OPS لا يُراجع الطلبات في الوقت المناسب، المزوّد يظل في حالة "انتظار" إلى الأبد. يجب SLA داخلي (مثلاً 24 ساعة).

✅ SIM-2: تحديث التقييم

⚠️ SIM-4: نجوم 0 أو 6

⚠️ SIM-5: حذف موظف بعد التقييم
