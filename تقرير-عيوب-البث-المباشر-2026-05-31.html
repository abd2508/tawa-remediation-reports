1) BUG-W-01 — تَعبئة المحفظة فوريّة بلا بوّابة دفع 🔴 CRITICAL

المصدر: backend/app/modules/payments/wallet_service.py:98-148 · web/src/pages/customer/WalletPage.tsx:88

ما يَحدث الآن (كما لاحظ المالك)

"المحفظة تعبأ مباشرة بمجرد وضع نقدي وتكتب المبلغ فيعبأ كيف هذا؟"

كَشفت لقطة الشاشة الثالثة سجلّ المعاملات يَتضمَّن:

  • 📤 شحن المحفظة — 2:31:16 PM
  • 📥 دفع طلب · HELD — 2:33:32 PM (بعد دقيقتين فقط)

أي العميل شَحَن، ثم اشترى فوراً — بلا أيّ عملية دفع خارجيّة بَينهما.

السبب الجذريّ في الكود

دالّة WalletService.topup_wallet:

async def topup_wallet(self, beneficiary_user_id, amount_minor, source_method, ...):
    wallet = await self._get_or_create_wallet(beneficiary_user_id)
    # … سجلّ WalletTopup + Idempotency …
    wallet.balance_minor += amount_minor    # ← يَزيد الرصيد فوراً
    await ledger.record_wallet_topup(...)   # ← قَيد دفتر متوازن

الـroute:

POST /wallets/topups          # CUSTOMER فقط
  → فحوصات: velocity_check + wallet_otp_gate + wallet_session_token
  → ثم: زيادة الرصيد + قَيد دفتر
  → استجابة 201

كلّ الفحوصات قبل الزيادة هي فحوصات هويّة وسرعة — لا تَتحقّق أبداً أنّ المال وَصل فعلاً للمنصّة. لا توجد:

  • أيّ نداء لبوّابة دفع (PSP) — تحقّقتُ بـgrep -rn "psp\|gateway\|edfa\|plutu\|tlync\|sadad\|moamalat" في backend/app/modules/payments/ — صفر مطابقات.
  • لا حقل external_transaction_id أو provider_reference مَطلوب.
  • لا webhook استلام تأكيد خارجي.
  • لا حالة PENDING_VERIFICATION للتعبئة — تَبدأ SUCCEEDED.

ما يَقوله FIN-COR

في contracts/feature_flags.yaml:

production_payment_enabled: false   # Until Legal + Sandbox gate
wallet_cash_out: false              # PERMANENTLY DISABLED
wallet_peer_transfer: false         # PERMANENTLY DISABLED

العَلَم production_payment_enabled مَقصود به أن يَحجب الدفع الإنتاجيّ — لكنّ topup_wallet لا يَستشيره. النتيجة: المحفظة تَعمل في «وَضع وَهميّ» على بيئة الإنتاج.

الأثر

  • أيّ عميل يَستطيع منح نفسه رصيداً غير محدود (مُقيَّداً فقط بـ velocity threshold ≈ 300 د.ل لكلّ فترة).
  • الطلبات المدفوعة بالمحفظة تَستهلك «مالاً» لم يَصل للمنصّة فعلاً — أيّ تسوية مع المزوّد ستكون من جَيب المنصّة.
  • يَنتهك مبدأ FIN-COR الأساسيّ: «لا تدفع لمن لم يَدفع».

الإصلاح المُقترَح

  1. على المدى القصير (قبل الترويج):
    • إضافة بوّابة في topup_wallet: if not settings.production_payment_enabled: raise 422 PAYMENT_NOT_ENABLED — تتطابق مع نيّة FIN-COR.
    • إخفاء زرّ «شحن المحفظة» في الواجهة لو production_payment_enabled=false — بَدلاً من إظهار نموذج وَهميّ.
  2. على المدى المتوسّط (التكامل الحقيقيّ):
    • تَصميم WalletTopup ذو حالات: PENDING_PSP → VERIFIED_BY_WEBHOOK → APPLIED.
    • الرصيد يَزيد فقط في حالة APPLIED بعد webhook PSP.
    • تكامل Plutu أو Edfa أو T-Lync (المتاحة في ليبيا) — مَوضوع طور التكامل.
    • لطريقة AGENT: التحقّق ضدّ جدول cash_handovers (المُوكيل سَلّم النقد فعلاً).
    • لطريقة BANK_TRANSFER: حقل bank_reference + موافقة OPS يدوياً (verify-mode) قبل تَطبيق الرصيد.

2) BUG-W-02 — خيار «نقدي» (CASH) لا معنى له 🔴 CRITICAL (UX)

المصدر: web/src/pages/customer/WalletPage.tsx:341
"لا يوجد في تعبية المحفظة نقدي، يوجد وكيل، يوجد تحويل بنكي، يوجد كرت أو بطاقة، يوجد وسائل المتوفرة في ليبيا … أما نقدي فهذه أول مرة أسمع بها — كيف أستطيع نقدي؟"

الكود الحاليّ يَعرض 3 خيارات في قائمة منسدلة:

<select value={sourceMethod} onChange={…}>
  <option value="BANK_TRANSFER">{t("wallet.source_bank_transfer")}</option>
  <option value="CASH">{t("wallet.source_cash")}</option>       ← العيب
  <option value="AGENT">{t("wallet.source_agent")}</option>
</select>

لماذا «نقدي» خاطئ

  • المستخدم على شاشة لاب توب أو هاتف — لا يَستطيع فيزيائياً إعطاء نقد للمنصّة.
  • إذا قَصدنا «دفع نقد لوكيل ميدانيّ» — فهذا هو AGENT، فلا داعي لتَكراره.
  • إذا قَصدنا «إعلام أنّ المُستخدم سيدفع لاحقاً» — هذا ليس شَحناً للمحفظة، هذا دين.

الإصلاح

  1. حذف خيار CASH كلّياً من القائمة (FE + ربما إضافة guard في BE يَرفض source_method="CASH").
  2. إعادة تَسمية القائمة لتعكس الواقع الليبيّ: 
    BANK_TRANSFER   → "تحويل بنكي (المصرف التجاريّ / الجمهوريّة / …)" — يتطلّب bank_reference
AGENT          → "وكيل تَسوية معتمَد (سَلِّم النقد للوكيل)"
CARD           → "بطاقة مصرفيّة (Edfa / Plutu)" — جديد
MOBILE_WALLET  → "محفظة موبايل (T-LYNC / Sadad)" — جديد، عند التكامل
  3. الخيارات الجديدة (CARD / MOBILE_WALLET) تُعرَض فقط عند production_payment_enabled=true AND توفّر تكامل PSP الموافق.

3) BUG-W-03 — وسائل ليبيا الحقيقيّة غائبة 🟠 HIGH

4) BUG-T-01 — «الوقت المتبقي» وَهميّ ويَبدأ مبكّراً 🔴 CRITICAL

المصدر: web/src/components/OrderCountdown.tsx · backend/app/modules/orders/order_router.py:119-134
"التوقيت — الوقت المتبقي — أولاً ما هذا الوقت، وقت ماذا؟ ثانياً لم ينتظر هذا الطلب حتى يوافق عليه المزوّد والسائق المناسب — يعني إيجاد السائق المناسب ويوافق المزوّد"

ما يَحدث الآن

في صفحة تَتبع الطلب يَظهر «⏱ الوقت المتبقي 29:27» وهو يَتناقص ثانية بثانية بمجرَّد تَحميل الصفحة.

السبب الجذريّ

الواجهة:

// OrderCountdown.tsx
const [secondsLeft, setSecondsLeft] = useState(etaMinutes * 60);
useEffect(() => setSecondsLeft(etaMinutes * 60), [etaMinutes]);
useEffect(() => {
  const id = setInterval(() => setSecondsLeft((s) => s - 1), 1000);
  return () => clearInterval(id);
}, []);

الخلفية:

# order_router.py
async def _eta_minutes_for(db, order):
    if order.order_state in _ETA_DONE_STATES: return None
    prep = await db.scalar(
      select(Provider.default_prep_time_min).where(Provider.id == order.provider_id)
    )
    return int(prep) if prep else None

المُشكلات المتعدّدة

  1. الرقم ليس «متبقّياً» لشيء. هو ببساطة default_prep_time_min الثابت في إعدادات المزوّد (عادةً 30). لا علاقة له بوقت بدء التحضير الفعليّ ولا بوقت توصيل مُتوقَّع.
  2. يَبدأ من المرحلة ACCEPTED (وأَحياناً قبلها). العميل في الصورة يَرى «مقبول» في الـtimeline لكن السائق لم يَقبل العرض بعد — والعدّاد يَنزل كأنّ التوصيل اقتراب.
  3. لا يَحسب مرحلة dispatch ولا قَبول السائق. 30 دقيقة من تَحضير لا تَتضمّن: وقت إيجاد سائق، قَبوله، ذَهابه للمتجر، الاستلام، ثم القيادة للعميل.
  4. يَتصفّر مع كلّ تَحميل صفحة. العدّاد client-only — لا anchor زمنيّ في الـDB، ففتح الصفحة بَعد 20 دقيقة يَعرض 30:00 من جديد.
  5. التَسمية «الوقت المتبقي» مُضلِّلة. صحيحه «وقت التحضير الافتراضيّ عند المزوّد».

الإصلاح المُقترَح (متعدّد الطبقات)

  1. عَدم إظهاره قبل بدء التحضير الفعليّ: 
    // OrderTrackingPage.tsx
{order.eta_minutes != null
  && ["IN_PREPARATION", "READY_FOR_PICKUP", "EN_ROUTE"].includes(order.order_state)
  && <OrderCountdown … />}
  2. تَثبيت نقطة بداية على الـserver: أضف eta_deadline_at (timestamp) عند انتقال الطلب لـIN_PREPARATION = now() + prep_time. الواجهة تَحسب deadline - now دائماً — فلا تَصفير عند الـreload.
  3. إعادة تَسمية:
    • قبل التحضير: لا يَظهر شيء (أو رسالة «بانتظار المزوّد»).
    • أثناء التحضير: «جاهز بَعد ~N دقيقة (تقديريّ)».
    • بَعد READY_FOR_PICKUP: «بانتظار السائق».
    • بعد EN_ROUTE: «التوصيل بَعد ~N دقيقة» (احسبها من ETA الخريطة لا من prep_time).
  4. إضافة مَراحل مَخفيّة للـtimeline: العميل لا يَرى «بانتظار قَبول المزوّد» ولا «بانتظار قَبول السائق» — يَجب إضافتهما كَخطوتَين مَرئيتَين قَبل «مقبول» / بَعدها على التوالي.

5) BUG-T-02 — العدّاد client-only يَتصفّر 🟠 HIGH

(جزء من BUG-T-01 ولكنّه مَوصوف مُنفصلاً للتَوضيح):

كلّ مرّة يُحدِّث العميل صفحة التَتبّع، أو يَفتحها من إشعار، أو يَنتقل بين تابات المتصفّح، يَبدأ العدّاد من etaMinutes * 60 من جَديد — مَعنى ذلك أنّ الرقم لا يَعني شَيئاً ثابتاً.

الحلّ: الانتقال إلى نَهج «deadline_at على الـserver + setInterval يَحسب الفَرق مع Date.now()» (مَوصوف فوق).

6) BUG-C-01 — صفّ «طريقة الدفع» يَفيض خارج الإطار 🔵 MEDIUM

المصدر: web/src/pages/customer/CheckoutPage.tsx:843
"الكتابة ليست صحيحة فوق بعضها"

في الصورة الأولى يَظهر شِيب «نقداً» الأخضر، وعلى يَساره شِيب آخر (يَبدأ بـ«بحـ» — يَرجَّح «بحساب المحفظة») مُختفٍ خارج الإطار. السَبب:

<div style={{ display: "flex", gap: "0.5rem" }} data-payment-row>
  {paymentOptions.filter((m) => m.available).map((m) => (
    <button className="btn" style={{ flex: 1, … }} … />     ← flex:1 بلا flexWrap
  ))}

عند عرض ضيّق + نَصّ عربيّ طويل («بحساب المحفظة») الشِّيبات تُضغَط أو تَفيض. حلّ سَطر واحد:

<div style={{
  display: "flex",
  gap: "0.5rem",
  flexWrap: "wrap"      // ← أَضِف
}} data-payment-row>

وحَبَّذا تَقصير عَنوان «بحساب المحفظة» → «المحفظة» (مع تَلميح صَغير تَحت).

7) ملاحظات إضافيّة من الصور

  1. عَنوان التَوصيل «gjgtdcd»: نَصّ غير صالح. يَجب التحقّق من العَنوان عند الإضافة (طول أدنى، أحرف عربيّة/لاتينية معقولة، GPS موجود). يُضاف فحص بسيط في AddressBook.
  2. الـtimeline 5 خطوات: مقبول → قيد التحضير → جاهز → في الطريق → تم التوصيل. لا تَظهر «بانتظار المزوّد» ولا «بانتظار قَبول السائق» — العميل لا يَفهم لِمَ تَأخّر إنْ كانت إحدى هاتين هي السَبب.
  3. زرّ «تقديم» الرَماديّ تحت إلغاء: غير واضح ما يَفعل — يَستحقّ تَسمية أوضح («تقديم شَكوى»؟ «التَقدّم لمرحلة جَديدة»؟).
  4. زرّ «شحن» الأخضر في WalletPage: يَفتح نَموذجاً يَعمل بشكل صَحيح من ناحية الـOTP، لكن جوهر العمليّة (BUG-W-01) خاطئ.
