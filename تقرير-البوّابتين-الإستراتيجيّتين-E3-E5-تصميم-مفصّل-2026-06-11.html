الجزء الأوّل — E3 · هيكل «المندوب الرئيس» (Master-Agent) يتطلّب migration

١. المفهوم

اليوم كلّ «مندوب تسوية» (نقطة) كيان مستقلّ يحمل عائمًا وحدودًا. المندوب الرئيس = طبقة إشراف: مندوب رئيس يدير مندوبين فرعيّين (نقاطه)، مع تجميع محتمل للعوائم/الحدود وتسويات متدحرجة إلى الرئيس — مفيد لشبكة وكلاء هرميّة (موزّع رئيس ⟵ نقاط فرعيّة).

٢. حالة الكود الحاليّة (مؤكَّدة)

٤. التقاطع الحرج مع تسوية E2 — SIM-E3-1

فحص E2 الذي بُني سابقًا (AGENT_FLOAT_MISMATCH) يقارن عائم كلّ مندوب منفردًا:

# E2 الحاليّ — لكلّ مندوب فعّال
expected_float = Σ(SettlementTransaction.cash_minor WHERE state=SETTLED, channel∈CASH/FULL)
               − Σ(CashHandover.amount_minor WHERE proof_type=AGENT_FLOAT_SETTLE)
if expected_float ≠ agent.current_float_minor:  → AGENT_FLOAT_MISMATCH
⚠️ الخطر: لو اختير «تجميع العائم» (ب)، فإنّ عائم الرئيس سيشمل حركات الفرعيّين، فيُعلِّم فحص E2 المندوبَ الرئيسَ والفرعيّين خطأً (المعادلة لكلّ مندوب لن تتوازن). العلاج الإلزاميّ: يجب أن يُعمَّم منطق E2 ليحسب على مستوى الشجرة (الرئيس + فرعيّوه) أو يستثني الرئيس من الفحص الفرديّ — قرار يُحسَم قبل الـmigration.
مع التجميع (ب) — الفحص الفرديّ يفشل: عائم الرئيس A = Σ(فرعيّوه) ← لكن A بلا معاملات خاصّة → expected(A)=0 ≠ float(A) ✗ العلاج: expected_tree(A) = Σ معاملات (A + A1 + A2 + A3) − Σ تسليمات الشجرة
شكل 3 — لماذا يجب تعميم فحص E2 على الشجرة عند التجميع.

٥. أسئلة القرار (تُحسَم في الجلسة)

Q1 — نموذج العائم: مستقلّ · مجمَّع · هجين؟ (يحدّد تعقيد E2 والتسوية)
Q2 — ماذا يتحكّم به الرئيس؟ حدود الفرعيّين · موافقة معاملاتهم · إعادة توزيع العائم · KYC؟
Q3 — التسوية المتدحرجة: هل يسوّي الفرعيّ مع رئيسه ثمّ الرئيس مع المركز؟ أم كلٌّ مع المركز مباشرة؟
Q4 — عمق الشجرة: مستوى واحد (رئيس→فرعيّ) أم متعدّد؟ (التعدّد يضاعف التعقيد)

٦. مراحل البناء (بعد حسم الأسئلة)

  1. م1 migration: parent_agent_id + فهرس (تحقّق upgrade/downgrade على PG).
  2. م2 منطق الهرميّة: حسب Q1–Q3 (تجميع/حدود/تسوية).
  3. م3 تعميم E2: فحص على مستوى الشجرة (علاج SIM-E3-1) + اختبارات.
  4. م4 واجهة OPS: شجرة المندوبين + إسناد فرعيّ + عرض العائم المجمَّع.
  5. م5 بوّابات: FIN-COR PASS · NEW=0 · tsc/lint/build/Vitest · تحقّق حيّ.

الجهد: كبير · المخاطر: متوسّطة-عالية (مال + migration + تقاطع E2) · التبعيّة: migration + قرارات التصميم.

الجزء الثاني — E5 · تحقّق الوثائق + كشف الحياة (Liveness/AI) يتطلّب مزوّدًا

١. المفهوم

تحقّق آليّ من وثائق KYC (أصالة المستند + مطابقة الوجه) + كشف الحياة (Liveness): التأكّد أنّ الصورة لشخص حيّ حاضر، لا صورةٍ-لصورة أو تزييف عميق — قبل اعتماد المندوب/السائق/المزوّد.

٢. حالة الكود الحاليّة (مؤكَّدة)

تخزين الوثائق: • AgentKyc (app/models/agent_kyc.py:29-30) doc_type · object_key → MinIO • DriverDocument (app/models/dispatch.py:301) doc_type · status(PENDING…) • العقد القانونيّ + صورة التوقيع (legal.py) ← صورة حيّة تُلتقَط بالكاميرا أصلًا تدفّق الاعتماد (نقطة الربط): • POST /operations/documents/{id}/approve (operations_router.py:2063) → _find_and_review_document(db, doc_id, user_id, "APPROVED") • POST .../reject (:2079)
شكل 4 — مخازن الوثائق ونقطة اعتمادها الحاليّة (حيث يُحقَن الذكاء).

٣. نقطة الربط والتدفّق المقترح — SIM-E5-1

[المستخدم] رفع الوثيقة/السيلفي ↓ تخزين MinIO (object_key) ↓ ┌─────────────────────────────┐ ┌────────────────────────────►│ مزوّد PAD/Liveness (API) │ │ (غير متزامن، استشاريّ) │ يقرأ الصورة عبر object_key │ │ │ يُعيد: درجة + أعلام (عرض/حقن) │ │ └──────────────┬──────────────┘ │ ↓ │ تُخزَّن النتيجة advisory (لا تحجب) │ ↓ └────────► OPS: approve_document ← يرى الدرجة/الأعلام ثمّ يقرّر يدويًّا (operations_router.py:2063)
شكل 5 — التدفّق المقترح: تحقّق استشاريّ غير حاجب يغذّي قرار المُعتمِد.
⚠️ SIM-E5-1 (إلزاميّ): الاستدعاء لا يحجب الاعتماد — لو بطؤ المورّد أو تعطّل، يبقى الاعتماد ممكنًا (الدرجة استشاريّة، fail-open). الحجب على مورّد خارجيّ = نقطة فشل أحاديّة.

٤. معيار 2026 (NIST) + مشهد المورّدين

NIST SP 800-63-4 (2025): يجعل PAD متطلَّبًا تنظيميًّا، ويفصل هجمات العرض (Presentation) عن هجمات الحقن (Injection) كمتطلَّبين مستقلّين — أيّ حلّ يجب أن يعالجهما معًا. Liveness سلبيّ (بلا حركة من المستخدم) يحمي نسبة إتمام التسجيل؛ النشط يضيف احتكاكًا لتوكيد أعلى.

٥. أسئلة القرار (تُحسَم في الجلسة)

Q1 — المورّد: Incode/Paravision/FaceMe/ID-Pal/Aware؟ (تجربة PoC لمرشّحين)
Q2 — على-الجهاز أم سحابيّ؟ (خصوصيّة بيانات المستخدم الليبيّ + التكلفة)
Q3 — استشاريّ أم حاجب؟ (موصى: استشاريّ، SIM-E5-1) + عتبة الدرجة للتنبيه
Q4 — النطاق: liveness السيلفي فقط · أم + أصالة المستند + مطابقة الوجه؟
Q5 — كشف الحقن: هل نشترط معالجة هجمات الحقن (NIST) من اليوم الأوّل؟

٦. مراحل البناء (بعد اختيار المورّد)

  1. م1 PoC: تجربة 1–2 مورّد على عيّنة وثائق (دقّة/تكلفة/خصوصيّة).
  2. م2 تكامل: عميل المورّد + قراءة MinIO عبر object_key + تخزين الدرجة (migration بسيطة لحقل الدرجة/الأعلام).
  3. م3 ربط الاعتماد: استدعاء استشاريّ غير متزامن (SIM-E5-1) + عرض الدرجة في واجهة approve_document.
  4. م4 بوّابات + خصوصيّة: سياسة بيانات + اختبارات (محاكاة مورّد) + تحقّق حيّ.

الجهد: كبير · المخاطر: عالية (تبعيّة خارجيّة + خصوصيّة + تكلفة) · التبعيّة: مورّد + قرار خصوصيّة/تكلفة.

أجندة الجلسة المقترحة

  • E3: حسم نموذج العائم (مستقلّ/مجمَّع/هجين) → تحكّم الرئيس → التسوية المتدحرجة → عمق الشجرة → ثمّ تعميم E2 ثمّ migration.
  • E5: اختيار مرشّحي مورّدين لـPoC → على-الجهاز/سحابيّ → استشاريّ/حاجب → نطاق (سيلفي/مستند/وجه) → كشف الحقن.
توصية التسلسل: E3 أولًا لو الأولويّة شبكة الوكلاء (داخليّ، يُبنى فورًا بعد حسم التصميم)؛ E5 يتبع قرار المورّد (يبدأ بـPoC قصير). كلاهما لا يبدأ دون حسم أسئلة القرار أعلاه.

الخلاصة

البوّابتان موصوفتان بدقّة على أساس الكود الفعليّ: E3 يحتاج عمود parent_agent_id + migration + حسم نموذج العائم، وأخطر تقاطعاته تعميم فحص التسوية E2 (SIM-E3-1)؛ E5 يُحقَن عند approve_document كتحقّق استشاريّ غير حاجب (SIM-E5-1) عبر مورّد PAD يقرأ الصورة من MinIO، وفق NIST SP 800-63-4. كلٌّ منهما يبدأ بجلسة قرار تحسم الأسئلة المذكورة. لم يُبنَ شيء — بانتظار قرارك ببدء أيّهما والإجابة عن أسئلة التصميم.
