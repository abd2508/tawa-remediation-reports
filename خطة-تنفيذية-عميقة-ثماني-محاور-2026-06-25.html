المراحل

  1. خلفية: عَلَمان + رمز خطأ + دالّة البوّابة (بلا هجرة)
  2. حقن البوّابة في ٤ نقاط بالترتيب الصحيح + phone_verified في /me
  3. اختبارات الخلفية (تأكيد «مُطفأ = خامل»)
  4. واجهة: تغيير PIN + تأكيد الهاتف + لافتات الخطأ + ترجمة ثلاثية
  5. اختبارات الواجهة + تكافؤ الترجمة
الإطلاق الآمن: العَلَمان مُطفآن → كل الاختبارات خضراء بلا تغيير سلوك. تُفعّل الهاتف أولًا في staging ثم الإنتاج؛ البريد لاحقًا. معايير القبول: مُطفأ=خامل · مفعّل+غير مُتحقَّق ⇒ 422 على التعبئة/التحويل/تعيين-PIN · الفتح/الرصيد/الاستقبال لا تُحجَب أبدًا · واجهة تغيير PIN تعمل (الفجوة مُغلقة) · FIN-COR PASS بلا هجرة.

٨ رسم التوصيل — إنهاء «مجاني» المضلِّل ١٧ سيناريو · عاجل

الواقع (مُعاد التحقّق): Provider.delivery_fee_minor افتراضه 0 ولا يُسنَد أبدًا → التصفّح يُخرج 0 → البطاقة تعرض «مجاني». 🐞 اكتشاف جديد: معادلتان مختلفتان — التصفّح الحيّ يستخدم geo_service.compute_delivery_fee_minor (أساس 2000، منصّة فقط)، والدفع يستخدم delivery_fee_service.compute_delivery_fee (أساس 3000، يحترم التوصيل الذاتي). نمط delivery_fee_is_live موجود في صفحة الفئة لكنه غير موصول بالبطاقة.

  • توحيد المعادلة (F13/F7): يحسب التصفّح الرسم عبر نفس دالّة الدفع — لا كذب في الرقم.
  • حساب حيّ في البحث: _provider_public_dict/search_providers يحسب الرسم بالمسافة (الإحداثيات مُمرَّرة أصلًا) + علَم delivery_fee_is_live.
  • سياسة «مجاني فوق حدّ»: عمود جديد Provider.free_delivery_over_minor (هجرة) — null=لا مجاني · 0=مجاني دائمًا · N=مجاني فوق N.
  • الواجهة: منطق لافتة جديد في ProviderCard/ProviderHeader/CategoryPage: حيّ → رقم · غير محسوب → «تُحسب عند الدفع» · مجاني حقيقي → «مجاني»/«مجاني فوق X».

المراحل

  1. توحيد المعادلة (بلا هجرة) + اختبار «التصفّح = الدفع»
  2. حساب الرسم الحيّ في مُسلسِل البحث + علَم live
  3. سياسة «مجاني فوق حدّ» (هجرة free_delivery_over_minor — تتطلّب إذنك)
  4. واجهة: الأنواع + منطق اللافتة + ترجمة
الإطلاق الآمن: المرحلتان ١–٢ تصحيح صادق بلا هجرة وتُشحن أوّلًا (تُوقف الكذب وتعرض التقدير الحقيقي). سياسة «المجاني» اختيارية لكل مزوّد (افتراضها null → لا أحد يظهر «مجاني» حتى يضبطه مزوّد/مشغّل). القبول: مزوّد برسم 0 بلا سياسة لا يعرض «مجاني» أبدًا · رقم التصفّح = الفاتورة · «مجاني» فقط بسياسة حقيقية.

الواقع (مُعاد التحقّق — مع تصحيحات): النقاط موصولة بالتسليم فعلًا (١٠/طلب) لكن غير قابلة للاستبدال ولا قيمة لها. الإحالة أكثر تطوّرًا مما ظُنّ: نموذج حواف متعدّدة + بوّابة تحويل Tier-2 + سقف سرعة + كشف احتيال بالجهاز/الهاتف. المُحال إليه لا يربح شيئًا. لا لوحة OPS إطلاقًا (إعدادات env فقط).

  • إعدادات وقتية: جدول loyalty_config (هجرة aa63) + محلّل (DB→افتراض الإعدادات) — مبذور من القيم الحالية → صفر تغيير سلوك.

٧ «تسوّق على قد فلوسك» (ميزانية) ١٢ سيناريو · ميزة جديدة

الواقع (مُعاد التحقّق): اللبنات جاهزة (سعر variant + فئة + ترتيب سعري). الناقص: لا بارامتر max_price في أي بحث، والسعر يُحسب في استعلام فرعي بعد الاستعلام الرئيسي وبعد limit. 🔒 قيد بنيوي حاسم: السلّة والطلب لمزوّد واحد (Order.provider_id NOT NULL · السلّة تُفرَّغ عند تبديل المتجر).

🏗️ التصميم

  • خلفية: رفع «أرخص variant» إلى الاستعلام الرئيسي + بارامتر max_price_minor (وcategory_id) + base_price ≤ max_price قبل limit + استثناء الأصناف بلا سعر.
  • واجهة: صفحة /budget-shop (مُبوَّبة بعَلَم) + إدخال مبلغ + صناديق فئات + شبكة أصناف + شريط ميزانية حيّ يمنع زيادة الكمية فوق المبلغ.
  • مرحلة ١: ميزانية داخل متجر واحد (يطابق السلّة الحالية). مرحلة ٢ (مُبوَّمة): سلّة متعدّدة المزوّدين تنقسم لطلب لكل مزوّد.
الإطلاق الآمن: عَلَم budget_shop_enabled مُطفأ. القبول: المسارات الثلاثة تقبل max_price_minor وتُرجع فقط ما ≤ الميزانية (في SQL قبل limit) · شريط ميزانية حيّ · قفل المتجر الواحد مُوضَّح · بحث عربي يعمل.

٦ تفعيل «تسوّق لي» (المشاوير) ١٣ سيناريو · قرار

الواقع (مُعاد التحقّق): الميزة مكتملة طرفًا لطرف لكن مُطفأة (errand_enabled=False). 🪤 فخّ E11: تفعيل العَلَم مع ترك المعرّف فارغًا → نقطة الحالة تُبلّغ «معطّل» فتختفي الميزة رغم قبول الخلفية. 💰 فجوة مالية: الميزانية تُحجَز كاملةً في مستحقّ منصّة، بلا تسوية ولا نموذج لتعويض السائق عن ثمن البضاعة (أجر المسافة موجود).
الفجوة: يجب بناء قيد المشاوير (إسكرو → تعويض السائق + أجر + عمولة) قبل التفعيل بمال حقيقي
