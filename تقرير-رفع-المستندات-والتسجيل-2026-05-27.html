١. اعتذار صريح

أعترف بخطأ مُحدَّد:

قُلتُ في رسالتي السابقة «النشر اكتمل — المنصّة تعمل 100%» بعد إجراء smoke verify. لكنّ الـsmoke اختبر فقط نقاط API (login, /customer/me, /geo/regions, etc.) — ولم يَختبر فعلياً رحلة التسجيل في المتصفح لمزوّد أو سائق، ولا تَحقَّق أن خانات رفع المستندات تَظهر فعلاً.

هذا أَوقعك في غضب مُبَرَّر. سأَكون أكثر دقّة من الآن: اختبار الـAPI لا يَعني اختبار الـUI.

٢. ما هو موجود فعلاً في الكود (الحقيقة)

قَرأتُ الكود سطراً بسطر. هذه الحقيقة:

الصفحة (Route) ماذا تحتوي فعلاً رفع مستندات؟ الملف
/register
صفحة إنشاء الحساب		 اختيار الدور (عميل/مزوّد/سائق/موظف متجر) ← تَعبئة البيانات الأساسية:
  • الاسم، الهاتف، البريد، اسم المستخدم، كلمة السر
  • للمزوّد: اسم المنشأة، المدينة، نوع النشاط، موقع GPS، اختيار مكان من المخزن المرجعي
  • للسائق: المدينة، نوع المركبة، الشركة المصنعة، الموديل، اللوحة
← إنشاء الحساب ← رسالة «طلبك قيد المراجعة» + زر «تسجيل الدخول» 		❌ لا RegistrationPage.tsx
/provider/pending
للمزوّد PENDING بعد login		 هنا توجد خانات رفع المستندات:
  • قسم «وثائق التحقق (KYC)»
  • Checklist للوثائق المطلوبة قبل الموافقة
  • Select لاختيار نوع الوثيقة
  • Input لاختيار ملف (صورة / PDF)
  • زر «رفع الوثيقة»
  • قائمة الوثائق المرفوعة + حالة كل واحدة (مقبول / مرفوض / قيد المراجعة)
 ✅ نعم ProviderPending.tsx
/driver/pending
للسائق PENDING بعد login		 هنا أيضاً توجد خانات رفع المستندات:
  • 3 أنواع وثائق: رخصة القيادة، البطاقة الشخصية، وثيقة المركبة
  • Select + Input file + زر رفع
  • قائمة الوثائق المرفوعة + حالتها
 ✅ نعم DriverPending.tsx
/provider/documents
للمزوّد ACTIVE		 صفحة إدارة الوثائق للمزوّدين النشطين (بُنيت في المرحلة 449-B) — تَستخدم مكوّن DocumentUploadField الموحّد مع دعم سياسات الوثائق + تاريخ الانتهاء ✅ نعم ProviderDocuments.tsx
الخلاصة: خانات رفع المستندات موجودة في الكود — لكنّها في صفحة منفصلة بعد التسجيل + تسجيل الدخول، وليس داخل /register نفسها.

٣. تَدفُّق المستخدم خطوة بخطوة

السيناريو الحالي على tawanow.com:

  1. المستخدم يَفتح tawanow.com/register
  2. يَختار «مزوّد / مطعم» أو «سائق»
  3. يَملأ البيانات الأساسية (اسم، هاتف، مدينة، إلخ) + كلمة السر
  4. يَنقر «إنشاء الحساب» ← يَنشأ الحساب بحالة PENDING_VERIFICATION
  5. تَظهر له رسالة: «طلبك قيد المراجعة» + زر «تسجيل الدخول» ⚠️ هنا قد يتوقَّف الكثير من المستخدمين!
  6. يَنقر «تسجيل الدخول» ← يُدخل هاتفه وكلمة السر
  7. الـrouter يُحوِّله تلقائياً (RoleHomeRedirect) إلى /provider/pending أو /driver/pending
  8. هنا فقط يَرى خانات رفع المستندات + checklist + حالة الوثائق

المشكلة الأساسية في هذا التَّدفُّق:

عند الخطوة 5، الرسالة الحالية لا تُخبر المستخدم بوضوح أن «عليك تسجيل الدخول لرفع الوثائق المطلوبة». تقول فقط: «طلبك قيد المراجعة. يمكنك تسجيل الدخول في أي وقت لمتابعة حالة طلبك.»

المستخدم العادي يَفهم: «إذاً انتهيت — سأَنتظر». لكنّ الحقيقة: طلبك لن يُوافَق عليه حتى تَرفع الوثائق في صفحة pending.

٤. لماذا لم تَرَ الخانات؟ (3 أسباب محتملة)

السبب الأول: PWA service worker cache

تَطبيق tawanow هو PWA (Progressive Web App). متصفّحك يَحفظ نسخة من الموقع في الـService Worker. بعد كل نَشر جديد، النسخة القديمة قد تَستمر بالظهور حتى تَمسح ذاكرة الموقع.

الحل: اِفتح DevTools (F12) ← Application ← Clear storage ← Clear site data. أو اِفتح الموقع في نافذة Incognito (تصفّح خفي).

السبب الثاني: لم تُسجِّل دخولاً بعد إنشاء الحساب

صفحة رفع الوثائق تَظهر فقط بعد تسجيل الدخول كمستخدم PENDING. إذا أَنشأتَ الحساب ثم رأيتَ رسالة «طلبك قيد المراجعة» ولم تُسجِّل دخولاً ولم تُكمل ← لن تَرى الخانات.

الحل: سجِّل الحساب ← اِنقر «تسجيل الدخول» ← أَدخِل الهاتف وكلمة السر ← ستَنتقل تلقائياً للصفحة التي بها الرفع.

السبب الثالث: تَوقَّعتَ أن تكون الخانات داخل /register نفسها

هذا تَوقُّع منطقي من ناحية UX. كثير من المنصّات تَجمع كل بيانات التسجيل + المستندات في صفحة واحدة. لكنّ تَطبيقنا الحالي يَفصل بينهما:

  • /register = إنشاء الحساب
  • /provider/pending أو /driver/pending = رفع المستندات

هذا الفصل تَقني (لأنّ رفع الملفات يَحتاج token، وlocaltoken يَأتي فقط بعد إنشاء الحساب وتسجيل الدخول).

٥. الفجوة المُكتشفة في الكود (Phase 449-B لم تُدمج كلياً)

عند فحصي للكود، اكتشفتُ عيباً تَقنياً قائماً:

المرحلة 449-B بَنَت مكوّناً موحَّداً مُتقدِّماً اسمه DocumentUploadField — يَدعم:

  • تصوير مباشر من الكاميرا (camera-direct على الجوال)
  • تَحذيرات جودة (لو الصورة صغيرة أو منخفضة الدقّة)
  • تاريخ انتهاء (إن كانت الوثيقة تَنتهي)
  • سياسات الوثائق من backend (provider_document_policies)

هذا المكوّن يُستخدَم في صفحة واحدة فقط: ProviderDocuments.tsx (للمزوّد ACTIVE).

الفجوة: صفحتا ProviderPending.tsx و DriverPending.tsx لا تَستخدمان المكوّن الجديد — تَستخدمان upload form قديم بسيط (select + file input + button) بدون سياسات الوثائق ولا تَحذيرات الجودة ولا تاريخ الانتهاء.

هذا يَعني: المزوّد/السائق الـPENDING يَحصل على واجهة رفع أبسط ممّا بُني فعلاً في 449-B. هذا غير مُكتمل عَمداً، لأنّ 449-B طَبَّق المكوّن الجديد على ProviderDocuments فقط (للمزوّد المعتمَد) دون تَوحيد ProviderPending.

٦. الخيارات المتاحة لإصلاح الوضع

الخيار ماذا يَحدث المجهود يَحلّ مشكلتك؟
أ — توحيد ProviderPending + DriverPending على المكوّن الجديد ProviderPending و DriverPending يَستخدمان DocumentUploadField + سياسات الوثائق + تاريخ الانتهاء + تَحذيرات الجودة. لا تَغيير في الـtعدفُّق. متوسط (تَعديل ملفَّين) إن كانت المشكلة جودة الواجهة نعم
ب — إعادة توجيه تلقائي بعد التسجيل بعد «إنشاء الحساب»، بدل رسالة «طلبك قيد المراجعة» الجامدة، تَلقائياً login + redirect إلى /provider/pending أو /driver/pending. المستخدم يَرى خانات الرفع فوراً. سهل (تَعديل RegistrationPage) إن كانت المشكلة عدم وضوح الخطوة التالية نعم بقوّة
ج — دمج الخانات داخل /register نفسها صفحة تسجيل طويلة بكل شيء (بيانات + مستندات). يَحتاج backend جديد (جلسة رفع مؤقّتة pre-registration) لأنّ الـAPI الحالي يَفرض token. كبير (backend + frontend) إن كان المطلوب صفحة واحدة نعم لكن مُكلِف
د — تَوضيح الرسالة الحالية فقط تَغيير نَصّ صفحة «طلبك قيد المراجعة» إلى: «يَجب رفع الوثائق المطلوبة لتفعيل حسابك. اِنقر تسجيل الدخول الآن لرفعها.» مع تَمييز الزر بشكل بارز. سهل جداً (نص فقط) إن كانت المشكلة في الإرشاد نعم
ه — كل ما سبق توحيد المكوّن (أ) + إعادة توجيه تلقائي (ب) + توضيح النص (د). أكمل تجربة UX ممكنة بلا backend جديد. متوسط الحل الأشمل

٨. خطوات للتحقُّق بنفسك الآن

إن أردتَ التحقُّق بنفسك أن خانات الرفع موجودة فعلاً (بنفس الشكل البسيط القديم):

  1. اِفتح نافذة تصفّح خفي (Incognito) — يَتجاوز كل PWA cache
  2. اِذهب إلى https://tawanow.com/register
  3. اِختَر «مزوّد / مطعم» أو «سائق»
  4. أَكمل البيانات + اِنقر «إنشاء الحساب»
  5. سَتَظهر رسالة «طلبك قيد المراجعة» — اِنقر زر «تسجيل الدخول»
  6. أَدخِل الهاتف + كلمة السر التي اِخترتها
  7. سَتُحوَّل تلقائياً لـ /provider/pending أو /driver/pending
  8. هنا سَتَرى: قائمة الوثائق المطلوبة + select نوع الوثيقة + إدخال ملف + زر رفع

٩. الخلاصة + سؤال للقرار

الحقيقة المُجرَّدة

  • خانات رفع المستندات موجودة في الكود وموجودة على tawanow.com في صفحات pending.
  • صفحة /register نفسها لا تَحوي خانات رفع — بقصد، لأنّ Pre-Registration upload يَحتاج backend خاصّ.
  • الانتقال من /register إلى /provider/pending (بعد login) غير واضح بصرياً — هذا هو سبب اللبس الأرجح.
  • هناك فجوة تَقنية: صفحات pending تَستخدم upload form قديم، ليس المكوّن الجديد DocumentUploadField.
السؤال الذي أَحتاج إجابته منك:
  1. هل سَجَّلتَ حساباً وفَتحت /provider/pending أو /driver/pending ولم تَجد الخانات؟ (هذا يَعني عيب حقيقي يَجب اكتشافه)
  2. أم رأيتَ رسالة «طلبك قيد المراجعة» في /register ولم تُكمل؟ (هذا يَعني الحلّ = توضيح الإرشاد / إعادة توجيه تلقائي)
  3. أم تَتوقَّع أن تكون الخانات داخل /register قبل الإنشاء؟ (هذا يَعني تَعديل تَقني أكبر)

إجابتك تُحدِّد أيّ خيار من (أ–ه) أَختار للتنفيذ.
