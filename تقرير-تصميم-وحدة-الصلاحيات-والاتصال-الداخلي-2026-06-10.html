4) القرار المعماريّ الجوهريّ — نموذج الصلاحيّات

المبدأ المقترح: «دور أساس + منح/سحب لكل-حساب» (Role baseline + per-account overrides).
الصلاحيّة الفعّالة لأيّ حساب = صلاحيّات دوره الافتراضيّة ⊕ منحٌ إضافيّة لهذا الحساب ⊖ سحبٌ لهذا الحساب. هذا يحقّق R1 (الدور جاهز بصلاحيّاته) و R4 (التخصيص الدقيق) معًا، ويبقى متوافقًا مع has_permission() القائم بأقلّ تغيير.

لماذا لا «أدوار جامدة فقط»؟ لأنها لا تحقّق R4 (حساب مخصّص بصلاحيّات يختارها السوبر-أدمن). ولماذا لا «صلاحيّات حرّة بلا أدوار»؟ لأنها تُفقِد R1/R2 (الجاهزيّة والتدرّج) وتُثقِل الإدارة. الحلّ الهجين هو الأنسب.

5) الجزء أ — نظام الأدوار والصلاحيّات الهرميّ

5.1 — الهرميّة المقترحة

SUPER_ADMIN — كل الصلاحيّات · ينشئ ويعدّل الكلّ · الوحيد الذي يمنح صلاحيّات «خطرة» (مالية/أعلام/إغلاق بوابات)
ADMIN (جديد) — صلاحيّات تشغيليّة واسعة · ينشئ SUPERVISOR وما دونه · لا يلمس القلب الماليّ المختوم ولا ينشئ ADMIN/SUPER
SUPERVISOR (جديد) — إشراف ميدانيّ · ينشئ موظفين متخصّصين/مراقبة · صلاحيّات أدنى من ADMIN
موظّفون متخصّصون — FINANCE_AGENT (مالية) · COMPLIANCE_AGENT (مراقبة/امتثال) · OPERATIONS_AGENT (عمليّات) · (+أدوار وظيفيّة تُضاف عند الحاجة: دعم، توزيع…)
MONITOR (جديد) — قراءة فقط، أبسط الصلاحيّات · لا يُغيّر شيئًا · وصوله الأساس = شات الكنترول روم

«الحساب المخصّص» ليس طبقة بل أيّ حساب (غالبًا بدور أساس محايد) يمنحه السوبر-أدمن اسمًا وصلاحيّات منتقاة عبر الـoverrides.

5.3 — محرّك الصلاحيّات الفعّالة

# core/roles.py (توسعة) — مع دالّة قاعدة-واعية
def effective_permissions(role, account_grants) -> set[str]:
    base = ROLE_PERMISSIONS[role]              # R1: جاهز بصلاحيّات الدور
    grants = {g.key for g in account_grants if g.effect=="GRANT"}
    revokes= {g.key for g in account_grants if g.effect=="REVOKE"}
    return (base | grants) - revokes      # R4: تخصيص دقيق
  • require_permission(perm) القائم يُعدَّل ليقرأ الصلاحيّات الفعّالة (دور + منح الحساب) بدل خريطة الدور وحدها — تغيير مركزيّ واحد، كلّ الحرّاس القائمين يستفيدون تلقائيًّا.
  • أداء: منح الحساب تُحمَّل مرّة (cache قصير TTL بالـRedis القائم) لتفادي استعلام لكل طلب.
  • حارس الخطورة: الصلاحيّات الموسومة is_dangerous (مالية/أعلام/إغلاق بوابات) لا يمنحها إلّا SUPER_ADMIN — ولا تُمنح أبدًا لـMONITOR.

5.4 — نقاط النهاية (توسعة على المسار القائم)

المسارمنالوظيفة
GET /admin/permissions-catalog (جديد)ADMIN+قائمة الصلاحيّات القابلة للمنح (مفلترة حسب رتبة المنشئ)
POST /admin/ops-accounts (توسعة)هرميّ+ display_name + grants[] + التحقّق الهرميّ (لا تنشئ فوق رتبتك، لا تمنح ما لا تملكه)
PATCH /admin/ops-accounts/{id} (جديد)هرميّتعديل الاسم/الدور/المنح (بنفس حرّاس الهرميّة)
GET /admin/ops-accounts/{id}/effective (جديد)ADMIN+عرض الصلاحيّات الفعّالة لحساب (شفافيّة)

حرّاس الهرميّة (جوهريّة): منشئ برتبة R لا يستطيع: (1) إنشاء/تعديل حساب برتبة ≥ R، (2) منح صلاحيّة لا يملكها هو، (3) منح صلاحيّة خطرة (SUPER فقط). كلّ تغيير يُكتب في سجلّ التدقيق (من، لمن، ماذا، السبب).

5.5 — الواجهة

  • توسعة OpsAccountManagement.tsx: منشئ حساب متعدّد الخطوات (اسم العرض → الدور الأساس → منتقي صلاحيّات مجمَّع حسب الفئة مع تمييز الخطرة → مراجعة).
  • محرّر حساب: عرض الصلاحيّات الفعّالة + منح/سحب.
  • opsAccess.ts: إضافة ADMIN/SUPERVISOR/MONITOR للمجموعات وخرائط المسارات؛ MONITOR يُقصَر على /ops/control-room (وربّما لوحات قراءة محدّدة).
  • i18n ثلاثيّ اللغة لكل النصوص الجديدة (حسب سياسة المرحلة 4: OPS عربيّ-أوّلًا، لكن المفاتيح البنيويّة تُضاف).

6) الجزء ب — الاتصال الداخليّ (شات الكنترول روم)

6.1 — نموذج البيانات (مبنيّ على نمط OrderMessage/SupportChat)

الجدولالحقول الرئيسيّة
internal_threads (جديد)id · kind (BROADCAST / GROUP / DIRECT) · title · created_by · created_at
internal_thread_participants (جديد)thread_id · user_id · role_at_join · last_read_at — يحدّد «لمن يظهر»
internal_messages (جديد)id · thread_id · sender_id · sender_role · sender_display_name · body · created_at · (مرفق لاحقًا)

أنواع المحادثة (R7): BROADCAST = يظهر لكل الموظفين · GROUP = للمشاركين المختارين فقط · DIRECT = شخصان. المرسِل يختار النوع والمستلمين عند الإنشاء.

6.2 — إشراف الكنترول روم (R8) — التصميم الحسّاس

المطلوب: الأدمن/المشرف/السوبر-أدمن تصلهم نسخة من كلّ المحادثات حتى الفرديّة. التصميم المقترح — «رؤية إشرافيّة» لا «مشاركة خفيّة»:
  • المشرفون لا يُحقنون كمشاركين خفيّين في كل خيط (يُربك المحادثة)؛ بل يملكون صلاحيّة internal_chat:oversee تتيح قراءة كلّ الخيوط عبر لوحة إشراف (GET /internal/threads?oversight=true).
  • الشفافيّة الأخلاقيّة: يُعرض للموظفين بوضوح أن «محادثات الكنترول روم خاضعة لإشراف الإدارة» (شعار دائم) — لتجنّب توقّع خصوصيّة زائف. هذا قرار سياسة يحتاج تأكيدك.
  • كلّ وصول إشرافيّ يُسجَّل في سجلّ التدقيق (من اطّلع على أيّ خيط ومتى).

6.3 — حساب المراقبة (R5) داخل الشات

  • MONITOR: قراءة فقط في كل أنحاء المنصّة (لا أزرار كتابة/تعديل في أيّ لوحة)، لكن له صلاحيّة internal_chat:participate — يكتب ويستقبل في الكنترول روم فقط (هذا غرضه الأساس كما ذكرت).

6.4 — الواجهة والفوريّة

  • صفحة جديدة /ops/control-room: قائمة الخيوط (بثّ/مجموعات/مباشر) + لوحة رسائل + منشئ خيط (اختيار النوع والمستلمين) + (للمشرفين) تبويب «إشراف: كل المحادثات».
  • الفوريّة: قناة SSE جديدة GET /sse/internal/threads/{id} + بثّ Redis بنمط القنوات القائمة (إعادة استخدام sse/publish.py) + استطلاع احتياطيّ.
  • إيصالات القراءة (last_read_at) + شارات غير المقروء.

عند إذنك بالبناء، سأُجري محاكاة ذهنيّة كاملة (كما في المراحل السابقة) تستخرج عيوب التنفيذ قبل وقوعها، وأقدّم خطّة منقّحة قبل كتابة أيّ كود.

10) القرارات المطلوبة منك قبل أن أبدأ

  1. D1 — النموذج: أوافق على «دور أساس + منح/سحب لكل-حساب» (§4)؟ أم تفضّل أدوارًا جامدة فقط (أبسط لكن بلا تخصيص R4)؟
  2. D2 — الأدوار الجديدة: ADMIN + SUPERVISOR + MONITOR — بهذه الأسماء؟ وهل تريد أدوارًا وظيفيّة إضافيّة الآن (دعم، توزيع، تسويق…)؟
  3. D3 — من ينشئ مَن: هل ADMIN ينشئ SUPERVISOR وما دون فقط (لا ADMIN آخر)؟ وهل SUPERVISOR ينشئ موظفين/مراقبة فقط؟
  4. D4 — سياسة إشراف الشات: أوافق على «رؤية إشرافيّة شفّافة» مع شعار «خاضع للإشراف» دائم (بدل المشاركة الخفيّة)؟ ومن يُشرف بالضبط: ADMIN+SUPERVISOR+SUPER فقط؟
  5. D5 — حدود البثّ: من يحقّ له «بثّ لكل الموظفين»؟ (مقترح: ADMIN+ فقط، لتفادي الإغراق).
  6. D6 — النطاق الأوّل: أبدأ بالجزء أ (الصلاحيّات) أوّلًا، أم ب (الشات) أوّلًا، أم الاثنان بالتسلسل؟
الخلاصة: الوحدة قابلة للبناء بنظافة فوق الأساس القائم: محرّك صلاحيّات هرميّ قابل للتخصيص (يحقّق R1–R5) + وحدة مراسلة داخليّة بإشراف شفّاف (يحقّق R6–R8)، عبر 6 مراحل صغيرة، migrations مُتحقَّقة على PostgreSQL، بلا مساس بالقلب الماليّ. لن أكتب سطر كود واحد قبل قراراتك الستّة أعلاه وإذنك الصريح بالبناء.
