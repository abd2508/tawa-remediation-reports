🔍 المشكلة بكلمات بسيطة

كانت كل إعدادات الولاء والإحالة (معدّل النقاط · قيمة المكافآت · التفعيل · سقف الإحالات) محبوسة في ملف env — أي تغيير يتطلّب تعديل ملف وإعادة نشر، ولا توجد أي لوحة للمشغّل ليتحكّم أو يعرض الأرصدة أو يراقب الاحتيال. كانت فجوة تشغيلية كاملة.
المعمارية: لوحة OPS → جدول config (DB) → محلّل (DB أو افتراض الإعدادات) → يؤثّر فورًا

🛠️ ما الذي بُني

  • هجرة aa62_loyalty_config: جدولان جديدان — loyalty_config (مفتاح/قيمة وقتية) + loyalty_adjustments (تدقيق كل تعديل رصيد). مُتحقَّقة upgrade+downgrade على PostgreSQL الحيّ (رفع → الجدولان · خفض → نظيف · إعادة رفع → الرأس aa62).
  • المحلّل: كل قيمة تُحلّ كـ«صفّ DB ← أو → افتراض الإعدادات» → صفر split-brain، صفر تغيير سلوك حتى يُغيّر OPS قيمة. وصّلتُ القراءات الحيّة (قيمة النقاط · النقاط/طلب · مكافأة المُحال) عبره فتؤثّر تغييرات OPS فورًا.
  • لوحة OpsLoyaltyControl (٤ تبويبات): الإعدادات (ضبط كل المعدّلات، كتابة بصلاحية SUPER) · الأرصدة (بحث + تعديل مُدقَّق بسبب إلزاميّ، يرفض الرصيد السالب، قفل صفّ) · الإحالات (الحواف + مراقبة احتيال) · التقارير (النقاط القائمة + قيمتها + التزام الإحالات).
  • ٦ نقاط نهاية /operations/loyalty/* + ربط كامل (مسار · صلاحيات 1:1 · شريط · API) + تدقيق audit_logger.

✅ أُثبِت حيًّا (من اللوحة على الخادم)

دخول admin ✓

الأمان: الاستبدال يبقى مختومًا خلف production_payment_enabled → لا حركة مال. تعديل الرصيد مُدقَّق (سبب إلزاميّ + لا يهبط دون صفر + قفل صفّ ضدّ التزامن). كتابة الإعدادات تتطلّب SUPER. العقود المختومة (FIN-COR) دون تغيير.
