١. الملاحظة 1: Offline-safe verification + Driver handoff

G-1 + G-2 · الأَكبر

🔐 رَمز التَّسليم يَعمل offline + يَنتقل عند تَبديل السائق

المشكلة كما طَرحتَها:

السائق وَصل لِلتَّسليم. الإنترنت مَقطوع. مَسح QR كود من العميل أو كَتب الرَّمز الذي أَعطاه له العميل، لكن لا يَستطيع التَّحقُّق لأن الـbackend غير مُتاح. ربّما رمز قَديم؟ ربّما رمز خاطئ؟ المنصَّة لا تَعرف.

إضافة: لو تَم تَبديل السائق (driver handoff)، السائق الجَديد يَأتي بدون أيّ بيانات → يَطلب من العميل الرَّمز مَرَّة أُخرى = تَجربة سَيِّئة.

الوَضع الحالي في الكود (مَفحوص):

Pickup verification (السائق ↔ المزوّد) الـbackend يُولِّد pickup_token (HMAC مَوقَّع) + pickup_short_code (4 أَحرف). المزوّد يَكتب أَحدهما → POST /providers/orders/{id}/verify-pickup → backend يَتحقَّق.
Handoff verification (العميل ↔ السائق) order.delivery_handoff_code = 4 أرقام عَشوائية. السائق يَكتبه → POST /dispatch/orders/{id}/verify-handoff → backend يَتحقَّق + 3 محاولات قُصوى.
Driver re-assignment ❌ غير موجود. driver_emergencies فيه أَنواع (ACCIDENT, VEHICLE_FAILURE, إلخ) لكن لا "REQUEST_REASSIGN" ولا endpoint لنَقل الطلب لسائق آخر.
Offline storage ❌ غير موجود. F-15 الذي بَنيناه اليوم يَدعم queue للـwrites (proof + cash) لكن ليس reads مُسبَقة.

تَحدٍّ أَمني مُهم 🔒

تَخزين الـ4 أرقام الخام (raw code) على جهاز السائق = ثَغرة أَمنية كَبيرة:

  • السائق يَستطيع فَتح DevTools / Storage Inspector ورؤية الرَّمز
  • عندها يَتجاوز خطوة "العميل أَعطاني الرَّمز" → يَستطيع التَّسليم وَهمياً (يَأخذ السلع ويَختفي)
  • الـhandoff code فُكرته الكاملة = إثبات أن العميل استلم فعلاً
الحل الأمني المُقترَح: HMAC hashes بَدلاً من raw codes
  • الـbackend يَرجع HMAC hash للـcode + server-side secret (لا raw code)
  • الجَهاز يَستلم الـhash فقط، يَخزّنه في IndexedDB
  • السائق يَكتب الـ4 أرقام التي أَعطاه العميل
  • الجَهاز يَحسب HMAC(input_code, stored_salt) ويُقارنه بالـhash المُخَزَّن
  • إذا تَطابَق → التَّسليم صحيح. الـverification يَتم محلياً
  • السائق لا يَستطيع استخراج الـcode الأَصلي من الـhash (one-way function)
  • الـrequest يُرسَل عَبر offline queue (F-15) للـbackend ليَسجل الـverification

async def get_offline_bundle(order_id, user, db):
    """
    Driver fetches an offline-safe verification bundle once the order is
    DRIVER_ASSIGNED. Returns:
      - pickup_token (HMAC signed, opaque)
      - handoff_code_hash (HMAC-SHA256 of the 4-digit code + per-order salt)
      - handoff_code_salt (the salt used; client needs it for local HMAC)
    The driver's app stores these in IndexedDB and uses them to verify
    pickup/handoff inputs offline. The actual raw code is never sent.

    # validate driver owns the order

    return {
        "pickup_token": order.pickup_token,
        "handoff_code_hash": hmac_sha256(order.delivery_handoff_code, salt),
        "handoff_code_salt": salt,
        "expires_at": ...,
    }

🔧 Frontend (2): hook useFieldErrors
// web/src/hooks/useFieldErrors.ts (جَديد)
// يَستخرج per-field errors من envelope.details
// envelope shape (مَتَوَقَّع من backend):
// { code: "VALIDATION", message_ar: "...", details: { fields: { email: "البريد مُستخدم", password: "..." } } }

export function useFieldErrors() {
  const [errors, setErrors] = useState<Record<string, string>>({});
  const [generalError, setGeneralError] = useState<string | null>(null);

  const setFromEnvelope = (envelope: ErrorEnvelope | null) => {
    if (!envelope) { setErrors({}); setGeneralError(null); return; }
    const fields = (envelope.details as { fields?: Record<string, string> })?.fields;
    if (fields && Object.keys(fields).length > 0) {
      setErrors(fields);
      setGeneralError(null);  // الحقول كَافية
    } else {
      setErrors({});
      setGeneralError(envelope.message_ar ?? envelope.message_en ?? "حدث خطأ");
    }
  };

  const clear = () => { setErrors({}); setGeneralError(null); };
  return { errors, generalError, setFromEnvelope, clear };
}

٣. الملاحظة 3: Email OTP بَدلاً من token طَويل

G-5 · backend + frontend

📧 رمز رَقمي 6-أَرقام للبريد بَدلاً من 32-حرف hex

المشكلة كما طَرحتَها:

الـemail يَجب أن يُتَحَقَّق منه عند التَّسجيل (مثل phone OTP). الآن: المسجِّل يَكتب أيّ email وَهمي ولا يُتَحَقَّق منه أَبداً. يَجب: يُرسَل رَمز قَصير للبريد، المسجِّل يَكتبه → يُتَأكَّد أنّ البريد ملكه فعلاً.

الوَضع الحالي في الكود (مَفحوص):

backend email/verify-request registration_router.py:712 — يُولِّد secrets.token_hex(16) = 32 حرف hex (مثل "a3f9b2c8d1e4f6a8b3c9d2e7f1a4b6c8")
backend email/verify :734 — يَطلب الـtoken الكامل، يُقارن بالـRedis
المسجِّل يَجب أن يَكتب 32 حرف تَجربة سَيِّئة جداً — لا يُمكن لمُستخدم عَادي كَتابتها بدون نَسخ من email
email provider مُفعَّل؟ ⚠️ لا — Phase 361 أَضاف email channel كـSMTP-stub. يُكتب الـtoken في logs فقط
email verification في RegistrationPage ❌ لا step — الـauthApi.emailVerifyRequest + emailVerify مَوجودان لكن غير مُستَخدمَين في تَدفُّق التَّسجيل

الأَعراض الجانبية:

  • email provider real مَطلوب: حالياً الـtoken في logs فقط. يَحتاج SMTP server حقيقي (Gmail OAuth أو SendGrid أو Postmark)
  • التَّكلفة: SendGrid مَجاني حتى 100/يوم. أَكثر = $20/شَهر
