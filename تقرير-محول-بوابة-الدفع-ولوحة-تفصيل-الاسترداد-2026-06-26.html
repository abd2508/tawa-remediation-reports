1 محوِّل بوّابة الدفع — مجرّد وقابل للتركيب

بلغة بسيطة: سابقًا كان وعاء الكرت يعتمد على «كعب رمليّ» مباشرةً. الآن فصلتُه عن أيّ بوّابة محدّدة عبر طبقة محوِّل: فحين تفتح المدفوعات، يُركَّب محوِّل بوّابة ليبية حقيقية (مثل Plutu) في ملفّ واحد دون لمس منطق الكرت.
المكوّنالدور
PaymentGateway (ABC)عقد موحّد: authorize → capture → void (+ configured/name).
SandboxGatewayالافتراضيّ — لا مال حقيقيّ، مراجع وهميّة (قابل للاختبار).
PlutuGatewayمحوِّل المُجمِّع الليبيّ — خامل حتى تُضبَط اعتمادات PLUTU_*؛ نقاط الوصل الفعليّة موسومة // TODO(plutu-live) تُملأ من وثائق Plutu عند التكامل.
get_gateway()يحلّ البوّابة من payment_gateway (افتراضي sandbox)؛ بوّابة حقيقية غير مضبوطة ⟶ يرتدّ إلى sandbox (fail-safe).
live: active gateway = sandbox · configured = True · payment_gateway = sandbox
      card still gated by production_payment (sealed=False) ✓
tests: default=sandbox · plutu-no-creds→sandbox fallback · plutu+creds→selected · sandbox auth/capture/void ✓

التفعيل لاحقًا (خطوة واحدة): فكّ production_payment (قرارك + بوّابة Legal/Sandbox) + PAYMENT_GATEWAY=plutu + اعتمادات Plutu + ملء // TODO(plutu-live) من وثائق Plutu.

2 لوحة OPS لتفصيل الاسترداد

بلغة بسيطة: حين يُستردّ طلبٌ مقسّط، يرى المشغّل الآن في لوحة الأوعية كيف عاد كل جزء لأصله: النقاط↩نقاطًا · المحفظة↩محفظةً · النقد↩رصيد محفظة.
  • الخلفية: نقطة GET /operations/payment-tenders صارت تُرجِع refund لكل طلب مُستردّ (المبلغ · الحالة · reversals — كل وعاء وإلى أين عُكِس)، عبر دالّة _refund_reversals (كامل ⟶ كل وعاء لأصله؛ جزئيّ ⟶ رصيد محفظة).
  • الواجهة: صفحة OpsSplitPayments تُظهر سطر «↩ استرداد» مع تفصيل العكس لكل وعاء.
