① الخلاصة

بإذنك «فعّل version_id_col» — أصلحتُ FINDING-2 (تزامن آلة حالات الطلب) جذريًّا بتفعيل القفل التفاؤليّ الذي قصده المطوّرون أصلًا بعمود version لكنّهم لم يُفعّلوه. الآن أيّ انتقالين متزامنين على نفس الطلب: واحد ينجح، والآخر يحصل على 409 نظيف (يُعيد القراءة والمحاولة) — بدل تباعد حالة الطلب عن آثارها الجانبيّة.

طبيعة الإصلاح
قفل تفاؤليّ على مستوى النموذج (تغيير واحد) يحمي كلّ المُستدعين دفعةً واحدة
بلا قفل تشاؤميّ
لا حاجة لقفل كلّ مُستدعٍ يدويًّا — version_id_col يكفي
الترحيل / المال
بلا migration (عمود version قائم) · بلا تغيير مبلغ · FIN-COR PASS

② العيب المُعالَج — FINDING-2 (من تدقيق آلة الحالات)

apply_order_transition كان يقرأ from_state ← يتحقّق ← يضبط order_state (check-then-act) بلا قفل؛ وعمود Order.version موجود لكن بلا version_id_col فهو عدّاد زخرفيّ؛ والمُستدعون غير متّسقين (بعضهم يقفل، أكثرهم لا). ⇒ انتقالان متزامنان (إلغاء + قبول) قد يمرّان معًا ⇒ تباعد الحالة عن آثارها.

③ كيف يعمل القفل التفاؤليّ

تحميل الطلب (version=5)← تعديل order_state← flush → UPDATE … SET version=6 WHERE id=… AND version=5← 0 صفوف؟ ⇒ StaleDataError ⇒ 409

إذا عدّل خيطٌ آخر الطلب بين التحميل والكتابة، تصير version=6 فعليًّا، فشرط WHERE version=5 لا يطابق ⇒ تُرفَض الكتابة الثانية (لا تطمس الأولى). SQLAlchemy يدير الزيادة تلقائيًّا.

④ الخطوات الأربع بالكود

1 — تفعيل القفل على نموذج Order

version: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
__mapper_args__ = {"version_id_col": version}

2 — إزالة 3 زيادات يدويّة (لتجنّب double-increment)

- if bump_version and hasattr(order, "version"): order.version += 1   # state_transitions:182
- if hasattr(order, "version") and ...: order.version += 1            # driver_emergency_router:191
- if hasattr(order, "version") and ...: order.version += 1            # operations_router:665
# الثلاثة تعدّل order_state أيضًا ⇒ الزيادة تلقائيّة الآن عبر version_id_col

3 — مُعالِج عامّ StaleDataError → 409

@app.exception_handler(StaleDataError)
async def stale_data_handler(request, exc):
    return JSONResponse(status_code=409, content=make_error(
        code=ErrorCodes.CONFLICT, retryable=True,
        message_ar="تم تعديل الطلب من جهة أخرى في الوقت نفسه، يرجى إعادة المحاولة", …))

4 — تأكيد fail-open للحلقات الخلفيّة

حلقات (release/escalation/abandonment) تلتقط Exception مزدوجًا ⇒ StaleDataError يُلتقَط ويُسجَّل وتُكمل الدورة (تُعيد الطلب المُتعارَض في الدورة التالية، لا تنهار).
