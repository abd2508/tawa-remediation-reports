1. Stage-2 Postgres Init — Recommended Approach

The recommended strategy combines the pg_dump --schema-only snapshot (rank 1) with the alembic stamp pattern (rank 2) and a separate migrate service in Docker Compose. This is the industry standard for platforms that have reached schema stabilisation.

Why not full migration run (current state)

171 migrations take 20–45 s on a cold SSD. The current start_period: 20s healthcheck fires before migrations complete, causing the condition: service_healthy chain to fail. There is zero retry logic in entrypoint.sh — one transient postgres hiccup during the 171-migration window crashes the container permanently (no restart policy).

Why pg_dump + stamp

pg_dump captures the final state of all 171 migrations in ~3–5 seconds of init time. The alembic stamp pattern makes alembic own the version record without re-running any DDL. Subsequent new migrations (ab21, ab22 …) still apply correctly via the normal upgrade head path in the entrypoint.

Key invariant: The pg_dump snapshot and the revision string in 03_stamp.sql must be taken from the same database state at the same instant. A mismatch between the schema in 02_schema.sql and the stamp in 03_stamp.sql causes alembic to either skip real migrations or re-run already-applied ones.

Architecture Overview

Container startup sequence
postgres:16-alpine (custom image)
  ├── /docker-entrypoint-initdb.d/01_extensions.sql  → CREATE EXTENSION pg_trgm
  ├── /docker-entrypoint-initdb.d/02_schema.sql       → full DDL (functions, triggers, tables, indexes)
  └── /docker-entrypoint-initdb.d/03_stamp.sql        → INSERT alembic_version

  Only fires on empty /var/lib/postgresql/data
  ~5–8 seconds total; postgres healthcheck fires after this completes

migrate service (one-shot)
  └── alembic stamp head  (if alembic_version row absent)
       OR
      alembic upgrade head (applies any new migrations since the image was cut)
  exits 0 → triggers service_completed_successfully

backend-core
  depends_on: migrate (service_completed_successfully)
  → uvicorn starts; start_period: 30s is ample (no migrations here)

Update entrypoint.sh with the stamp-detect pattern

Replaces the current unconditional alembic upgrade head. The entrypoint now checks whether alembic_version is empty and stamps vs. upgrades accordingly.

backend/entrypoint.sh (full replacement)
#!/bin/sh
set -e

# Detect whether this is a fresh schema (init.sql just ran) or an existing DB.
# alembic_version empty → init.sql schema is already correct → stamp head only.
# alembic_version present → apply any new migrations since the image was cut.
COUNT=$(psql "$DATABASE_SYNC_URL" -tAc \
  "SELECT COUNT(*) FROM public.alembic_version" 2>/dev/null || echo 0)

if [ "$COUNT" -eq 0 ]; then
  echo "[entrypoint] Fresh schema detected — stamping head (ab20_staff_evaluation)"
  alembic stamp head
else
  echo "[entrypoint] Existing DB — running alembic upgrade head"
  alembic upgrade head
fi

exec uvicorn app.main:app --host 0.0.0.0 --port 8000
Requires psql in the backend container. Verify: docker exec tawalocal-backend-core-1 which psql. If absent, add libpq-dev or postgresql-client to the backend Dockerfile's apk/apt install step, or use the Python-psycopg2 count query variant below as a fallback.
Python fallback (if psql unavailable in container)
# Replace the COUNT=$(psql ...) block with:
COUNT=$(python3 -c "
import os, psycopg2
url = os.environ.get('DATABASE_SYNC_URL','')
try:
    conn = psycopg2.connect(url)
    cur = conn.cursor()
    cur.execute('SELECT COUNT(*) FROM public.alembic_version')
    print(cur.fetchone()[0])

except: print(0)

Create rebuild script

scripts/rebuild-db-image.sh
#!/bin/bash
set -e
REPO_ROOT=$(git rev-parse --show-toplevel)
cd "$REPO_ROOT"

# 1. Get current alembic head
HEAD=$(python3 -c "
from alembic.config import Config
from alembic.script import ScriptDirectory
cfg = Config('backend/alembic.ini')
sd = ScriptDirectory.from_config(cfg)
print(sd.get_current_head())
")
echo "[rebuild] Head: $HEAD"

# 2. Verify source DB matches head
DB_HEAD=$(docker exec tawalocal-postgres-1 psql -U postgres -d libya_platform \
  -tAc "SELECT version_num FROM public.alembic_version" 2>/dev/null)
if [ "$DB_HEAD" != "$HEAD" ]; then
  echo "ERROR: source DB is at $DB_HEAD, expected $HEAD. Run migrations first."
  exit 1
fi

# 3. Regenerate schema dump
docker exec tawalocal-postgres-1 pg_dump \
  --schema-only --no-owner --no-acl \
  --no-comments --no-tablespaces \
  --clean --if-exists --encoding=UTF8 \
  -U postgres -d libya_platform \
  > docker/postgres-init/02_schema.sql

# 4. Update stamp file
cat > docker/postgres-init/03_stamp.sql << EOF
-- Tawa Stage-2: Alembic version stamp (auto-generated by rebuild-db-image.sh)
-- Head: $HEAD  Generated: $(date -u +%Y-%m-%dT%H:%M:%SZ)
INSERT INTO public.alembic_version (version_num)
VALUES ('$HEAD')
ON CONFLICT DO NOTHING;
EOF

# 5. Build image tagged with head revision
docker build -f docker/postgres-init/Dockerfile \
  -t tawa-postgres:$HEAD \
  -t tawa-postgres:latest \
  docker/postgres-init/

echo "[rebuild] tawa-postgres:$HEAD built successfully"
echo "[rebuild] Update docker-compose.yml image: tawa-postgres:$HEAD"

3. The Three SQL Files — Purpose and Rules

File Source Purpose Update Trigger Must Be Idempotent?
01_extensions.sql Hand-written CREATE EXTENSION IF NOT EXISTS pg_trgm. Runs before schema — pg_trgm must exist before the GIN trgm indexes in 02_schema.sql are created. Never (unless a new extension is added to migrations) Yes — IF NOT EXISTS
02_schema.sql pg_dump --schema-only from a fully-migrated live DB All DDL: tables, constraints, indexes, sequences, functions (arabic_normalize, check_journal_balanced), triggers (ledger_journal_balanced), views. Automatically includes alembic_version TABLE DDL but NOT its rows. Every new Alembic migration. Run rebuild script. Yes — --clean --if-exists prepends DROP IF EXISTS before each object
03_stamp.sql Hand-written (auto-updated by rebuild script) INSERT the current head revision into alembic_version so alembic finds the correct state on first startup. Must match the DB state captured in 02_schema.sql exactly. Every new Alembic migration (same trigger as 02). Rebuild script auto-updates this. Yes — ON CONFLICT DO NOTHING
Critical: search_path is empty after pg_dump header. pg_dump emits SELECT pg_catalog.set_config('search_path', '', false);. Every SQL statement in 02_schema.sql that pg_dump generated is fully schema-qualified (public.tablename). The hand-written 03_stamp.sql must also be schema-qualified — use public.alembic_version, never bare alembic_version. 01_extensions.sql runs in a separate psql session so it is unaffected.

What pg_dump captures (relevant to Tawa)

  • All 171 migrations' final DDL state — tables, columns, constraints, indexes
  • arabic_normalize(TEXT) IMMUTABLE plpgsql function
  • check_journal_balanced() trigger function
  • ledger_journal_balanced CONSTRAINT TRIGGER (DEFERRABLE INITIALLY DEFERRED)
  • pg_trgm GIN indexes (assuming 01_extensions.sql ran first)
  • All feature_toggle seed rows — NO (schema-only; data is NOT captured)
  • alembic_version TABLE — YES; alembic_version ROW — NO
Feature toggle seeded rows are NOT in 02_schema.sql. 60 migrations use op.execute() for INSERT statements — these are data, not schema. On a fresh Stage-2 container, the backend will start without any feature_toggle rows. Verify on first boot: SELECT name, enabled FROM feature_toggles ORDER BY name;. If toggles control critical behavior (split_payment, loyalty), they must be seeded separately or via a post-init migration. The preferred approach is a dedicated 04_seed_feature_toggles.sql generated from the live DB with pg_dump --data-only --table=feature_toggles.

4. Dockerfile — Exact Content

docker/postgres-init/Dockerfile
# Tawa Stage-2 — Custom postgres image with baked-in schema
# Build: docker build -f docker/postgres-init/Dockerfile -t tawa-postgres:ab20 docker/postgres-init/
# Tag convention: tawa-postgres:{alembic_head}
# Rebuild trigger: every new Alembic migration (use scripts/rebuild-db-image.sh)

FROM postgres:16-alpine@sha256:4e6e670bb069649261c9c18031f0aded7bb249a5b6664ddec29c013a89310d50

# Encoding args only apply on first init (empty data directory).
# These match the values used when the source DB was initialized.
ENV POSTGRES_INITDB_ARGS="--encoding=UTF8 --lc-collate=C --lc-ctype=C"

# Docker executes .sql files in /docker-entrypoint-initdb.d/ in
# lexicographic order (01 → 02 → 03). Each file runs in a separate
# psql session with -v ON_ERROR_STOP=1 — any SQL error stops init.
COPY 01_extensions.sql /docker-entrypoint-initdb.d/
COPY 02_schema.sql     /docker-entrypoint-initdb.d/
COPY 03_stamp.sql      /docker-entrypoint-initdb.d/

# Optional: include seed data for feature_toggles
# COPY 04_seed_feature_toggles.sql /docker-entrypoint-initdb.d/
The digest pin is mandatory. postgres:16-alpine without a digest is a mutable tag — a CI rebuild six months from now could silently pull a different image. The digest sha256:4e6e670bb069649261c9c18031f0aded7bb249a5b6664ddec29c013a89310d50 was verified from the existing docker-compose.yml. Keep it pinned here.

5. Top 15 Critical Scenarios

BUILD-05 CRIT 02_schema.sql generated but 03_stamp.sql left at old revision
Trigger: Developer runs pg_dump manually, forgets to update 03_stamp.sql. Image built and deployed.
Impact: alembic finds e.g. aa15 stamped, attempts to run migrations aa16–ab20. Tables already exist → crash-loop.
Use scripts/rebuild-db-image.sh which atomically updates both files and verifies they match before building.
BUILD-06 CRIT 02_schema.sql generated without 01_extensions.sql running first
Trigger: pg_dump run against a DB that had pg_trgm active; dump includes GIN trgm indexes. On a fresh container, 02_schema.sql executes before 01_extensions.sql (wrong sort order).
Impact: CREATE INDEX USING gin(... gin_trgm_ops) fails — extension not yet loaded. Full init fails.
File naming guarantees order: 01 always before 02. Verify with ls docker/postgres-init/ — must be 01 < 02 < 03. The --clean --if-exists flag makes 02 self-repairing on re-run.
STARTUP-02 CRIT alembic_version empty on a non-fresh DB (corrupt state)
Trigger: Someone manually deletes the alembic_version row or truncates the table on a running deployment.
Impact: Entrypoint sees COUNT=0, stamps head. But the schema is not guaranteed to match ab20 if this is a database that was at a different revision. Silent mismatch.
The stamp path should also verify: SELECT COUNT(*) FROM information_schema.tables WHERE table_name='orders' > 0 as a secondary check. Add this guard to entrypoint.sh for production.
STARTUP-17 CRIT pg_isready returns true before initdb.d scripts finish
Trigger: postgres accepts connections (pg_isready = success) while 02_schema.sql is still executing. The migrate service starts, sees alembic_version empty, stamps or upgrades against a half-initialized schema.
Impact: Race condition. Intermittent failures on fast hardware.
The start_period: 20s on postgres healthcheck covers initdb (~5–8 s). The first successful pg_isready probe only counts after start_period elapses, by which time initdb is complete. Do not reduce start_period below 15s.
OPS-14 CRIT Team uses 02_schema.sql as a production backup/restore mechanism
Trigger: Developer sees 02_schema.sql and assumes it is a full backup. Restores from it during incident. All data is lost.
Impact: Complete data loss on production.
Add a prominent comment at the top of 02_schema.sql: -- SCHEMA DDL ONLY — NO DATA. Use pg_dump without --schema-only for backups. Document this in ops runbook.
OPS-04 HIGH Feature toggle rows absent on fresh container
Trigger: Stage-2 init creates schema without data. split_payment_enabled, loyalty_redemption_enabled are missing from feature_toggles. Backend code reads them on startup and crashes or defaults to wrong state.
Generate 04_seed_feature_toggles.sql from live DB: docker exec postgres pg_dump --data-only --table=feature_toggles -U postgres -d libya_platform. Include in custom image. Re-generate alongside 02_schema.sql.
OPS-24 HIGH New migration ab21 deployed without rebuilding custom postgres image
Trigger: Developer adds migration ab21, deploys backend, but the postgres image is still baked at ab20. Backend entrypoint stamps ab20, alembic skips ab21 (COUNT > 0 path runs upgrade head → applies ab21 correctly). Actually this is fine — this is the designed path. Only fails if the stamp path fires on a non-fresh DB.
The designed behavior handles this correctly. The entrypoint only stamps on COUNT=0 (fresh DB). Existing DBs always run upgrade head, which applies ab21. Document this in team onboarding.
RECOVERY-04 CRIT docker compose down -v on production
Trigger: Anyone runs docker compose down -v. The pg_data named volume is deleted. All data is lost. init.sql recreates the schema on next start but all orders, users, providers are gone.
The custom image with baked schema makes recovery fast (fresh schema in 8 s) but does NOT replace backups. Implement pg_dump cron backup BEFORE Stage-2 deploy. Restrict docker compose down -v to documented disaster-recovery runbook only.
BUILD-11 HIGH CONCURRENTLY index added to a future migration causes initdb failure
Trigger: A future migration uses CREATE INDEX CONCURRENTLY. This requires being outside a transaction. Docker's initdb runs each file in a transaction. The index creation fails with "ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block."
The analysis confirms zero CONCURRENTLY indexes in current 171 migrations. Add a lint check to CI: grep -r CONCURRENTLY backend/alembic/versions/ && echo "WARN: CONCURRENTLY index found — requires special handling in init.sql". For any future CONCURRENTLY index, the rebuild script must add a post-transaction CREATE INDEX CONCURRENTLY call outside the main DDL block.
STARTUP-09 HIGH postgres container has no restart policy — stays crashed
Trigger: postgres OOM killed or disk full. Current config has no restart policy (Docker default = no). Container stays dead. All services that depend on it are stuck. Manual intervention required.
Add restart: unless-stopped to postgres service in docker-compose.yml. This is a one-line change. Also add to backend-core and redis.
TEAM-21 HIGH Manual pg_dump taken at wrong moment (partial transaction)
Trigger: pg_dump run while an alembic upgrade is in progress. The dump captures a schema at an intermediate migration state. The stamp in 03_stamp.sql claims ab20 but schema is actually at ab18.
The rebuild script verifies source DB head BEFORE running pg_dump. Never run pg_dump manually for init.sql — always use the rebuild script which enforces this order.
BUILD-14 MED 02_schema.sql committed but not rebuilt after 3 migrations
Trigger: Developer adds ab21, ab22, ab23 over 3 days but only rebuilds the image after ab23. The commit history shows 02_schema.sql updated once for ab23. Team member tries to set up dev env between ab21 and ab22.
The upgrade head path in entrypoint handles this: the entrypoint stamps only COUNT=0. If someone spins up against an image at ab20 and the backend is at ab22, upgrade head runs ab21+ab22. The init image is a performance optimization, not a correctness dependency.
OPS-12 MED arabic_normalize function lost — not captured in pg_dump
Trigger: pg_dump run with a flag that excludes functions, or against a DB where the function was never created. GIN trgm indexes that depend on arabic_normalize fail at query time.
Verify after dump generation: grep -c "arabic_normalize" docker/postgres-init/02_schema.sql must return ≥ 2 (definition + at least one usage). Add this check to the rebuild script.
STARTUP-22 MED DATABASE_SYNC_URL not set — entrypoint psql call fails silently
Trigger: New environment missing DATABASE_SYNC_URL env var. The psql "$DATABASE_SYNC_URL" call in entrypoint.sh uses an empty URL, fails, the || echo 0 catches it, COUNT=0, and the entrypoint stamps on an existing DB.
Add explicit env check at top of entrypoint.sh: [ -z "$DATABASE_SYNC_URL" ] && echo "ERROR: DATABASE_SYNC_URL not set" && exit 1. Document required env vars in docker-compose.yml comments.
BUILD-20 MED ledger_journal_balanced trigger missing from dump — function defined after trigger
Trigger: pg_dump dependency ordering puts the trigger before the function definition (should not happen but possible with --clean). The function CREATE fails because the trigger references it.
pg_dump handles dependency ordering correctly — function definitions always precede the triggers that reference them. Verify: grep -n "check_journal_balanced\|ledger_journal_balanced" 02_schema.sql — function definition line number must be lower than trigger definition line number.

8. DECIDED: Multi-File vs Single init.sql

Decision
Multi-file approach: 01_extensions.sql + 02_schema.sql + 03_stamp.sql

Rejected: single init.sql combining all three.

Reason 1 — Ordering integrity: pg_trgm extension must exist before the GIN trgm indexes in the schema dump. Separate files with lexicographic naming (01/02/03) enforce this order unconditionally, with no reliance on careful editing of a monolithic file.

Reason 2 — Targeted regeneration: When a new migration is added, only 02_schema.sql and 03_stamp.sql need regeneration. 01_extensions.sql is stable and never needs to change unless a new extension is introduced. In a single-file setup, the whole file is regenerated and the extension line can drift.

Reason 3 — Error isolation: Docker's initdb runs each file as a separate psql session with -v ON_ERROR_STOP=1. A failure in 02_schema.sql does not silently skip 01_extensions.sql. Error output names the exact failing file.

Reason 4 — Diffability: A schema regeneration produces a clean diff on 02_schema.sql only. Code review can see exactly what changed between ab20 and ab21. A single file changes entirely.

9. DECIDED: Update Policy After New Migrations

Decision
Regenerate on every new Alembic migration using scripts/rebuild-db-image.sh

Trigger: Any new migration file added to backend/alembic/versions/.

What the rebuild script does atomically: (1) verifies source DB is at the correct head, (2) pg_dumps to 02_schema.sql, (3) updates 03_stamp.sql with the new head, (4) builds and tags the image as tawa-postgres:{head}.

Image tagging convention: tawa-postgres:ab20, tawa-postgres:ab21, etc. The tag encodes the migration head, making it immediately visible in docker ps or docker images which schema version is running.

Why not lazy regeneration (only when performance matters): The stamp in 03_stamp.sql must always match the schema in 02_schema.sql. Allowing them to drift — even temporarily — creates a class of bugs (scenario BUILD-05) that are extremely hard to diagnose. The rebuild script takes ~30 seconds and prevents an entire category of production incidents.

Exception: If the source DB (the fully-migrated reference DB) is not available at migration time (e.g., the migration is written and reviewed before deployment), defer the image rebuild to immediately before the migration is applied to a live DB. Never commit a 03_stamp.sql pointing to a revision that is not yet in the reference DB.

10. Multi-Device group_id — Recommended Approach

Remove the localStorage dependency entirely. The group_id column already exists on the Order model and is populated for all group orders. The bug is a pure serialization gap — the data has been in the database since the cart feature shipped; it just was never included in the API response.

The localStorage approach fails on a second device by design. localStorage is per-origin per-browser-instance. An order placed on desktop is invisible as a group order on mobile. The server already knows the relationship — it is stored in orders.group_id. Using localStorage to reconstruct this relationship is architecturally incorrect.

What changes

  • Backend: 1 field added to Pydantic schema + 1 line in serializer
  • Frontend: 2 hooks deleted, 1 render expression changed, 1 type updated
  • Tests: MSW mock updated, new Vitest tests for badge render

What does NOT change

  • No database migration — column already exists
  • No new API endpoint
  • No TanStack Query change — group_id rides on the existing orders query
  • Zero N+1 — group_id is a column on the Order row

16. DECIDED: localStorage Cleanup Strategy

Decision
Add one-time removeItem in main.tsx; do NOT add transitional dual-source logic

Rationale: Backend and frontend deploy together in this project. There is no window where new frontend talks to old backend (deploy is atomic). The transitional dual-source approach (reading both order.group_id AND localStorage) adds 15+ lines of code that must be reverted in a second PR — this increases risk without benefit in an atomic deploy context.

In main.tsx (or auth initialization), add once:

// One-time cleanup — remove old localStorage group map after API migration
// Safe to call on every app start; removeItem on missing key is a no-op
try {
  localStorage.removeItem('tawa_group_map');
} catch {
  // private browsing / quota errors — silent ignore
}

Also add to logout handler alongside other session cleanup to prevent cross-user leakage on shared devices.

18. DECIDED: Pydantic v2 Syntax

Decision
Use str | None = None (modern Python 3.10+ union syntax)

Rejected: Optional[str] = None (Pydantic v1 style).

Both are runtime-identical in Pydantic v2. The modern form is preferred because it is shorter, requires no import, and aligns with the Python 3.10+ standard that is active in this codebase. Pydantic v2 documentation uses this form in all examples.

If the file already uses Optional throughout: add the new field with str | None = None regardless. Do not refactor existing Optional fields in the same PR — that is a scope expansion with no functional benefit. Mixed use within the same file is acceptable in Pydantic v2.
