المنهجية (مهم)

منفذ الوكلاء (الوكيل) محجوب من الوصول المباشر للإنترنت، لذا نُفِّذت كل التدفّقات من جهة الخادم (SSH) بضرب الـ API الحيّ https://tawanow.com/api فعلياً: تسجيل حسابات جديدة، موافقات غرفة العمليات، توقيع عقود، طلبات نقدية، وتسليم كامل — كتابات حقيقية في قاعدة الإنتاج. رموز OTP تُجلب من سجلّ حاوية الخلفية. هذا «حقيقي وليس محاكى» ضمن حدود البيئة (لا متصفّح بشري على الموقع العامّ من هنا).

مراقب الانحراف: كل نتيجة موثّقة برمز HTTP فعلي + الخطوة. النتائج التي تبيّن أنها أخطاء في أداة الاختبار (لا عيوب منصّة) أُعيد تصنيفها صراحةً (انظر القسم الأخير) لتجنّب الهلوسة/الإبلاغ الكاذب.

1) ملخّص تنفيذي

دورة الحياة الكاملة عبر جميع الأدوار نجحت حتى DELIVERED على الإنتاج. عميل جديد سجّل وطلب؛ مزوّد جديد سجّل ووافقت عليه غرفة العمليات ووقّع العقد ونشر صنفاً؛ سائق جديد سجّل ووُوفِق عليه ووقّع؛ موظّف انضمّ بكود دعوة؛ ثم سُلِّم الطلب نقداً مع حساب مالي صحيح (سلع+رسم، مقرّب لـ250).

الجوهر سليم. العيوب المؤكَّدة تقع عند حواف الإعداد/التفعيل لا في مسار المال: أبرزها أنّ المزوّد بعد اكتمال الإعداد (موافقة+عقد+نشر) يبقى «غير متاح» حتى يفعّل علَمين منفصلين يدوياً، وعدم اتّساق في رموز مستندات KYC، وعدم إنشاء عرض تلقائي للسائق المتاح.

3) العيوب المؤكَّدة (مرتّبة بالخطورة)

#الخطورةالعيبالدليل الحيّالتوصية
PROV-1عالٍالمزوّد بعد اكتمال الإعداد (موافقة+عقد+نشر) يبقى «Provider is not available» ويرفض الطلبات حتى يفعّل علَمين منفصلين يدوياً: PUT /providers/me/status {active_now} وPOST /providers/me/accept-toggle {is_accepting_orders}. لا يوجد زرّ «افتح المتجر» واحد، ومزوّد جديد لن يكتشف ذلك.create order → 422 «Provider is not available»؛ بعد ضبط العلَمين → 201زرّ «متصل/مفتوح» واحد يضبط العلَمين، أو تفعيلهما افتراضياً بعد توقيع العقد + أول نشر؛ ورسالة الطلب تشرح السبب.
PROV-2متوسطلا يمكن نشر صنف قبل إضافة سعر/variant — availability=PUBLISHED يردّ 422 برسالة غير مُرشدة، ومسار «الموافقة على الصنف» في غرفة العمليات يردّ NOT_PENDING (الصنف ليس قيد مراجعة أصلاً) فيضلّل.publish 422 (قبل variant) → variant 201 → publish 200؛ moderation approve 422 NOT_PENDINGرسالة واضحة «أضِف سعراً قبل النشر»؛ توضيح متى يخضع الصنف للمراجعة.
KYC-1متوسطرموز مستندات KYC غير متّسقة: commercial_register مقبول (200) بينما owner_id وfood_license مرفوضان (422). مزوّد يخمّن أسماء شائعة يُحجَب.upload owner_id 422 · food_license 422 · commercial_register 200كشف قائمة doc_type المسموحة عبر نقطة عامة (مثل نمط N2) وعرضها في الواجهة.
D-5متوسطالتوزيع التلقائي لم يُنشئ عرضاً لسائق متاح على نفس الإحداثيات بعد جهوزية الطلب؛ تطلّب تدخّل غرفة العمليات لإنشاء العرض يدوياً.GET /dispatch/offers فارغ بعد ready+available → أنشأت OPS العرضفحص مسار auto_dispatch/GEO وأهلية السائق الطازج (سجلّ السائق/الإحداثيات/التوقيت) — مذكور كاحتمال GEOSEARCH/eligibility.
CUST-6منخفضمعاينة الرسم أعادت distance_km=0.0 (رسم أساسي فقط) — يحتمل غياب إحداثيات المزوّد المختار.delivery-quote 200 · distance_km=0.0تأكيد ضبط إحداثيات المزوّدين؛ مؤشّر «تقديري» عند غياب المسافة.

4) مراقب التدفّق — سلامة العمليات عبر اللوحات والخلفية

  • آلة الحالات سليمة: AWAITING_PROVIDER_ACCEPTANCE → ACCEPTED → IN_PREPARATION → READY_FOR_PICKUP → DRIVER_ASSIGNED → DRIVER_AT_PROVIDER → EN_ROUTE → ARRIVED → DELIVERED، كلّ انتقال بسلطته الصحيحة (الاستلام بسلطة المزوّد عبر verify-pickup).
  • المال سليم عبر الأدوار: التحصيل النقدي 48.000 = سلع 45.000 + رسم 3.000، مقرّب لـ250؛ يتطابق مع cash_due_minor المعروض للعميل.
  • حواجز الصلاحيات تعمل: العقد يحجب العمل حتى التوقيع؛ غرفة العمليات تملك الموافقة والتوزيع؛ بوابة قيد CHECK الجديدة (aa22) فعّالة على الإنتاج.
  • فجوة التفعيل (PROV-1) هي أبرز انقطاع في تدفّق الإعداد→التشغيل.

5) مراقب الانحراف — تصحيح ادّعاءات

  • «التقييمات معطّلة (422)» — أُعيد تصنيفها: ليست عيباً. سبب 422 = إغفال أداة الاختبار للحقل المطلوب target_id في POST /orders/{id}/ratings (يتطلّب target_type + target_id + stars). ملاحظة UX حقيقية فقط: تأكّد أنّ استجابة تتبّع العميل تكشف driver_id ليتمكّن من تقييم السائق.
  • «publish 422» أوّل مرة لم يكن بوابة مراجعة بل غياب variant — صُحِّح بعد إضافة السعر (PROV-2).
  • كل رمز HTTP أعلاه من تشغيل فعليّ؛ لا توجد نتائج مُستنتجة بلا دليل.

6) التقييم العام والأولويات

الحكم: المنصّة تؤدّي دورة الأعمال الكاملة (إعداد بموافقة وعقود → طلب → تسليم نقدي → دفتر مالي) على الإنتاج بنجاح. جاهزة للتجربة الداخلية؛ العيوب المُكتشفة لا تمنع التشغيل لكنها تعيق الإعداد الذاتي لمزوّد/سائق جديد دون مساعدة.

أولويات الإصلاح:

  1. PROV-1 زرّ «افتح المتجر» موحّد (أو تفعيل تلقائي بعد العقد+النشر) — أعلى أثر على تجربة المزوّد الجديد.
  2. D-5 التحقّق من التوزيع التلقائي للسائق المتاح.
  3. KYC-1 كشف قائمة doc_type المسموحة.
  4. PROV-2 رسائل نشر الصنف الموجِّهة.
  5. منخفض CUST-6 (إحداثيات/تقدير الرسم) · API-3 (201).

بيانات اختبار أُنشئت على الإنتاج (مُوَسَّمة، للحذف): عملاء/مزوّد/سائق/موظّف بأسماء «خبير-*» + 2 طلب (093331e7 AWAITING، 04272b8c DELIVERED). يمكن حذفها عند الطلب.
