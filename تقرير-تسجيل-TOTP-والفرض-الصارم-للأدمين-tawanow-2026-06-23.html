١) المنهج — لماذا على مرحلتين

التسلسل الآمن المُطبَّق: المرحلة (أ) تسجيل TOTP + التحقّق من دورة الدخول الكاملة ← إثبات أنّك لن تُقفَل │ (report-only ما زال فعّالاً هنا → admin/admin غير محجوب فيُمكِن التسجيل) ▼ المرحلة (ب) قلب MFA_REPORT_ONLY=false → الفرض الصارم ← كلمة المرور وحدها لا تكفي │ ▼ تحقّق نهائيّ: admin/admin → requires_totp → كود → توكن كامل ✓

القاعدة: لا نُفعّل الفرض إلّا بعد إثبات أنّ صاحب الحساب يستطيع إكمال الدخول بالعامل الثاني — وإلّا فخطر قفل أوّل-تشغيل (دجاجة-وبيضة).

٢) المرحلة (أ): تسجيل TOTP — خطوة بخطوة (مُتحقَّقة حيّاً)

٤) أثر الفرض على الحسابات المُمتازة الأخرى

الأدوار المُلزَمة الآن: SUPER_ADMIN · OPERATIONS_AGENT · FINANCE_AGENT · COMPLIANCE_AGENT.

  • أيّ حساب بأحد هذه الأدوار وبلا TOTP مُسجَّل سيحصل عند الدخول على توكن تسجيل مُقيَّد فقط ولن يستطيع تنفيذ أيّ إجراء حتى يُسجِّل TOTP (عبر /auth/totp/setup ثم /enable — التوكن المُقيَّد يسمح بهاتين فقط).
  • هذا هو الفرض المقصود؛ إن وُجد موظّفو OPS فعليّون، أبلغهم بتسجيل TOTP عند أول دخول.
  • العملاء والسائقون والمزوّدون غير متأثّرين (ليسوا أدواراً مُمتازة).

٥) 🆘 break-glass — إن فقدتَ السرّ أو قُفِلت

على الخادم في /home/deploy/platform (نسخة احتياطيّة من الإعداد موجودة: /tmp/staging.yml.bak.*):

  1. تعطيل الصرامة فوراً (يعود admin/admin للعمل):
    sed -i 's/MFA_REPORT_ONLY: "false"/MFA_REPORT_ONLY: "true"/' docker-compose.staging.yml docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d backend-core
  2. أو إلغاء TOTP لـadmin عبر قاعدة البيانات:
    docker exec -it tawa-postgres-1 psql -U <user> -d <db> \ -c "UPDATE users SET totp_enabled=false WHERE username='admin';"
  3. إعادة تسجيل سرّ جديد: كرّر المرحلة (أ) (login → setup → enable).
